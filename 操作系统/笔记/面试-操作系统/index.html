    用户态和内核态

    内核态和用户态是操作系统中的两种运行模式。主要区别在于 权限和可执行的操作 ：

    **【内核态】：**在内核态下，CPU可以执行所有的指令和访问所有的硬件资源。

    这种模式下的操作具有更高的权限，主要用于 操作系统内核的运行 。

    【 用户态】：在用户态下，CPU只能执行部分指令集 ， 无法直接访问硬件资源 。

    这种模式下的操作权限较低，主要用于 运行用户程序 。

    分为内核态和用户态的原因

    安全性：通过对权限的划分，用户程序无法直接访问硬件资源，从而避免了恶意程序对系统资源的破坏。

    稳定性：用户态程序出现问题时，不会影响到整个系统，避免了程序故障导致系统崩溃的风险。

    用户态和内核态转换

    系统调用（Syscall）

    用户进程需要访问 文件、网络、设备 等资源时，会触发 系统调用 （如 read() 、 write() ）。

    中断（Interrupt）

    硬件中断 （如键盘输入、网卡接收数据）或 软件中断 （如 SIGSEGV ）。

    内核需要响应中断，调度相应的处理程序。

    异常（Exception）

    比如 缺页异常 （Page Fault），程序访问不在内存的页，触发异常，进入内核态加载数据。

    进程调度

    操作系统 决定切换到另一个进程 时，会进入内核态，执行任务切换。

    切换耗时优化

    减少系统调用

    批量 I/O ：减少 read/write 频率，比如 mmap 直接映射文件到内存，避免频繁 read() 。

    零拷贝（Zero-copy） ：

    sendfile() 直接在内核态拷贝数据，避免用户态-内核态切换。

    Netty 的 ByteBuf 使用 堆外内存（DirectByteBuffer） ，减少拷贝次数。

    减少进程切换

    使用 epoll 代替 select/poll （epoll 事件驱动减少 CPU 开销）。

    使用 io_uring （Linux 5.1 引入，减少系统调用）。

    使用用户态网络协议栈（DPDK）

    传统网络协议栈需要 内核态处理 ，可以使用 DPDK 让网络协议栈跑在 用户态 ，减少切换。

    中断和异常

    中断 ：外部设备触发，异步发生（I/O 完成、时钟中断）。

    异常 ：CPU 执行指令时触发，同步发生（除零、缺页、非法指令）

    中断 是操作系统核心的基础机制，是CPU响应硬件或软件事件的方式。

    工作原理 ：当某个事件（如键盘被按下、网卡收到数据、时钟芯片计时到期）发生时，它会向CPU发送一个 中断信号 。CPU会 立即暂停当前正在执行的指令 ，保存当前现场，然后转去执行一个预先设定好的 中断服务程序 来处理这个事件。处理完毕后，再恢复之前保存的现场，继续执行被中断的任务。

    中断时 CPU 做什么

    中断请求： 当外部硬件设备或程序触发中断时，CPU 会接收到一个中断请求信号。

    保存当前状态： 当 CPU 接收到中断信号时，会先保存当前正在执行的程序的状态。

    保存程序计数器（PC）中的值，这样可以确保中断处理完毕后，能够继续执行之前的程序。

    保存 CPU 的寄存器值（程序状态字、堆栈指针等），确保执行中断处理程序时不会丢失之前的工作状态。

    中断向量表： 中断被识别后，CPU 会根据中断类型查找中断向量表。该表存储了不同中断类型对应的处理程序的地址。

    执行中断服务程序： CPU 中断处理程序，执行相应的操作。这些操作可能包括响应、处理异常

    恢复现场： 中断处理完毕后，CPU 会从堆栈中恢复之前保存的程序计数器和寄存器状态，恢复程序的执行，继续执行中断前的代码。

    常见系统调用
    分类 示例系统调用 描述
    进程控制 fork() 、 exec() 、 exit() 创建/执行/退出进程
    文件操作 open() 、 read() 、 write() 、 close() 文件读写、打开关闭
    设备管理 ioctl() 、 read() 、 write() 和设备打交道（如磁盘、终端）
    内存管理 brk() 、 mmap() 、 munmap() 分配和释放虚拟内存空间
    进程通信（IPC） pipe() 、 shmget() 、 semop() 、 socket() 进程间通信手段
    网络通信 socket() 、 bind() 、 connect() 、 recv() 网络编程相关
    信号处理 signal() 、 kill() 异步事件处理
    用户信息 getuid() 、 getpid() 获取用户、进程等信息

    内存分配流程

    请求内存 ：程序通过 malloc() 或 new 请求内存。

    查找空闲块 ：内存管理器在空闲链表中查找合适的内存块（根据算法如首次适应、最佳适应等）。

    分割与分配 ：若找到的块大于需求，将其分割，分配所需部分，剩余部分放回空闲链表。

    更新元数据 ：记录分配的内存块信息（如大小、位置）。

    返回指针 ：返回分配的内存地址供程序使用。

    关键机制 ：

    分页/分段 ：操作系统将物理内存划分为页（如4KB）或段，通过页表管理虚拟地址映射。

    虚拟内存 ：允许使用磁盘空间扩展物理内存，通过缺页中断处理未加载的页。

    碎片管理 ：外部碎片（空闲块分散）和内部碎片（分配块未完全使用）通过算法优化。

    内存分配是用户进程与操作系统协作的过程，主要分为用户态申请、内核态分配、虚拟地址映射三个阶段

    用户态请求 ：应用程序 调用 malloc / new ，触发 用户态内存管理 （如线程缓存 TCache）。如果缓存中有可用内存块直接分配，避免频繁系统调用。

    触发系统调用 ：若缓存不足，用户态通过 brk （扩展堆）或 mmap （匿名映射）向内核申请内存。

    小对象（如 \<64KB）通常用 brk 移动堆顶，

    大对象用 mmap 直接分配独立内存区域。

    内核分配物理内存 ：操作系统通过伙伴系统管理大块连续内存（按 2 的幂次方分割），或通过 Slab 分配器高效复用小对象（如文件描述符）。

    虚拟地址映射 ：内核更新页表，将分配的物理页映射到进程的虚拟地址空间（如堆区）。若未写入数据，可能延迟分配（Copy-on-Write）。

    返回用户态 ：最终将虚拟地址返回给应用程序，完成分配。

    进程管理

    进程vs线程vs协程

    进程 ：资源分配单位，独立内存空间，切换开销大。

    线程 ：CPU调度单位，共享进程内存，需同步机制。

    协程 ：用户态轻量级线程，由程序控制切换，适合 高并发I/O密集型 任务。

    进程（Process）

    定义 ：进程是 操作系统 调度资源的单位，拥有 独立的内存空间 、代码、数据段、堆栈等。

    通信开销大 ：每个进程彼此独立， 进程间通信（IPC）需依赖管道、消息队列、共享内存等 ，效率较低。

    切换开销较大 ： 上下文切换涉及内核态；

    线程（Thread）

    定义 ：线程是 进程内的一个执行单元 ，是 CPU调度基本单位 ，同一进程内的多个线程共享 堆、全局变量 ，但各自有 独立的栈和寄存器 。

    通信高效 ：线程间可以 直接访问共享数据 ， 无需IPC，开销较低 ，但可能产生 数据竞争 。

    切换成本较低 ：线程切换比进程快但仍需 内核调度 ，存在 线程安全问题 （需加锁）。

    适用场景 ：适合 高并发计算和数据共享 ，如Web服务器、数据库查询。

    协程（Coroutine）

    定义 ： 协程 是一种 比线程更轻量级的并发方式 。与线程不同，协程通常 在用户态自己调度 ，而不是操作系统调度，协程的切换不需要上下文切换的开销， 适合 I/O 密集型任务

    单线程执行 ：多个协程在同一个线程内运行，不存在 线程同步问题 ，但 可能因阻塞影响整个线程 。

    特点 ：

    切换极快：在 用户态完成 ；

    多为单线程协作式并发， 主动让出控制权（非抢占） ；

    无需上下文切换 ， 性能最高 、无锁编程， 更适合 IO 密集型场景 ；

    适用场景 ：适合 高并发、I/O密集型任务 ，如 网络爬虫、异步编程（async/await） 。

    语言支持 ：Python（async/await）、 Go（goroutine） 、C++20（协程语法）等

    协程调度策略🟢

    协程由用户程序控制任务的挂起与恢复，通常不涉及内核， 仅在用户态完成 ，

    切换过程只涉及**用户态上下文（栈和寄存器）**的保存与恢复，从

    调度策略上看，协程多为 非抢占式调度 ，调度主动权掌握在协程自身， 调度器 仅负责管理生命周期和 切换逻辑 。

    相比传统多线程模型，协程通过 用户态调度器 实现 轻量切换和非阻塞并发 ，省去了内核态切换成本，尤其 适合 I/O 密集型场景 。

    切换触发 ：由开发者显式控制（通过 yield 、 await 、 resume 、 co_switch() 等）或I/O事件驱动

    调度策略 ：

    协作式调度 ：协程显式调用 yield 或 await 让出执行权，调度器从就绪队列选取下一个。

    抢占式调度 ：调度器通过信号（如Golang的监控线程）中断运行协程。

    I/O阻塞？ ：协程发起 非阻塞I/O操作 ，注册回调后主动切换。

    判断协程是否阻塞

    运行时表现 ：某个协程长时间没有 resume，任务处理堆积，可能是阻塞。

    调度状态 ：比如在 epoll 模型下事件已准备却没有 resume，可以判定逻辑被阻塞。 我会结合 runtime 提供的调试接口，比如 Go 的 PProf、Kotlin 的协程 Debug 模式，甚至设置任务超时机制，捕获潜在的阻塞问题。

    事件驱动（epoll）

    epoll的工作模式 ：

    水平触发（LT） ：只要文件描述符就绪，持续通知。

    边缘触发（ET） ：仅在状态变化时通知一次，需一次性处理所有就绪事件。

    与协程结合 ：

    协程发起非阻塞IO请求（如读取网络数据）。

    若数据未就绪，协程挂起，注册到epoll监听队列。

    epoll_wait监听到事件后，唤醒关联协程继续执行。

    Go的goroutine

    我知道比如 Go语言的goroutine 使用 GMP调度模型 ，对协程调度的一种工程化实践

    每个M（机器线程）绑定一个P（处理器），管理多个G（goroutine）。

    M：内核级线程 G：代表一个goroutine（本质上goroutine就是协程，但是完全运行在 用户态 ，） P：Processor， 处理器 ，用来为G提供必须的资源，管理和执行goroutine的。

    Go 的协程是 抢占式调度 （自 Go 1.14 后），在函数调用边界处插入 async preempt ，避免协程长时间不释放 CPU；

    切换时，调度器选择合适的G来执行，而无需进入内核态。

    **抢占式调度：**调度器使用监控线程（sysmon）检测长时间运行的goroutine并进行抢占。

    协程通过用户态调度机制，如事件驱动（epoll）+ 非阻塞IO，实现高并发低开销执行；调度无需进入内核态，除非真正发起阻塞系统调用；Go 的 GMP 模型就是对协程调度的一种工程化实践。

    线程：Python vs Java

    Python的线程 ：

    Python的多线程由于 全局解释器锁（GIL） 的存在， 不能实现真正的并行 。GIL 使得每次只有一个线程在执行 Python 字节码，即使在多核 CPU 上也是如此。

    适用于 I/O 密集型任务，但对于 CPU 密集型任务效果较差。

    Java的线程 ：

    Java 的线程可以利用多核 CPU 实现 真正的并行 ，通过操作系统的线程调度，Java 能够在多核环境中并行执行多个线程。

    适用于 CPU 密集型和 I/O 密集型任务。

    线程和进程区别

    调度方式

    进程切换 ：进程切换涉及 页表、内存等资源的重新加载 ，开销较大。

    线程切换 ：线程切换只需要切换 寄存器、栈等 ，开销比进程小， 更轻量级 。

    通信方式

    进程间通信（IPC） ：进程间通信需要 管道、消息队列、共享内存、信号量、Socket等 ，开销较大。

    线程间通信 ：线程共享进程的资源， 直接通过全局变量、堆等 共享数据，但需要加锁避免 竞争 。

    资源开销

    进程创建 ：创建进程需要分配独立的地址空间，消耗较大。

    线程创建 ：线程共享进程资源，不需要重新分配地址空间，创建和销毁更快。

    场景：实际开发用多线程还是多进程

    我会根据任务的类型来选择：

    IO 密集型任务（如爬虫、日志处理、Web 请求） ：优先选择 多线程或协程 ，因为大部分时间都在等待 IO，线程切换快更划算。

    CPU 密集型任务（如图片识别、加密压缩） ：优先使用 多进程 ，可以真正利用多核 CPU，并且避免 GIL 限制。

    进程五种状态

    新建（New） ：进程正在被创建（分配PCB，初始化资源）。

    就绪（Ready） ：已获得除CPU外的所有资源，等待调度。

    运行（Running） ：正在CPU上执行。

    阻塞（Blocked） ：等待事件（如I/O完成、信号量）。

    终止（Terminated） ：执行结束，资源待回收

    状态切换触发条件 ：
    切换路径 触发条件
    新建 → 就绪 初始化完成，加入就绪队列。
    就绪 → 运行 调度器选中（如时间片轮转、优先级抢占）。
    运行 → 就绪 时间片耗尽、更高优先级进程抢占。
    运行 → 阻塞 主动等待资源（如 read() 系统调用）。
    阻塞 → 就绪 等待的事件完成（如I/O数据到达）。
    运行 → 终止 进程执行 exit() 或被终止信号（如 SIGKILL ）杀死。

    通信方式

    进程间通信IPC

    进程有独立的地址空间，无法直接共享内存，需要操作系统提供显式的通信机制，就像两个公司之间要走正式流程。

    核心机制 ：

    管道 (Pipe) / 命名管道 (FIFO) ：单向数据流，一个写，一个读。

    消息队列 (Message Queue) ：消息链表，允许异步通信。

    共享内存 (Shared Memory) ： 最快的方式 。映射同一块物理内存到不同进程的地址空间，但需要配合信号量等机制来同步访问。

    信号 (Signal) ：用于通知异步事件，内容量小。

    Socket ：最通用的通信方式，可用于不同主机间的进程通信。

    线程间通信

    线程共享进程的资源（内存、文件等），因此通信就是直接读写这些共享数据。但最大的挑战是 并发安全 。

    核心机制 ： 通过共享内存进行通信 。

    自然共享 ：直接读写全局变量、堆内存。

    必须同步 ：必须使用 锁（Mutex）、信号量（Semaphore）、条件变量（Condition Variable） 等同步原语来保护共享数据，防止竞态条件。

    协程间通信

    协程在用户态执行，通常在单线程内切换，不存在真正的并行，因此没有数据竞争问题。

    核心机制 ：

    Channel (通道) ： Go语言的推荐做法 。像一个线程安全的队列，协程通过发送和接收来通信，实现了“通过通信来共享内存”的理念。

    Future/Promise ：一种异步编程模型，用于在协程间传递和获取异步操作的结果。

    直接共享变量 ：因为在一个线程内交替执行， 无需加锁 也可以安全地共享变量（但需注意可见性）

    调度

    进程线程调度

    1. 进程与线程的调度
    都由 操作系统内核 进行 抢占式调度 。

    调度者 ：操作系统内核。

    调度方式 ： 抢占式 。内核分配一个时间片，时间到了就强行剥夺CPU使用权，切换到下一个任务，不管当前任务是否愿意。

    切换代价 ： 高昂 。需要切换地址空间、内核栈、硬件上下文等，这称为 上下文切换（Context Switch） ，需要从用户态陷入内核态。

    调度算法 ：时间片轮转（RR）、多级反馈队列（MLFQ）等，追求公平性和吞吐量。

    协程调度

    运行在用户态 ，无需内核介入，减少上下文切换开销。

    非抢占式调度 ：协程显式调用 yield 或 await 让出执行权，调度器从就绪队列选取下一个。

    抢占式调度 ：Go语言通过Goroutine调度器在多个线程间分配协程。

    切换代价 ： 极低 。仅需保存和恢复 少量寄存器状态 （如程序计数器PC、栈指针SP）， 完全在用户态完成 ，不涉及内核态切换。

    事件驱动 ：基于Epoll/Kqueue等I/O多路复用，协程在I/O阻塞时挂起。

    遇到 I/O（通过 epoll / select /IOCP）→ 注册回调/等待事件 → 当前协程挂起、调度器切换执行其他协程 → I/O 完成后协程恢复

    多线程调度->多协程调度

    调度成本 ：从内核的 抢占式调度 变为用户态的 协作式调度 。

    线程调度是内核强制发生的（时间片用尽或更高优先级线程就绪），

    协程是主动让出（ yield ）控制权。

    效率 ：协程切换完全在用户态，无需陷入内核，代价更低。

    控制力 ：程序员对协程的调度有完全的控制权，可以实现更优化的调度策略。

    用户态调度（协作式） ：

    通常与 事件循环 结合。一个主循环（Event Loop）不断检查是否有事件就绪（如I/O完成、定时器到期）。

    当一个协程执行I/O操作时，它不会阻塞，而是 主动挂起 （yield），并将自己注册到事件循环中，同时让出CPU。

    事件循环发现该I/O操作完成时，就安排对应的协程 恢复执行 （resume）。

    关键点 ：如果一个协程不主动让出CPU（比如执行一个耗时计算），就会阻塞整个事件循环和其他所有协程。所以协程适用于I/O密集型，而非CPU密集型任务。

    调度算法

    进程调度/CPU调度

    进程调度的主要目标是 最大化CPU利用率，保证公平性，减少响应时间，提高吞吐量 ，同时满足不同任务的需求

    先进先出FIFO

    是最简单的， 非抢占式的 ，按到达顺序执行，执行完一个任务再执行下一个任务只有当任务结束后才会发生切换。

    但是可能会导致短作业等待时间长，比如一个长作业先到达，后面很多短作业需要等待，平均等待时间可能很高。

    短作业优先SJF

    优先调度耗时短的任务，长作业可能被饿死

    可以优化平均等待时间，但需要预知作业的运行时间，实际中难以实现。

    ==最大化系统的 吞吐量 （单位时间内完成的任务数）==，**短作业优先（SJF）**是理论上最好的选择。

    优先调度

    给每一个进程分配优先级，根据进程优先级来分配CPU，随着时间推移，增加等待进程的优先级

    主要问题 ： 饥饿 。低优先级的进程可能永远得不到执行。

    解决方案 ： 老化（Aging） 。这是解决饥饿问题的关键技术。系统会逐渐增加那些等待时间过长的进程的优先级，确保即使是最低优先级的进程，在等待足够长的时间后，其优先级也能升到足够高，从而获得CPU。

    时间片轮转法

    是每个进程分配一个时间片，时间片用完将此任务放到队列尾部就切换到下一个进程执行。

    能解决耗时长任务饥饿的问题，适用于分时系统，保证公平性，

    但时间片大小的选择很重要， 太小会导致频繁上下文切换 ，太大又可能退化成 先进先出 。

    多级反馈队列（现代操作系统Linux 和 Windows 使用的v综合调度算法）

    结合了多种策略，将进程分为多个队列，不同队列有不同的优先级和时间片。

    新进程进入高优先级队列，随着执行时间增加可能被移到低优先级队列。

    这种动态调整可以平衡响应时间和吞吐量，但实现相对复杂。

    实时调度算法

    如EDF和RMS，适用于有严格时间约束的任务。

    EDF选择截止时间最早的任务执行，

    RMS根据任务周期分配优先级，周期越短优先级越高。

    进程上下文切换

    进程切换过程中，内核会先保存当前进程的寄存器和执行状态，然后通过调度器选择一个新的进程。随后系统切换页表（地址空间）、TLB、内核栈，并恢复新进程的寄存器和程序计数器，最后跳回用户态继续执行。相比线程切换，进程切换还要切换虚拟内存空间，代价更大

    1.当前进程触发内核态进入（中断/系统调用）

    例如：时间片到 → 触发时钟中断 → CPU 执行中断处理程序

    此时 CPU 从用户态进入内核态，准备调度新进程

    2. 保存当前进程上下文 ：进程的寄存器、程序计数器、栈指针（被保存在内核栈上的 thread_struct ）

    3.调度新进程 ：调用调度器 schedule() 函数，根据调度策略（CFS、实时优先级等）选择下一个进程。

    4. 内核态切换与地址空间切换

    切换地址空间（虚拟内存）

    切换页表基址寄存器 CR3 ：加载新进程的页表基址到 CR3 寄存器（x86架构）。

    但是会导致TLB失效，后续内存访问需重新查询页表。

    切换内存管理数据结构 ：更新 mm_struct （管理进程虚拟内存区域）

    切换内核栈 ：当前进程的内核栈指针（ thread_info ）切换到新进程的内核栈。

    5. 恢复目标进程上下文 ：恢复 next 进程的寄存器、程序计数器、栈指针

    6. 从内核返回用户态，继续执行新进程

    上下文保存位置

    进程的上下文切换不仅包含了虚拟内存、栈、全局变量等用户空间的资源，还包括了内核堆栈、寄存器等内核空间的资源

    保存/恢复的上下文保存在 内核栈顶部的 thread_struct 结构体

    task_struct 是操作系统描述进程最核心的数据结构

    包括：进程状态、PID、调度信息、指向页表的指针、文件描述符等

    C++
    struct task_struct {
    pid_t pid; // 进程 ID
    struct mm_struct *mm; // 虚拟内存空间
    struct files_struct *files; // 打开的文件等资源
    struct thread_struct thread; // 子结构thread_struct：寄存器、栈指针、程序计数器等
    // ... 其他上下文信息
    };
    上下文类型 存储位置
    进程上下文 进程控制块（PCB，Linux中为 task_struct ），存储在内核空间。
    线程上下文 线程控制块（TCB，如 thread_struct 结构），位于线程内核栈底部（内核空间）。 TCB是管理线程的 数据结构 ，包含了 线程的状态、寄存器的值、堆栈信息 等。
    协程上下文 用户态栈或堆（如Golang的 g 结构体）

    进程切换 vs 线程切换

    进程切换 ：CPU 从一个进程的上下文切换到另一个进程，涉及 资源切换、内存空间切换 。保存和恢复 PCB（寄存器、程序计数器、内核栈、页表、文件描述符表）。

    线程切换 ：只切换寄存器、程序计数器和栈， 无需切换内存空间 。

    1. 资源切换范围

    进程切换 ：

    切换 虚拟内存空间（ mm_struct ） ，包括页表、TLB刷新。

    切换页表 （TLB失效） ⇒ 缓存命中率下降

    切换 内核资源 ：文件描述符、信号处理表、进程权限等。

    切换文件表、信号表 ⇒ 数据结构多

    切换 硬件上下文 ：寄存器、程序计数器、栈指针等。

    线程切换 ：

    仅切换 线程私有上下文（寄存器、栈指针、程序计数器） 。

    共享进程资源 ：地址空间、文件描述符、信号处理等无需切换。

    2. 调度单位

    进程切换 ：必须通过 内核态 完成（涉及地址空间和资源管理）。

    线程切换 ：

    内核级线程 ：需进入内核态，但资源切换较少。

    用户级线程 ：完全在用户态切换（如协程），无需内核介入。

    3.示例 ：

    进程切换：浏览器切换到视频播放器（不同进程，内存隔离）。

    线程切换：Web服务器处理多个HTTP请求（同一进程内线程切换）

    为什么进程切换慢？

    页表切换（CR3寄存器）

    页表（Page Table） ：每个进程有独立的页表，负责将 虚拟地址 映射到 物理地址 。

    每个进程有独立地址空间 → 切换时必须换页表（即切换 CR3 ）

    页表切换意味着 CPU 的页表缓存（TLB）失效 → TLB Flush

    TLB Flush

    TLB是页表的 高速缓存 ，作用加速地址转换。

    进程切换时切换地址空间 → TLB 无效 → 下次内存访问必须重新查页表 → 性能下降

    CPU 缓存命中率降低

    新进程的内存访问可能与前一个进程完全不同 → 导致 CPU 缓存（L1/L2/L3）中旧进程的数据被覆盖，L1/L2 缓存命中率下降

    示例 ：

    进程 A 正在处理数组计算，其数据缓存在 CPU 中。

    切换到进程 B（处理文件 I/O）后，进程 B 的数据覆盖缓存，进程 A 重新执行时需重新加载数据

    资源状态保存复杂

    进程涉及更多资源状态（文件描述符、信号、内存映射）→ 保存/恢复更复杂

    线程切换

    线程切换的步骤可分为 用户态触发 → 内核态调度 → 保存上下文 → 切换内核栈 → 恢复上下文 → 用户态运行新线程”

    线程切换的触发->线程陷入内核态，进入调度过程

    主动让出 ：如调用 pthread_yield() 或 sched_yield() 等系统调用

    被抢占 ：如时间片耗尽触发时钟中断，调度器决定当前线程不再运行

    内核态调度与上下文切换

    保存当前线程上下文（当前线程 → thread_struct ）

    CPU寄存器、栈指针、程序计数器存入 当前线程的内核栈的 thread_struct 结构 。

    切换调度器（调用 schedule() ）

    操作系统将执行权切换到调度器

    调度器负责选择下一个要执行的线程，并根据调度算法做出决策。

    切换内核栈 ：调度器根据新线程的 task_struct 找到其内核栈， 将栈指针切换到目标线程的内核栈

    恢复新线程上下文（新线程 ← thread_struct ）

    从目标线程的 thread_struct 恢复 寄存器、栈指针、程序计数器 。

    3. 跳转回用户态，执行新线程

    协程切换🟢

    运行在用户态 ，无须陷入内核， 切换开销极小

    上下文保存位置 ：用户栈或堆内存。

    切换触发 ：由开发者显式控制（通过 yield 、 await 、 resume 、 co_switch() 等）或I/O事件驱动

    调度策略 ：

    协作式调度 ：协程显式调用 yield 或 await 让出执行权，调度器从就绪队列选取下一个。

    抢占式调度 ：调度器通过信号（如Golang的监控线程）中断运行协程。

    I/O阻塞？ ：协程发起非阻塞I/O操作，注册回调后主动切换。

    协程由用户程序控制任务的挂起与恢复，通常不涉及内核， 仅在用户态完成 ，切换过程只涉及 用户态上下文（栈和寄存器）的保存与恢复，从调度策略上看，协程多为非抢占式调度 ，调度主动权掌握在协程自身， 调度器 仅负责管理生命周期和 切换逻辑 。

    相比传统多线程模型，协程通过 用户态调度器 实现轻量切换和非阻塞并发，省去了内核态切换成本，尤其 适合 I/O 密集型场景 。

    我知道比如 Go语言的goroutine 使用 GMP调度模型

    每个M（机器线程）绑定一个P（处理器），管理多个G（goroutine）。

    M：内核级线程 G：代表一个goroutine（本质上goroutine就是协程，但是完全运行在 用户态 ，） P：Processor， 处理器 ，用来为G提供必须的资源，管理和执行goroutine的。

    Go 的协程是 抢占式调度 （自 Go 1.14 后），在函数调用边界处插入 async preempt ，避免协程长时间不释放 CPU；

    切换时，调度器选择合适的G来执行，而无需进入内核态。

    **抢占式调度：**调度器使用监控线程（sysmon）检测长时间运行的goroutine并进行抢占。

    进程复制

    fork()创建新进程

    fork() 是 Unix/Linux 系统中用于 创建新进程 的 系统调用 。调用一次，返回两次（在父进程和子进程中各返回一次）。其核心是 复制父进程 。

    它的作用是：

    复制当前进程，创建一个几乎一模一样的子进程（child process）* ，这个子进程会拥有与父进程 相同的代码段、数据段、堆、栈、打开的文件描述符等资源* 。

    fork过程

    调用 fork() ：父进程通过系统调用 fork() 请求操作系统创建子进程。

    分配资源+复制父进程 ：操作系统为子进程 分配新的进程控制块（PCB）、唯一的进程 ID（PID） ，并复制父进程的 内存（代码、数据、堆栈等） 、打开的文件描述符、信号处理等上下文信息。

    写时复制（Copy-On-Write, COW）优化 ：

    延迟物理内存复制 ：现代系统不会立即复制父进程的内存，而是让父子进程共享 同一物理内存 。

    写操作触发复制 ：当任一进程尝试修改内存时，内核会为修改的页面（Page）创建独立副本，确保进程间隔离。

    📌 fork() 的返回值很关键（可区分父子）：

    在 父进程 中， fork() 返回的是子进程的 PID（一个大于 0 的整数）；

    在 子进程 中， fork() 返回的是 0；

    如果创建失败，返回 -1（比如系统资源不足）

    总结 ： fork() 的本质是“复制自己”。通过写时复制技术，它变得非常高效。调用后，系统里出现两个几乎完全相同的进程，它们从 fork() 调用后的下一条指令继续执行，唯一的区别是 fork() 的返回值。

    fork() 复制：写时复制COW

    虽然叫“复制”，操作系统为了效率不会真的一下子复制所有内存数据，

    操作系统使用了 写时复制机制（Copy-On-Write, COW）节省资源 ：

    父子进程最初 共享同一份物理内存 ；

    只有当 某一方尝试修改内存数据时 ，操作系统才会为 该页分配新内存 并进行复制；

    这样可以 极大节省资源 ，特别是在很多场景下，子进程会直接执行 exec() 来加载新程序，这样原本的复制根本用不上。

    fork()、vfork()、clone() 区别

    1️⃣ fork()

    创建一个子进程，拥有 独立的虚拟地址空间（通过 COW 实现） ；

    安全、稳定，是最常用的进程创建方式；

    子进程可以执行独立逻辑或使用 exec() 执行新程序。

    2️⃣ vfork()

    是 fork() 的性能优化版本；

    子进程与父进程共享地址空间，父进程挂起，直到子进程调用 exec() 或 _exit() 退出 ；

    更高效，但有风险 （子进程可能修改父进程的数据）所以仅限用于马上 exec() 的场景。

    使用场景：创建子进程并立即加载新程序时（比如 shell 中运行命令）。

    3️⃣ clone()

    比 fork() 更灵活 ，可以控制 哪些资源共享（如内存、文件描述符） 。

    可以创建线程 （ pthread_create() 内部使用 clone() ）。

    适用于 轻量级进程和容器（如 Docker） 。

    通信机制🟢

    进程间通信方式（IPC）

    进程间通信（IPC）是 指在 不同进程之间传递数据和信号 的机制

    面试表述模板

    “进程间通信主要解决的是独立地址空间之间的数据共享或同步问题。常见的方式有共享内存、消息队列、管道和 socket。其中共享内存速度最快，但需要加锁，适用于高性能场景；消息队列和 socket 更适合结构化或远程通信。

    操作系统提供了多种进程间通信机制，主要根据通信的范围（是否跨主机）、是否需要同步、传输数据量等场景选择：

    如果是本地父子进程通信，我倾向于用匿名管道（Pipe）；

    如果是多个不相关进程，我可以用命名管道或者消息队列；

    对于大数据量共享，比如多个进程处理共享缓存，效率最高的是 共享内存 ，不过需要加锁，

    1. 管道（Pipe）

    定义 ： 管道 是一种最简单的 IPC 方式，主要用于 父子进程之间 的通信。管道是 单向的

    单向通信 ，数据从一端写入，从另一端读取。

    进程间无格式的字节流通信 。

    仅适用于父子进程 ，因为管道依赖于进程创建时的文件描述符。

    数据先进先出（FIFO） ，不支持文件定位操作（ lseek ）。

    管道2种方式

    匿名管道：是一种在 父子进程或者兄弟进程 之间进行通信的机制，只能用于具有亲缘关系的进程间通信

    通常通过pipe系统调用创建，随进程的创建而建立，进程结束，管道也随之销毁。

    命名管道：是一种 允许无关的进程间 进行通信的机制，基于文件系统，可以在不相关的进程之间进行通信。

    ** 独立于进程**。即使创建它的进程结束了，只要不手动删除这个文件，它就一直存在。

    2. 消息队列

    消息队列 克服了管道通信的数据是无格式的字节流的问题，一种基于 消息链表 的通信方式，进程可以向队列中 发送和读取 结构化的数据。

    性能差： 每次数据的写入和读取都需要经过用户态与内核态之间的拷贝过程。

    **3. 共享内存mmap【最快】 **

    原理：文件或匿名页映射到进程虚拟地址空间；缺页访问触发内核映射物理页；多个进程可共享同一物理页。 优点：零拷贝、进程间高速通信、大文件处理高效

    共享内存 是 最快 的 IPC 方式，为数据直接映射到虚拟地址空间， 每个进程都可以直接访问 ， 无需拷贝 。

    可以解决消息队列通信中 用户态与内核态之间数据拷贝过程带来的开销

    4. 信号量（Semaphore）

    信号量不仅可以实现访问的互斥性，还可以实现进程间的同步，

    信号量其实是一个计数器，表示的是资源个数，其值可以通过两个原子操作来控制，分别是 P 操作和 V 操作 。

    5. 信号

    信号是 异步通信机制 ，信号可以在应用 进程和内核 之间直接交互，

    信号事件的来源主要有硬件来源（如键盘 Cltr+C ）和软件来源（如 kill 命令）

    一旦有信号发生， 进程有三种方式响应信号 1. 执行默认操作、2. 捕捉信号、3. 忽略信号 。有两个信号是应用进程无法捕捉和忽略的，即 SIGKILL 和 SIGSTOP，这是为了方便我们能在任何时候结束或停止某个进程。

    6. 套接字（Socket）

    Socket（套接字）是一种通用 的 IPC 方式，不仅支持本机进程通信，还支持 不同主机间的进程通信 （如 TCP/IP 网络通信）。

    本地进程通信（Unix Domain Socket）

    适用于同一台机器上的进程通信，使用 AF_UNIX 地址族。

    比 TCP/UDP 更快 ，因为不经过网络协议栈。

    网络通信（TCP/UDP Socket）

    基于 TCP 协议的通信方式， ：可靠的双向通信，适用于 Web 服务器。

    基于 UDP 协议的通信方式 ：无连接，速度快，适用于音视频流。

    线程通信

    由于线程共享同一个进程地址空间，所以通信方式主要基于 共享内存 + 同步机制 ：

    共享内存通信 ：所有线程共享全局变量、堆内存；一个线程写入变量，另一个线程读取

    但由于 多个线程同时访问数据 可能会引发竞争问题，因此需要 同步机制 来保证数据一致性。

    Linux系统提供了五种用于线程通信的方式： 互斥锁、读写锁、条件变量、自旋锁和信号量 。

    1.互斥锁

    定义 ：互斥锁是一种 独占锁 ，用于防止多个线程同时访问 共享资源 。只有 一个线程 可以持有互斥锁，其他线程必须等待锁的释放。

    特点 ：

    互斥性 ：同一时刻只有一个线程可以持有互斥锁。

    阻塞 ：如果一个线程尝试获取一个已被其他线程持有的锁，则它会被阻塞，直到锁被释放。

    公平性 ：多个线程等待同一个互斥锁时，操作系统调度决定哪个线程先获得锁（可能是 FIFO 方式）。

    适用场景 ：多个线程需要修改共享变量，如 银行账户转账 。

    优点 ：操作系统提供了 内核级别 的支持，确保线程同步。

    上下文切换开销 ：如果多个线程等待锁，会导致线程切换，影响性能。

    可能导致死锁 ：如果多个线程交叉持有锁并相互等待，可能发生 死锁 （Deadlock）。

    2. 读写锁

    定义 ：读写锁是一种 改进的互斥锁 ，适用于 读多写少 的场景。由 读锁（Read Lock） 和 写锁（Write Lock） 组成：

    读锁 （ 读锁是共享的 ）：多个线程可以同时获取读锁，只要没有线程持有写锁。

    写锁 （ 写锁是独占的 ）：同一时刻只能有一个线程持有写锁，且持有写锁时，其他线程无法获取读锁或写锁。

    3. 自旋锁

    作用 ：当一个线程获取不到锁时，不会阻塞，而是 不断循环检查锁的状态 。

    实现方式 ：自旋锁通过 CPU 提供的 CAS 函数 （ Compare And Swap ），在**「用户态」完成加锁和解锁**操作， 不会主动产生线程上下文切换

    一般加锁的过程，包含两个步骤：

    第一步，查看锁的状态，发生多线程竞争锁的情况， 加锁失败的线程会「忙等待」 ，直到它拿到锁

    确认锁是空闲的第二步，将锁设置为当前线程持有；

    CAS 函数就把查看是否上锁然后加锁合并成一条硬件级指令，形成 原子指令 ，这样就保证了这两个步骤是不可分割的。

    「忙等待」可以用用 CPU 提供的 PAUSE 指令 来实现「忙等待」

    适用场景 ：适合 短时间锁竞争激烈 的情况，如操作系统内核同步。

    缺点 ：长时间自旋会浪费CPU资源，不适用于锁竞争严重的情况。

    4. 条件变量

    定义 ：条件变量是一种 线程同步机制 ，用于 线程间的等待和唤醒 。它允许线程在某个条件不满足时 等待 ，直到另一个线程 发出信号 通知它条件满足，从而减少忙等待，提高性能。

    特点 ： 结合互斥锁 使用，可以让线程在满足条件前 释放锁并等待 ，提高效率。

    等待条件成立（pthread_cond_wait）

    线程调用 pthread_cond_wait 进入 阻塞状态 ，直到其他线程发出信号。

    注意 ：调用 pthread_cond_wait 之前必须先 加锁 互斥锁，否则可能会出现竞争条件。

    通知等待线程

    pthread_cond_signal ： 唤醒一个等待的线程 （如果有多个线程等待，只唤醒一个）。

    pthread_cond_broadcast ： 唤醒所有等待的线程 。

    5. 信号量

    信号量 是一种 同步机制 ，用于 控制多个线程对共享资源的访问 。

    信号量通常用于 计数资源 ，可以限制 同时访问某个资源的线程数量 ，适用于 生产者-消费者模型 等场景。

    信号量的操作主要有两个：

    P 操作（wait 或 down 操作）用于申请资源 。

    sem-- ，当 sem \< 0 ，线程进入 阻塞等待 。

    V 操作（signal 或 up 操作）用于释放资源 。

    sem++ ，当 sem \<= 0 ，唤醒一个等待中的线程。

    信号量的修改是 原子操作 ，不会被线程切换中断，保证线程安全。

    线程通信常见问题

    竞态条件 ：多个线程并发访问共享变量，执行顺序不确定，结果不一致；

    死锁 ：多个线程互相等待对方释放资源；

    虚假唤醒 ：条件变量唤醒后不一定条件满足，所以必须加判断条件；

    内存可见性 ：一个线程写的数据，另一个线程不一定能立即读到（需内存屏障/同步机制）

    内存管理

    操作系统内存管理

    操作系统主要采用 虚拟内存机制 ，将虚拟地址空间与物理内存进行映射， 每个进程可以独享一个完整、独立的地址空间 ，增强安全性和扩展性。

    物理内存 ：就是我们实际机器上的内存条，容量有限，例如 8GB、16GB。

    虚拟内存 ：是操作系统为每个进程提供的 逻辑地址空间 ，通常比实际内存大。例如，64 位系统的进程可拥有高达 2^48 的地址空间。虚拟内存通过将程序的地址空间划分成若干个固定大小的页或段，并将这些页或者段映射到物理内存中的不同位置，从而使得程序在运行时可以更高效地利用物理内存。

    虚拟地址

    虚拟地址是操作系统内存管理的基石，它通过MMU将 进程使用的虚拟地址映射到物理内存的实际物理地址 。其核心好处如下：

    内存保护与安全

    每个进程拥有独立的虚拟地址空间。进程A无法直接访问进程B的地址空间，因为它的虚拟地址会被MMU映射到不同的物理页面。这防止了恶意或错误的程序破坏其他进程或内核的数据。

    进程内存隔离与简化编程

    对于每个进程来说，它都“独占”整个内存空间（如在32位系统上，每个进程都认为自己拥有0-4GB的连续内存）。程序员编译程序时无需关心物理内存的实际布局，链接器和加载器使用统一的虚拟地址，极大简化了程序开发。

    更高的内存利用率：允许运行比物理内存更大的程序

    通过 交换技术 ，操作系统可以将暂时不用的内存页（如代码页、数据页）写入磁盘（交换区），从而释放物理内存给急需的进程使用。这使得系统可以运行总内存需求远超物理内存的程序。

    简化内存管理：解决碎片化问题

    物理内存 会因为频繁的分配和释放产生外部碎片，导致虽然有足够的总空闲内存，但无法分配一块大的连续空间。

    虚拟内存 使得进程只需要获得 连续的虚拟地址空间 即可，操作系统可以将其映射到 物理上不连续的页框 中。这完美地解决了外部碎片问题。

    管理内存——分页

    Linux 是通过对内存分页的方式来管理内存的。 分页的思想是把整个虚拟地址空间和物理地址空间，切分为一段段固定大小的内存块 ，这种固定大小的内存单位我们称为 页（Page） 。在大多数 64 位 Linux 系统下，每一页的大小是 4KB 。

    分页的最大优势是可以简化内存管理并降低碎片，同时使得虚拟地址空间的使用变得灵活。具体地：

    虚拟地址空间是连续的

    物理地址空间可以是不连续的

    这中间的转换过程由 页表 完成。

    页表

    页表就是一个映射表，将 虚拟页号映射到物理页框号 （PFN）。查页表后得到 物理页框号（PFN） ，再加上 offset 得到 最终的物理地址 。

    虚拟内存采用分页机制，虚拟地址被拆分为两部分：

    高位： 虚拟页号（VPN） ，用来查页表；

    低位： 页内偏移（Offset） ，保留原始页内的位置；

    为了加速地址转换过程，Linux 使用以下机制：

    TLB

    由于查页表是一个内存访问操作，CPU 内部引入了 TLB（快表）来 缓存 常用页表项 用于加速地址转换。

    如果 TLB 中命中就可以快速完成地址转换，没命中则访问页表。但是页表修改后需要刷新 TLB（如上下文切换）。

    多级页表

    如果每个页表都很大，会造成内存浪费。为了解决这个问题，现代操作系统（如 Linux x86-64）采用 四级页表结构（PGD → PUD → PMD → PTE） ，可以做到按需分配、节省空间。每一级都进一步细化空间，只在需要的时候分配，节省内存

    段表

    另一种内存管理方式是 分段 （Segmentation）：

    程序划分为多个段，如代码段、数据段、栈段；

    每个段有自己的 基址（Base）和限长（Limit） ；

    虚拟地址 = 段号 + 段内偏移。

    段表适合逻辑划分明确的程序结构，但不适合大规模内存管理，现代系统多用分页，段机制常用于实现权限隔离和特权保护。

    堆 vs 栈

    分配方式 ：

    堆是动态分配内存，由程序员手动申请和释放内存手动分配（ malloc/new ），通常用于存储动态数据结构和对象。

    栈是静态分配内存，由编译器自动分配和释放内存，用于存储函数的局部变量和函数调用信息。

    内存管理 ：

    堆需要程序员手动管理内存的分配和释放，如果管理不当可能会导致内存泄漏或内存溢出。

    栈由编译器自动管理内存，遵循后进先出的原则，变量的生命周期由其作用域决定，函数调用时分配内存，函数返回时释放内存。

    大小和速度 ：

    堆通常比栈大，内存空间较大，动态分配和释放内存需要时间开销。

    栈大小有限，通常比较小，内存分配和释放速度较快，因为是编译器自动管理。

    malloc()

    malloc() 不是系统调用 ，而是 C 库里的函数，用于动态分配内存 。

    malloc() 源码里默认定义了一个阈值：

    如果用户分配的内存小于 128 KB，通过 brk() 系统调用从堆分配内存

    小块内存（如 1KB）通常从堆中分配，内部通过 brk() 系统调用向上扩展堆顶；

    如果用户分配的内存大于 128 KB， 通过 mmap() 系统调用在文件映射区域分配内存

    glibc 会通过 mmap() 映射匿名页，不使用堆，便于回收

    操作系统内存不足处理机制

    申请虚拟内存→访问时触发缺页中断→检查空闲内存→无则回收内存（后台→直接）→仍不足则OOM Killer。

    内存不足时，操作系统通过缺页中断触发内存分配，依次尝试后台回收、直接回收

    回收策略针对 文件页和匿名页 分别处理，依赖 LRU算法 选择决定了哪些页会被换出。

    调优需结合监控数据，平衡性能与资源使用，避免频繁回收或OOM事件。

    如果物理内存和 swap 都满了，Linux 会触发 OOM Killer 杀掉内存占用大的进程。

    内存申请与缺页中断

    虚拟内存申请 ： malloc 等函数分配的是虚拟内存，此时物理内存尚未分配。

    当程序真正访问这块虚拟内存时，CPU会发现这个虚拟地址没有对应的物理内存映射，于是触发缺页中断（Page Fault）。这时候，进程会从用户态切换到内核态，由操作系统的缺页中断处理函数来处理这个问题。

    首次访问触发缺页中断 ：当程序读写虚拟内存时，若该地址未映射到物理内存，CPU触发 缺页中断 ，进程会 从用户态切换到内核态

    由操作系统的 缺页中断处理函数 来处理 缺页（Page Fault） ：

    若有空闲物理内存，直接分配并建立虚拟内存与物理内存之间的映射关系。

    若无空闲内存，进入内存回收流程。

    内存回收机制

    如果没有空闲的物理内存，那么内核就会开始进行 回收内存 的工作，回收的方式主要是两种：直接内存回收和后台内存回收。

    后台内存回收 （kswapd）：在物理内存紧张的时候，会唤醒 kswapd 内核线程来回收内存，这个回收内存的过程 异步 的，不会阻塞进程的执行。

    直接内存回收 （direct reclaim）：如果后台异步回收跟不上进程内存申请的速度，就会开始直接回收，这个回收内存的过程是 同步 的，会阻塞进程的执行。

    可回收内存类型

    1.文件页

    文件页是指通过文件映射（如 mmap ）、磁盘读写缓存产生的内存页，具有磁盘上的物理载体因此更容易回收

    来源 ：文件系统缓存（如 Buffer/Cache ）和内存映射文件（ mmap ）。

    回收方式 ：

    干净页：没有被修改过，可以 直接释放**，未来访问时再从磁盘加载；

    脏页 ：已被修改但尚未同步到磁盘， 需要先写回磁盘 ，才能释放对应内存；

    优化 ：通过 sync 命令或 fsync 系统调用主动刷脏页。

    2.匿名页

    匿名页是指那些 没有文件映射关系的内存页 ，

    来源 ：堆、栈、共享内存等无文件后备的数据。

    回收方式 ： 通过 Linux 的 Swap 机制 换出到磁盘（交换分区或文件）。

    换出（page-out） ：Swap 会把不常访问的内存先写到磁盘中，然后释放这些内存

    换入（page-in） ：如果被访问了再重新从磁盘读入内存 ，性能会受到很大影响（因为磁盘慢）。

    回收策略 LRU 算法

    回收策略针对 文件页和匿名页 分别处理，依赖 LRU算法 选择决定了哪些页会被换出，也就是优先回收不常访问的内存。

    LRU 回收算法，实际上维护着 active 和 inactive 两个双向链表，其中：

    active_list 活跃内存页链表，这里存放的是最近被访问过（活跃）的内存页；

    inactive_list 不活跃内存页链表，这里存放的是很少被访问（非活跃）的内存页；

    越接近链表尾部，就表示内存页越不常访问。这样，在回收内存时，系统就可以根据活跃程度，优先回收不活跃的内存。

    OOM Killer机制

    当内存回收仍无法满足需求时（物理内存和 swap 都满了），触发 OOM（Out of Memory）Killer 杀掉内存占用大的进程：

    选择策略 ：基于 oom_score （综合内存占用量、进程优先级、运行时间等）。

    Plaintext
    # 查看进程oom_score
    cat /proc/<pid>/oom_score

    终止进程 ：杀死高得分进程释放内存，可能多次触发直到内存足够。

    日志记录 ：通过 dmesg 可查看OOM事件详情

    常见页面置换算法

    页面置换算法的功能是， 当出现缺页异常，需调入新页面而内存已满时，选择被置换的物理页面 ，也就是说选择一个物理页面换出到磁盘，然后把需要访问的页面换入到物理页。
    算法 原理描述 优缺点
    FIFO 最先进入的页面最先淘汰 简单但可能误杀热点页
    LRU 最近最久未使用的页淘汰（理论最优近似） 性能好，需维护时间戳
    Clock 环形指针+访问位，近似 LRU 实现 高效简化
    NRU Not Recently Used，按访问/修改位分类淘汰 合理但复杂
    LFU 最少使用次数淘汰 可被频繁突增页面干扰
    Random 随机淘汰 简单，但性能波动大

    高性能网络编程

    I/O模型
    模型 核心机制 典型实现 适用场景
    阻塞 I/O 调用线程阻塞等待数据就绪 read() , recv() 简单客户端、低并发
    非阻塞 I/O 轮询检查数据是否就绪，避免阻塞 fcntl(O_NONBLOCK) 需低延迟响应的轻量级服务
    I/O 多路复用 单线程监听多个 I/O 事件，统一处理就绪的 I/O select() , poll() , epoll() 高并发服务（Web 服务器、代理）
    信号驱动 I/O 内核通过信号通知进程数据就绪 SIGIO 信号 实时性要求高的场景（如 UDP 流）
    异步 I/O 内核完成 I/O 操作后主动通知应用，全程无阻塞 Linux io_uring , Windows IOCP 超高并发、低延迟（数据库、存储）

    1. 阻塞 I/O

    应用程序发起I/O操作后会被阻塞，直到操作完成才返回结果

    流程 ：

    线程调用 recv() 等待数据到达内核缓冲区。

    数据到达后，内核复制数据到用户空间，线程解除阻塞。

    每个连接一个线程，这样当有很多连接的时候，线程数会很高，导致资源消耗大，效率低下

    2. 非阻塞 I/O

    应用程序发起I/O操作后立即返回，不会被阻塞，

    但需要不断轮询或者使用select/poll/epoll等系统调用来检查I/O操作是否完成。

    适合 短时请求 ，如轻量级应用。 轮询（CPU 资源浪费）成本可接受 的应用

    3. I/O 复用

    核心思想 ：单线程通过一个 系统调用 监听 多个 I/O 事件 ，仅处理就绪的 I/O。

    实现方式 ：使用 select/poll / epoll 等待多个 I/O 事件，当任何一个 I/O 事件就绪进程会收到通知，然后进行 read() 。

    select ：线性扫描所有 fd，支持数量有限（1024）。

    poll ：链表存储 fd，无数量限制，但性能随 fd 数增长下降。

    epoll ：事件驱动，仅返回就绪的 fd，性能最优。

    4. 信号驱动 I/O

    应用程序发起I/O操作后，可以继续做其他事情，

    当I/O操作完成时，操作系统会向应用程序发送信号来通知其完成。

    适用场景 ：适用于 异步通知机制 （如 Linux 服务器进程）。

    5. 异步 I/O

    应用程序发起I/O操作后可以立即做其他事情，当I/O操作完成时，应用程序会得到通知。

    异步I/O模型由 操作系统内核 完成I/O操作，应用程序只需等待通知即可。

    适用场景 ： 高并发 I/O 服务器 （如数据库、文件存储）。

    I/O 多路复用

    I/O 多路复用 是指通过一个线程（或进程） 同时监听多个 I/O 事件 （如 socket 连接、文件读写等），一旦有 socket 可读/写，统一处理。避免为每个 I/O 操作创建独立线程的开销，用于 处理大量并发连接的场景

    核心机制 ：通过内核提供的系统调用（如 select , poll , epoll ） 批量监听多个 FD 的状态 ，当某个 FD 就绪（可读/可写）时，通知程序进行处理。

    SELECT

    原理 ：select每次调用都需要把fd集合 从用户态拷贝到内核态 ，而且遍历所有fd来检查状态，再由内核返回产生了事件的连接，然后在用户态中再处理这些连接对应的请求。

    特点：

    fd文件描述符数量限制

    select 采用 fd_set bitmap结构 来存储文件描述符，每个 bit 代表一个文件描述符是否被监听。

    fd_set 是 固定大小的数组 ，最大 1024，所以 select 最多能监控 1024 个文件描述符

    **性能：**每次调用时， select 都要遍历整个文件描述符集，因此随着连接数的增加，性能会显著下降，O(n) 的时间复杂度。

    POLL

    原理 ： poll 和 select 的工作原理类似，都是通过轮询fd来检查哪些fd有事件发生,但 poll 没有文件描述符数量的限制

    特点：

    采用 链表 结构，解决了 select 1024 个 fd 限制 问题。

    poll 使用 struct pollfd 来存储文件描述符的信息。

    但仍然存在频繁用户态和内核态拷贝性能开销较大，仍需要遍历所有 FD 判断就绪，0(n)的轮询时间复杂度。

    EPOLL

    epoll是 Linux 提供的一种高性能 I/O 多路复用机制。

    它使用事件通知机制， 当fd就绪时通过回调函数通知程序 ，不需要遍历所有fd。

    Epoll是为了解决传统 select / poll 的性能瓶颈。 select/poll 每次调用都需要遍历所有 FD，并将 FD 集合从用户态拷贝到内核态，导致开销为 O(n)。在连接数大的场景下，性能会明显下降。

    epoll ：基于 epoll_ctl 维护事件列表，事件驱动（O(1)）

    数据结构

    红黑树 ：内核用红黑树存储所有监听的fd（ epoll_ctl 操作）

    增删改查fd效率 O(log n) ，避免 select / poll 的 O(N) 遍历开销。

    就绪链表 ：当某个 fd 发生 I/O 事件时，内核将其从 红黑树取出加入 就绪链表 ， epoll_wait 仅需检查该链表。

    epoll_wait() 只需扫描 就绪链表 ，避免 poll 需要每次遍历所有 fd

    事件就绪检查：O(1)（仅遍历就绪链表）

    底层原理

    事件触发模式 ：只有当某个 FD 真正准备好了才会通知不会每次都全部扫一遍

    水平触发（LT） ：只要描述符处于就绪状态，每次 epoll_wait 都会通知。

    边缘触发（ET） ：仅在状态变化时通知一次，需一次处理完所有数据，效率更高

    Epoll 提供三个系统调用 ：

    epoll_create 创建 epoll 实例

    epoll_ctl 注册、修改、删除监听的文件描述符（FD）

    epoll_wait 阻塞等待内核返回“就绪的 FD 列表”

    Epoll 流程

    ** epoll_create 创建 epoll 实例：**创建 eventpoll 结构体，内含 红黑树、就绪链表 等数据结构。

    epoll_ctl 添加监听的 FD 到 epoll 的红黑树

    文件描述符（fd）被插入到 epoll 的红黑树 中（便于快速查找和管理）。

    同时给 fd 绑定一个回调函数 ，当 fd 发生 I/O 事件时，内核会自动触发 回调函数 ，将该 fd 放入 就绪链表

    内核监听这些 FD 的状态变化

    epoll_wait() 调用时 内核把就绪链表里的 FD 拷贝到 用户态 （无需遍历所有 FD）,返回这些已就绪的 FD 给你处理

    Epoll优势

    事件驱动，O(1) 复杂度

    epoll_ctl() 注册文件描述符（fd）时 ，为每个 fd 绑定 回调函数 。

    epoll_wait() 仅遍历就绪的 fd ，避免 select / poll 的 O(N) 轮询 ，使其时间复杂度降至 O(1) 。

    避免频繁拷贝，减少系统调用

    epoll_ctl() 只在监听 fd 时传递一次 ，而 epoll_wait() 无需反复传递 fd 集合 。

    基于 红黑树 + 双向链表 存储结构

    红黑树（RB-Tree） 存储所有监听的 fd ，支持 高效增删改查（O(logN)） ，避免 poll 的 线性查找 。

    双向链表（Ready List） 存储就绪 fd ，避免 poll 需要遍历整个 fd 集合。

    最大连接数不受限制 （不像 select 存在 FD_SETSIZE = 1024 限制）。

    使用内核事件通知机制 + 共享内存

    epoll 采用事件通知机制 ，即 只有事件触发时才通知用户进程 ，避免 select/poll 反复轮询 fd 集合的低效方式。

    通过 内核和用户空间的共享内存（mmap + epoll 事件队列） ，用户态可以 直接访问就绪事件列表 ，避免内核态拷贝到用户态的额外开销，提高性能。

    epoll个人理解

    先创建一个大的结构体，结构体里面主要有一个双向链表，一颗红黑树，一个等待队列。

    然后将不同socket连接返回的fd以及eventpoll的指针以及等待队列的指针组装成一个红黑树节点，将其插入到红黑树种。

    当某个socket对应的tcp链接有数据来了，就由这个链接对应的fd在红黑树中进行查找，找到这个链接对应的节点。将这个节点拷贝到双向链表中。

    然后就是epoll-wait监听到双向链表中有数据，就去将链表中的节点数据拷贝到用户空间，同时从节点中拿到对应休眠进程的信息，去唤醒这个队列。

    这个进程重新占用cpu，从拷贝过来的节点中拿到文件描述符，通过这个文件描述符读取对应的读缓冲区。从而拿到接受到的数据。

    DMA技术

    传统I/O过程：

    CPU发指令给磁盘控制器

    磁盘控制器准备数据并讲数据放入磁盘控制器內部缓冲区，产生一个中断信号

    CPU讲数据读进自己寄存器，随后把寄存器数据写入内存，在数据传输过程中CPU无法执行其他任务

    存在问题： 大量读取太浪费CPU的时间

    DMA （直接访问内存） 放在磁盘和CPU中间，数据搬运的工作DMA来做。

    CPU将IO请求发送给DMA，自己该干嘛干嘛

    DMA将请求发给磁盘

    磁盘控制器将数据读入自身内部缓冲区向DMA产生一个中断信号

    DMA将磁盘控制器中的数据拷贝到内核缓冲区

    DMA读取数据结束之后就发中断信号给CPU

    CPU将数据从内核拷贝到用户空间。

    如果服务端要提供文件传输的功能，我们需要将磁盘上的文件读取出来，然后通过网络协议发送给客户端。 四次用户态和内核态的切换，四次数据拷贝。

    DMA将磁盘上的数据拷贝到内核缓冲区

    CPU将内核缓冲区数据拷贝到用户缓冲区

    CPU将用户区的数据拷贝到Socket发送缓冲区

    DMA将socket缓冲区中的数据拷贝到网卡缓冲区里

    这个过程中 2，3是没有必要的，因为用户空间是不会对数据进行加工的。

    零拷贝（Zero-copy）技术：

    send_file 省第三步，两次切换
