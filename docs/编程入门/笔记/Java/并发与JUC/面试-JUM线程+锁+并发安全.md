**1.进程**

**进程 vs 线程 vs协程🟢**

**多进程**

每个进程都有独立的内存空间，因此进程间的通信成本较高，但稳定性较好，一个进程崩溃不会影响其他进程。

创建和销毁进程开销大，因为涉及内存映射、页表建立、内核数据结构分配等。

适合CPU密集型任务，因为每个进程可以运行在不同的CPU核心上，充分利用多核资源。

**进程上下文切换** ：进程切换由操作系统内核完成，需保存和恢复整个上下文（包括寄存器、页表、打开文件等）

由于每个进程都有独立的虚拟内存空间，切换时需要更新内存管理单元（MMU）中的页表，这会导致较大的开销。

**多线程**

是 **CPU调度** 的基本单位，一个进程可以包含多个线程。

所有线程共享进程的地址空间（全局变量、堆），但每个线程有 **独立的栈和寄存器状态** 。

线程间通信可以直接通过 **共享内存** 进行，速度快，但需要同步机制（如互斥锁、条件变量）避免竞态条件。

线程 **创建和切换开销小于进程** ，但仍需内核参与（内核级线程）

**线程上下文切换** ：只需保存和恢复寄存器状态、栈指针等少量信息，无需切换内存管理信息或文件描述符等资源，开销相对较小。

在IO密集型任务中表现良好，因为当一个线程阻塞时，其他线程可以继续执行。

**多个线程共享同一个进程的地址空间和资源** ，线程间的通信成本较低。

协程（Coroutine）：

是用户态的轻量级线程，由应用程序自行调度，不依赖操作系统调度器。

协程切换 **无需陷入内核，开销极小** （仅保存/恢复寄存器和栈指针）。

协程是协作式调度，一个协程主动让出控制权（yield）后，调度器才能切换到其他协程。

适合高并发I/O场景（如Web服务器），可轻松创建数万个协程。

常见实现：Go的goroutine、Python的async/await、C++20协程、Lua协程等

**底层实现原理：**

核心是栈切换和上下文保存。使用setjmp/longjmp（C语言）或汇编指令（保存/恢复寄存器）实现上下文切换。

每个协程有独立的栈空间（可动态分配），调度器维护协程队列。

在I/O阻塞时，协程主动yield，调度器切换到就绪协程，I/O完成后再将其唤醒。

**进程状态**

进程的状态转换图，可能包括 **新建、就绪、运行、阻塞、终止** 这几个状态。

当进程被创建的时候，它处于新建状态，然后被操作系统放入就绪队列，变成就绪状态。

当CPU调度到这个进程的时候，它开始运行，进入运行态。

如果进程需要等待某个事件，比如I/O操作完成，就会进入阻塞状态，等到事件完成后再回到就绪状态。

最后，当进程执行完毕或者被终止，它就进入终止状态，释放资源。

**进程通信方式**

进程通信的方式主要有以下几种：管道（Pipe）、命名管道（Named Pipe）、消息队列（Message Queue）、共享内存（Shared Memory）、信号量（Semaphore）、套接字（Socket）等。

**管道（Pipe）** ：管道是一种半双工的通信方式，数据只能在一个方向上传输。创建管道后，数据从写端写入，通过读端读取。管道适用于父子进程之间的通信，使用时需注意进程的同步。

**命名管道（Named Pipe）** ：与普通管道不同，命名管道有一个名字，可以用于无亲缘关系的进程之间的通信。它是全双工的，允许双向通信。

**消息队列（Message Queue）** ：消息队列允许进程以消息为单位进行通信。消息可以是任意大小的字节流，进程可以选择读取特定优先级的消息。优势在于可以实现异步通信。

**共享内存（Shared Memory）** ：共享内存允许多个进程访问同一块内存区域，速度非常快，但需要额外的同步机制（如信号量）来避免竞争条件。

**信号量（Semaphore）** ：信号量是一种同步机制，常用于控制对共享资源的访问。它可以用于实现进程间的互斥和同步，常与共享内存配合使用。

**套接字（Socket）** ：套接字不仅用于同一台机器上的进程通信，也可用于不同机器间的通信。它支持全双工通信，适用于网络编程。

**2.线程**

**线程状态**

Java 中线程的生命周期有以下几个状态：

**New（新建状态）** ：当线程被创建但尚未调用 start() 方法时，线程处于 New 状态。

**Runnable（可运行状态）** ：线程调用了 start() 方法后，进入可运行状态，线程可以被操作系统调度执行。注意：此状态并不意味着线程正在执行，只是线程可以被 CPU 执行，它可能被阻塞等待 CPU 时间片。

**Blocked（阻塞状态）** ：当一个线程在等待获得一个对象的锁（即同步锁）时，会进入 Blocked 状态。

**Waiting（等待状态）** ：等待其他线程的特定操作（例如调用 wait() 、 join() 或 park() ）。

**Timed Waiting（计时等待状态）** ：

线程进入此状态时会等待一定的时间。例如，调用 sleep(time) 、 join(time) 或 wait(time) 时，线程进入计时等待状态，等待时间结束后线程自动进入可运行状态。

**Terminated（终止状态）** ：线程执行完任务或者因为异常导致终止进入终止状态。

**Runnable状态**

线程处于 **Runnable** 状态时，是指线程已经被调用 start() 方法后，它处于可以被调度执行的状态。线程在以下情况下会处于 Runnable 状态：

**线程调用了 start()** **方法** ：一旦调用 start() 方法，线程就从 New 状态变为 Runnable 状态，准备被 CPU 调度执行。

**线程没有被阻塞** ：当线程没有被阻塞或等待（即没有进入 Blocked 、 Waiting 或 Timed Waiting 状态），它就处于 Runnable 状态。线程可能因操作系统调度未得到 CPU 执行而暂时不运行，但依然处于可运行状态。

**线程获取了 CPU 执行时间片** ：线程在 Runnable 状态时，可以通过操作系统的调度机制（如线程调度器）获取执行时间片，开始执行任务。

注意，线程进入 **Runnable** 状态并 不意味着线程正在运行 ，它只意味着线程已经准备好并可以被调度执行。当操作系统调度到该线程时，线程会进入 **Running（运行中）** 状态。

**线程的创建方式**

**继承 Thread 类** ：通过继承 Thread 类并重写其 run() 方法来定义线程的任务。

**优点** ：实现简单，适合任务较为单一、明确的情况。

**缺点** ：Java 不支持多重继承，若已经继承了其他类，则不能继承 Thread 类

**实现Runnable 接口** ：通过实现 Runnable 接口，重写 run() 方法，定义线程任务，再通过 Thread 对象执行。

**优点** ： **为什么更推荐？** Java是单继承，实现接口更灵活，以实现多个接口并避免类的继承冲突，更适合线程池等高级用法。

**缺点** ：需要额外创建 Runnable 实现类。

**使用 Callable 接口** ：实现 Callable 接口来获取任务的返回值，通过 ExecutorService 提交任务，并通过 Future 获取结果。

**优点** ： Callable 可以返回任务执行的结果，适用于需要返回值的任务。

**缺点** ：比 Runnable 稍微复杂，且需要使用 ExecutorService 来管理线程池。

**基于线程池** （ **实际开发中最常用** ）：使用 Executors 工具类或直接创建 ThreadPoolExecutor 实例

**优点** ：线程池可以复用线程，减少线程创建和销毁的开销，适用于高并发场景。

**缺点** ：需要管理线程池的生命周期，稍显复杂。

**使用场景/为了干什么** ：

**降低资源消耗** ：可以减少线程频繁创建和销毁带来的性能开销，因为线程创建会涉及到 **CPU上下文切换，内存分配** 等工作。线程池本身会有参数控制线程创建的数量，这就可以避免无休止的创建线程，起到 资源保护 的作用

**提高响应速度** ：任务到达时，通常有现成线程立即执行。

**提高线程的可管理性** ：统一管理线程的生命周期、任务分配和监控。

**常见场景** ：处理大量短期异步任务，例如HTTP请求、文件处理、消息消费等

**种类**

在 Java 的 Executors 工具类中，JDK 提供了几种 **线程池的标准实现** ，底层都基于 ThreadPoolExecutor ：

**Fixed ThreadPool（固定线程池）**

**核心线程数 = 最大线程数** ，线程不会回收，任务多了进入 **无界队列** 。

**适用场景** ：适合 **CPU 密集型任务** （如固定并发任务）。

**Cached ThreadPool（缓存线程池）**

**线程数不固定** ，任务多时创建新线程，空闲 60s 后销毁线程。

**适用场景** ：适合 **短时间大量请求** ，但线程不可控，可能导致内存溢出（OOM）。

**Single ThreadExecutor（单线程池）**

只有 **一个线程** ，所有任务 **按顺序执行** ，保证线程安全。

**适用场景** ：日志记录、数据库操作等 **需要串行执行的任务** 。

**自定义的 ThreadPoolExecutor**

实际开发中，我们更推荐使用自定义的 ThreadPoolExecutor 来创建线程池，以避免因默认使用无界队列或无限线程数带来的系统风险，同时也方便精细化管理线程的生命周期和资源使用。”

**线程创建：线程工厂**

如果不指定，使用的是默认工厂：线程名混乱，无法做日志上下文、监控、异常处理，调试困难。

**线程工厂类型** ：

**自定义线程工厂** ：实现 ThreadFactory 接口，可设置线程名、优先级、守护线程等（如 Guava 的 ThreadFactoryBuilder ）

**线程池池化**

线程池的“池化”机制指的是：

***预先创建并复用一批线程** ，这些线程被保存在“线程池”中，任务来了就复用已有线程执行，而不是每次都创建/销毁线程。*

\*\*不用池会怎么样？\*\*如果每个任务都新建线程来执行，有几个严重问题：

**频繁创建销毁线程非常昂贵** ：线程是系统资源，涉及 JVM 和操作系统的开销；

**线程太多会导致上下文切换开销大** ：过度并发反而导致 CPU 花大量时间在线程调度上；

**可能触发 OOM** ：线程默认栈空间较大（1M 左右），过多线程易耗尽内存；

**调度不可控** ：每个线程都调度会让系统不可预测

**池化核心机制**

**核心线程池** :线程池 **创建后** ，核心线程会一直存在，不会销毁（即使空闲）。提交任务优先使用 **核心线程** 执行。

**任务队列）** :当核心线程都在执行任务时，新的任务进入任务队列 **等待执行** 。

**非核心线程** :如果任务队列已满，且线程数小于 maximumPoolSize ，则会创建 **新线程** 处理任务。

**线程复用** : **执行完任务的线程不会销毁** ，而是回到 **线程池中等待新任务** 。

线程池中的线程在执行完任务后，并不会立即销毁，而是通过 线程存活时间 和核心线程数 的配置来决定是否销毁。如果线程池的线程数超过了核心线程数，并且空闲时间超过了线程存活时间，线程会被销毁；否则，线程会保留在池中，准备执行后续的任务。

**线程销毁** :线程空闲超过 keepAliveTime ，会被销毁（但核心线程不会被销毁）。

**参数 🟢**

**核心线程数** ： 线程池长期维持的线程数，即使空闲也不会销毁

**参数设置：根据 CPU 核数和任务类型（CPU 密集 / IO 密集）设定**

**CPU 密集型任务** （如计算）： 核心线程数 = CPU核数 或 CPU核数 + 1，避免过多线程上下文切换。

**IO 密集型任务** （如网络请求）：由于线程大部分时间在等待IO，可以设置更多的线程 核心线程数 = CPU 核数 \* 2，以便在等待IO时让其他线程使用CPU。

这只是一个 **初始值** 。在真实的生产环境中，需要结合 **监控指标** （如线程池的活跃度、队列大小）进行 **压测和动态调整** ，找到最适合当前业务场景的数值。

**最大线程数** ：线程池允许创建的最大线程数

根据峰值负载设置， **不能无限大** ，避免 OOM

最大线程数-核心线程数就是临时线程数

**线程池队列** : 用来缓存等待执行的任务。

如果线程池中的核心线程数已满，且队列也满了，线程池会根据策略创建新的线程，直到达到最大线程数。

**非核心线程空闲存活时间:** 当线程池中的线程数超过核心线程数时，空闲线程会在指定时间后被销毁。

**线程池拒绝策略:**

当队列满了且线程池中的线程数达到最大线程数时，使用拒绝策略来处理超出任务数的请求。常见的拒绝策略有：

**AbortPolicy** （默认策略）：抛异常，适用于严格要求一致性的场景。（抛出 RejectedExecutionException 异常）

**CallerRunsPolicy(最常用)** ：由提交任务的线程执行任务，适合能容忍延迟的任务。

**DiscardPolicy** ：丢弃任务。

**DiscardOldestPolicy** ：丢弃队列中最旧的任务。

**核心线程数设置为0可不可以？**

当核心线程数为0的时候，会创建一个非核心线程进行执行。

当核心线程数为 0 时，来了一个任务之后，会先将任务添加到任务队列，同时也会判断当前工作的线程数是否为 0，如果为 0，则会创建线程来执行线程池的任务。

**不用阻塞队列如何控制核心线程数**

**✅ 方法 1：使用 SynchronousQueue**

SynchronousQueue **不存储任务** ，任务提交后必须立即由线程执行，否则会创建新线程。

通过 **限制最大线程数为核心线程数** ，确保不会创建额外的线程。

**使用 SynchronousQueue** ，确保线程池中线程数不会超过核心线程数，因为任务提交必须被立即处理

✅ **不想使用线程池的阻塞队列，可以手动管理线程** ：

创建固定数量的核心线程

使用 ExecutorCompletionService管理任务,任务完成后再提交新任务

**手动管理线程生命周期** ，用 ExecutorCompletionService 控制核心线程数并确保任务执行顺序。

**同步机制**

线程池内部为了保证并发线程对任务队列和状态的安全访问，主要依赖 ReentrantLock、Condition、CAS 操作以及 volatile，这样既保证线程安全，

结合执行流程如何体现同步机制

当任务提交到线程池 → 需要加锁检查线程状态，可能新建线程或入队；

当线程从队列中拉取任务 → 需要 **加锁** 判断队列是否为空；

**Condition** 配合 ReentrantLock 实现 **等待-通知机制** ；

例如：当队列为空，工作线程挂起等待新任务；当任务加入队列，调用 condition.signal() 唤醒等待线程；

ReentrantLock ：加锁控制任务队列与工作线程访问；

ReentrantLock 支持中断、定时等待、非公平模式， **适用于高性能线程池设计** ；

不用synchronized 粒度大、可重入但不可中断、性能低；

当线程执行完任务 → 使用 compareAndSet 或 ctl.decrement 原子地修改线程计数；

当线程池 shutdown → 使用 CAS 修改状态，控制是否允许接收新任务。

CAS 操作（如原子变量）：用于状态切换（如 shutdown 等）；

**线程池如何调度线程？🟢**

假设调用 executor.execute(task) 提交了一个任务

**优先使用核心线程** ，如果核心线程都在忙，任务 **进入队列等待** 。

某个线程完成任务后，采用 **FIFO（先进先出）** 方式从队列取出任务

如果 **队列满了** ，创建 **非核心线程** 执行任务。

**线程执行** : **内核级线程调度（由操作系统管理）** ，常见调度算法：

**时间片轮转（RR）** :线程获取 CPU 时间片后执行，时间片耗尽后被挂起，等待下次调度。

**优先级调度** : **高优先级线程** 可能会 **抢占低优先级线程** 的 CPU 资源。

**多级反馈队列（MLFQ）** :长时间运行的线程 **优先级下降** ，避免线程长期占用 CPU。

如果 **线程池已满** ，则触发 **拒绝策略** 。

Future和CompletableFuture是Java中用于 **处理异步任务的接口和类** 。

**Future的原理** ：Future是一个简单的接口，定义了几个方法来获取异步任务的结果。它的核心思想是通过一个线程池执行任务，并返回一个Future对象，这个对象可以用来查询任务的状态或者获取任务的结果。Future的核心方法包括get()、isDone()、cancel()等。其中get()方法会阻塞当前线程直到任务完成并返回结果。

**CompletableFuture异步线程**

CompletableFuture是 **基于事件驱动的异步回调类**

简单来说，就是使用异步线程执行任务时，我们希望任务结束后能够自动触发一个后续的动作。

**JMM（Java内存模型）**

**核心规则** ：

**可见性**

一个线程修改了共享变量，其他线程可能无法立即看到修改后的值（例如，变量可能被缓存在 CPU 核心的寄存器或本地缓存中）

使用 volatile 关键字：强制将变量的读写直接作用于主内存，禁用缓存，保证修改对其他线程立即可见。

使用 synchronized 块或 Lock ：线程在释放锁时会将本地缓存刷新到主内存，获取锁时会从主内存重新加载变量。

**有序性**

编译器和处理器可能对指令进行重排序（优化），导致代码的执行顺序与编写顺序不一致，引发意想不到的结果。

**Happens-Before 规则** ：定义了一系列操作之间的顺序约束，确保某些操作的结果对其他操作可见。

禁止特定类型的重排序（例如 volatile 变量的写操作不能与后续的读操作重排序）

**原子性**

某些操作需要不可中断的原子性（例如 i++ 不是原子操作，因为它包含读取、修改、写入三步）

使用 synchronized 或 Lock 保证代码块的原子性。

使用原子类（如 AtomicInteger ），通过 CAS（Compare-And-Swap）机制实现无锁原子操作。

**1.Synchronized 🟢**

**synchronized在Java中用于实现线程同步，确保多个线程对共享资源的访问是线程安全的。**

**使用方法** ：

**✅ 使用方法**

**同步实例方法**

**锁对象** ：当前实例对象 ( this )。

**竞争场景** ：多个线程调用 **同一个对象实例** 的此方法时会发生锁竞争。

**非竞争场景** ：线程调用 **不同对象实例** 的此方法时，因为锁对象不同，不会相互阻塞。

**同步静态方法**

**锁对象** ：当前类的 Class 对象（如 MyClass.class ）。

**竞争场景** ：所有线程，无论调用哪个实例的此静态方法，甚至直接通过类名调用，都会竞争 **同一个类级别锁** 。它与实例锁完全无关。

**同步代码块（更灵活、更推荐）**

**锁对象** ：可以指定任意对象（ lockObject ）作为锁。

**优势** ：

**减小锁粒度** ：只同步需要保护的临界区代码，而不是整个方法，可以提高并发性能。

**灵活性** ：可以使用专门的私有锁对象（ private final Object lock = new Object(); ），避免直接使用 this 或 Class 对象导致意外的锁竞争（如外部代码直接锁定了你的对象）。

**优缺点**

**优点** ：

**简单易用** ：语法简单，JVM 自动管理锁的获取与释放，无需开发者手动解锁，避免了死锁的可能性（在正常流程下）。

**JVM 保障** ：是 JVM 原生支持的特性，随着 JVM 版本的迭代，其性能一直在优化（如锁升级过程）。

**缺点** ：

**性能开销** ：尽管经过优化，但在高竞争场景下，锁的获取和释放仍然存在开销（尤其是重量级锁）。

**不灵活** ：

**不可中断** ：一个线程如果试图获取一个已被占用的锁，它会一直阻塞下去，直到成功，期间无法被中断。

**非公平锁** ：默认是 **非公平** 的，允许插队，可能导致某些线程长时间饥饿。虽然提供了偏向公平性的策略，但无法严格保证。

**单一条件** ：锁与一个隐式的条件队列（ wait/notify ）绑定，无法实现复杂的条件等待（对比 Lock 接口的多个 Condition ）

**底层原理**

synchronized 的实现依赖于每个 Java 对象内置的一个 **监视器锁 (Monitor)** ，而锁的状态信息则记录在对象的 **对象头中。，当一个线程进入synchronized代码块时，它实际上是在尝试获取该对象的Monitor锁** 。线程进入同步代码块时，首先获取锁，执行完毕后释放锁。如果多个线程争抢同一个对象的锁，则需要等待，直到锁被释放。并且为了平衡性能与开销，JVM 还采用了 **自适应** 的锁升级策略/

**对象头与 Monitor 机制** ：

每个Java对象在内存中都有一个 **对象头** ，其中一部分叫 **Mark Word**

**Mark Word** ：它的结构是非固定的，会根据对象的状态变化， **用来存储对象自身的运行时数据** 如哈希码、GC分代年龄、 **锁状态标志** 等

Mark Word像一个 **状态机** ，会根据锁的状态表示不同的含义：

当没有线程竞争时，它处于 **无锁状态** 。

当第一个线程来加锁，它可能变成 **偏向锁** ，记录这个线程的ID。

当有少量线程竞争，它会升级为 **轻量级锁** ，记录一个指向线程栈中锁记录的指针。

当竞争激烈时，它最终会变成 **重量级锁** ，记录一个指向操作系统级别 **Monitor** 对象的指针。

当 synchronized 作用于代码块或方法时， 通过 "对象头" 来存储锁的状态信息，和 monitor （监视器锁） 来实现同步\*\*。\*\*

**锁升级过程**

JVM 为了优化 synchronized 的性能，引入了 **锁升级** 机制，锁状态随着竞争情况而变化：从 **无锁→偏向锁→轻量级锁→重量级锁** 升级，不可逆。

*synchronized 加锁的过程，其实就是 **改变对象头中 Mark Word 的锁标志位和内容** 的过程*

**无锁** ：一个对象在未被任何线程作为锁对象使用

**偏向锁** ：单线程重复访问时使用。

当第一个线程访问同步块时，通过 CAS 操作将其 线程ID 记录到 Mark Word 中，并将锁标志位设为偏向锁。之后这个线程再进入时，只需检查 线程ID 是否是自己，如果是，则直接进入。 **这里就实现了可重入：检查通过，无需额外操作。**

**轻量级锁** ：当有另一个线程来竞争（多线程轻度竞争时），偏向锁会通过 **CAS自旋** 升级为轻量级锁。

**过程** ：通过 **CAS 操作** 来尝试获取锁。如果成功，就使用轻量级锁；如果失败，说明有竞争，则 **膨胀** 为重量级锁。

**可重入实现** ：JVM 会检查指向 Lock Record 的指针是否指向当前线程的栈帧。如果是，说明是同一线程，允许再次进入，只需在栈中再添加一个 Lock Record 即可。

**重量级锁** ：

**目的** ：处理 **高竞争** 场景如果 **自旋失败（竞争激烈）** ，锁会升级为 **重量级锁**

**过程** ：未抢到锁的线程会 **被阻塞** ，并进入内核态的等待队列，等待操作系统的调度。此时性能开销最大。

**膨胀条件** ：竞争激烈时，轻量级锁自旋超过阈值（默认10次），或有多个线程竞争。

**锁的状态**

Java中的锁机制为了提高性能，采用了锁升级的策略，也就是根据竞争情况动态调整锁的状态。

锁的状态包括无锁、偏向锁、轻量级锁和重量级锁。这些状态之间的转换称为锁的膨胀过程。

**无锁状态** ：当没有线程访问同步代码块时，对象处于无锁状态。

**偏向锁** ：适用于只有一个线程访问同步块的场景。偏向锁通过在对象头中记录线程ID，使得同一线程再次进入时可以无需额外的同步开销。

**轻量级锁** ：当有多个线程交替访问同步块，但没有同时竞争时，锁会升级为轻量级锁。

轻量级锁使用CAS操作来尝试获取锁，避免阻塞。

**重量级锁** ：当多个线程竞争同一锁时，轻量级锁会膨胀为重量级锁。

重量级锁依赖于操作系统的互斥量（mutex）来实现，会导致线程阻塞和唤醒，带来较大的性能开销

**synchronized可重入**

**可重入锁** ，也叫做递归锁，指的是： **同一个线程在外层方法获取锁之后，在进入内层方法时会自动获取同一把锁，而不会因为之前已经获取过但还没释放就被阻塞。**

synchronized 的可重入性是如何在底层实现关键在于 **锁计数器** 。

**对象头与Monitor** ：锁信息存储在对象头的 Mark Word 中，并与一个 Monitor 关联。

**计数器机制** ：在 Monitor 的内部结构有一个重要的字段叫 **\_count** **（计数器）** 。

当线程第一次成功获取锁时，JVM 会将 Monitor 的 Owner 设置为当前线程，并将计数器 \_count **加 1** （从0变为1）。

**当这个同一个线程再次获取同一个锁时** ，它发现 Owner 就是自己，于是不会进行真正的获取锁操作（比如CAS），而仅仅是将计数器 \_count **再次加 1** （比如从1变为2）。

当线程退出同步代码块时，计数器 \_count 不会直接清零，而是会 **减 1** 。

只有当计数器 **减到 0** 时，才表示这个线程彻底释放了锁，此时 JVM 才会将 Monitor 的 Owner 设置为 null ，并唤醒其他在 EntrySet 中等待的线程

**2. ReentrantLock 🟢**

ReentrantLock 是 **Lock** **接口** 的实现类，可以提供 **更高级的锁控制** ， **如公平锁、非公平锁、可中断锁、超时获取锁、多 Condition** **变量等。**

lockInterruptibly() 允许线程 **在等待锁的过程中被中断** ：

**锁的管理** ：与 synchronized 不同， Lock 需要显式地调用 lock() 和 unlock() 方法来加锁和释放锁。必须确保 unlock() 被调用，否则会导致死锁。

**可以中断** ： Lock 可以响应中断。线程在等待锁时可以中断，避免了 synchronized 不能中断阻塞线程的问题。

**公平性** ： Lock 可以设置为 **公平锁** ，即线程按照请求锁的顺序获取锁，防止线程饥饿。

**条件变量** ： Lock 还提供了条件变量（通过 Condition ），允许线程在等待锁时进行更精细的线

**AQS队列同步器**

AQS 通过 **双向链表** 管理线程的排队与唤醒，并维护一个 **状态变量（state）** **表示锁的占用状态** 。 ReentrantLock 通过 **继承 AQS 并实现其模板方法** （如 tryAcquire 、 tryRelease ）来实现 **可重入锁,阻塞 加锁 解锁** 。

**加锁** ：当一个线程尝试获取锁时，AQS 会检查锁是否被占用（通过 tryAcquire() ），通过 CAS 修改 state 。如果锁已经被占用，将线程封装为 Node 加入等待队列尾部，进入阻塞状态。

**释放锁** ：当线程释放锁时，调用 release(int) 修改 state ，并唤醒等待队列中的下一个线程。

**可重入**

**状态变量（state）**

AQS内部维护了一个状态变量（state），用来表示 **锁是否被占用和锁的持有次数** （通过 getState() 和 setState() 方法）。当线程尝试获取锁时，会通过CAS操作来修改state的值。

如果state为0，表示锁未被占用，线程可以获取锁并将state加1；

如果state不为0且当前线程是锁的持有者，则state继续加1，实现可重入。

**公平锁与非公平锁**

ReentrantLock 支持公平锁（按请求顺序获取）和非公平锁（抢占式）。

ReentrantLock 的公平锁与非公平锁的差异，核心体现在 **线程获取锁的策略** 上：

**公平锁 (Fair Lock)** ：遵循 **“先来后到”** 原则。锁被释放时，总是优先分配给 **等待时间最长** 的线程。

**非公平锁 (Nonfair Lock)** ：允许 **“插队”** （抢占）。线程可以尝试直接获取锁，无论等待队列中是否已有其他线程在等待。

AQS 提供了队列的管理，并通过某些逻辑来实现这两种模式

**获取锁逻辑** ：区别完全体现在 tryAcquire 方法的实现上

**非公平锁** ：

线程一来，先直接尝试一次 CAS 操作去抢锁（ compareAndSetState(0, 1) ），如果成功，就直接拿到锁了。 **这次尝试插了所有等待队列中线程的队** 。

如果抢失败，才调用 AQS 的 acquire 方法，该方法内部会再次调用 tryAcquire ，此时才会去检查队列。

**公平锁** ：

在尝试 CAS 设置 state 之前，会先调用 hasQueuedPredecessors() 方法 **检查等待队列中是否有比自己更早的线程在排队** 。

如果有，那么当前线程乖乖地失败，然后去队列尾排队。保证了绝对的公平。

可中断： lockInterruptibly() 允许中断等待。

超时机制： tryLock(long, TimeUnit) 避免死锁。

**Q：为什么用 双向链表 ？**

AQS的核心是 **公平等待和条件变量** 。公平等待意味着每个线程都能平等地被唤醒；而条件变量则允许线程在特定条件下被唤醒。

删除指定线程 用单向链表的话，得从头开始找这个节点的前驱，效率太低了。而用双向链表，直接通过prev找到它

挂起等待 用双向链表的话，检查前驱节点的状态，就能快速判断是否可以挂起

**同步器AQS（自己理解）**

**锁** 是面向使用者的，它定义了线程如何获取和释放资源的规则。锁通常是通过 API 来进行操作，用户只关心如何通过这些 API 来控制线程的同步。

**同步器 AQS** 是面向实现者的，它定义了锁如何实现。AQS 提供了一个基础的框架和机制，隐藏了许多并发操作的复杂性，允许我们根据需求实现不同类型的锁或同步器。

AQS不是锁，而是一个高效的等待队列。它通过双向链表实现各种操作，比如删除节点、挂起等待等，极大地提升了并发系统的性能和效率。

**ReentrantLock重写AQS**

模板方法模式

AQS 使用了 **模板方法模式** ，即通过定义一组固定的流程（如获取锁、释放锁等），只需要去重写AQS 的抽象方法 tryAcquire() 和 tryRelease() ,就可以实现根据自己需要不同的同步/互斥/锁效果

如果我们实现一个自定义的同步器，比如一个简化版的锁，我们只需要关注两个核心方法：

tryAcquire(int arg) ：尝试获取锁的逻辑。

tryRelease(int arg) ：释放锁的逻辑。

ReentrantLock的可重入锁的实现,阻塞 加锁 解锁都是基于的AQS组件实现的

**synchronied vs lock？**

|            |                                         |                                                                                                                 |
|------------|-----------------------------------------|-----------------------------------------------------------------------------------------------------------------|
| 特性       | synchronized                            | ReentrantLock                                                                                                   |
| **用法**   | JVM 关键字，隐式加锁解锁                | API 形式，需显式 lock() 和 unlock()                                                                             |
| **灵活性** | 基础，不灵活                            | **非常灵活** ：可尝试非阻塞获取( tryLock )、可中断( lockInterruptibly )、可超时( tryLock(time) )、可公平/非公平 |

**选择建议：**

**语法** ： synchronized 是关键字，JVM层面； Lock 是接口，API层面。

**灵活性** ： Lock 更灵活，可以尝试非阻塞获取锁( tryLock() )、可中断( lockInterruptibly() )、公平锁等。

**优先考虑 synchronized** ：如果你的需求非常简单，不需要 Lock 提供的那些高级功能（如可中断、超时）， **永远优先选择 synchronized** 。因为它更简洁，由 JVM 管理不会忘记解锁，并且经过充分优化，性能不差。

**必须使用 ReentrantLock** ：只有当你的业务需要 **synchronized** **无法提供的特性** 时，才使用 ReentrantLock 。例如：

需要尝试获取锁 ( tryLock() )。

需要可中断的锁获取 ( lockInterruptibly() )。

需要公平锁。

需要同时等待多个条件（ Condition ）。

**Volatile 关键字🟢**

**volatile** **的原理** ：它用于 **确保线程可见性** ，即当一个线程修改了被 volatile 修饰的变量，其他线程能立即看到这个变化。它的实现通过 **内存屏障** （Memory Barrier）来强制将修改写入主内存，并确保不会对值的读取进行优化。

**保证可见性** ：一个线程修改了volatile变量，新值会立刻刷新到主内存，并使得其他线程的工作内存中的该变量副本失效。

**禁止指令重排** ：通过插入 **内存屏障** 实现

volatile 变量的读写不会与其他变量的读写发生重排序：

在 volatile 变量的读/写前后，可能会插入 \*\*内存屏障指令 \*\*，确保 CPU 不会对该变量的访问进行重排序。

内存屏障，是一类CPU指令。可以把它理解成一个 **栅栏** ，插入在两个指令之间，保证屏障前的指令一定在屏障后的指令之前执行。

volatile关键字的 **应用场景** 主要有：

**状态标记变量** ：用于表示线程的状态，如线程的终止标志。一个线程可以通过修改volatile修饰的状态变量来通知其他线程停止执行。

**单例模式的双重检查锁定** ：在实现单例模式时，使用volatile来保证在多线程环境下实例的唯一性和可见性。

**Q** ： **volatile** 如何保证 **可见性和有序性** ？

**可见性** ：通过 JMM 的 store 和 write 操作强制将工作内存变量刷到主内存。

**有序性** ：插入内存屏障（如 StoreStore 屏障禁止写重排序）。

**Q ： volatile 能用作线程同步吗(锁/原子性)？**

**不能** 。 volatile 只保证可见性，但 **不保证原子性** 和 **不保证操作顺序** ，因此它不能用来替代 synchronized 或其他线程同步机制。比如 x++ 这样的操作， volatile 不能确保其原子性。

**ThreadLocal 🟢**

**原理**

ThreadLocal实现了线程安全，是因为它为每个线程提供了独立的变量副本，从而避免了多线程竞争。

**内存结构**

每个 Thread 对象内部都有一个 ThreadLocalMap 类型的变量 threadLocals

ThreadLocal Map的Key是 **ThreadLocal** **对象本身（弱引用）** ，Value是存储的值。

**Key是弱引用** ：

在 ThreadLocalMap 中，Key（也就是 ThreadLocal 对象）是以 **弱引用** 的形式存储的。

**目的** ：防止内存泄漏。当外部的强引用指向 ThreadLocal 对象被回收时（比如设置为 null ），弱引用不会阻止该 ThreadLocal 对象被垃圾回收。

**Value是强引用** ：

如果线程长期存在（例如使用线程池），那么即使 ThreadLocal 对象被回收了，Map 中也会存在一个 Key为null 但 Value不为null 的条目，这个 Value 无法被访问，但也无法被回收，从而造成 **内存泄漏** 。

**线程安全实现方式：**

由于每个线程在访问ThreadLocal变量时，操作的都是各自线程内部的ThreadLocalMap，所以不存在多线程共享数据的问题，自然也就没有线程安全问题。

**实现原理** ：

**操作流程** ：

**set(value)** ：当调用 set() 时，实际上是以当前 ThreadLocal 实例为Key，将值存入了当前线程的 threadLocals 中

**get()** ：从当前线程的 threadLocals 中以当前 ThreadLocal 实例为 Key 查找对应的值；如果不存在，则调用 initialValue() 方法初始化，并将初始值存入 Map。

**核心思想** ：数据不保存在 ThreadLocal 本身中，而是保存在 **线程对象（Thread）** 中。 ThreadLocal 只是一个用于访问这些数据的 **工具类（Key）** 。这样就完美实现了 **数据在不同线程间的隔离** 。

**JVM怎么实现线程安全**

JVM为每个线程分配了独立的栈内存空间，而ThreadLocal变量实际上是存储在每个线程的ThreadLocalMap中，这个ThreadLocalMap是线程私有的，位于堆中，但通过线程对象的引用进行关联，每个线程只能访问自己的ThreadLocalMap。

JVM的内存管理机制（如堆、栈的隔离）以及垃圾回收机制（特别是对弱引用的处理）也帮助了ThreadLocal的实现。

**ThreadLocal 变体**

ThreadLocal 的扩展，解决了值在 **线程之间传递** 的问题。

**InheritableThreadLocal** ：

**解决的问题** ：普通 ThreadLocal 无法在父子线程间共享数据。

子线程在创建时会拷贝父线程的 ThreadLocal 值。

适合需要继承上下文的场景（如日志 traceId、用户会话信息）。

局限：只能在 **新建子线程时** 继承，线程池复用线程时不生效。

**TransmittableThreadLocal (TTL)** ：

阿里开源，专门解决 **线程池复用场景下上下文传递** 的问题。

通过包装线程池任务（Runnable/Callable），在任务提交和执行时手动传递上下文。

在任务被线程池执行 **前** （ execute 方法），会抓取当前线程的TTL值（快照）；在任务实际 **执行时** ，会将快照的值还原到线程的TTL中，执行完后再清理。完美适配了线程池的异步场景。

**ThreadLocal 会产生哪些问题**

**内存泄漏** ：

由于 ThreadLocalMap 的 key 使用 **弱引用** ，ThreadLocal 对象被回收后可能导致 **value 内存泄漏** （如果线程长时间存在，比如线程池场景）

**线程池** 场景会复用线程，因此某些线程在执行完任务后继续执行其他任务，可能导致之前使用 ThreadLocal 存储的线程局部变量被错误地共享或覆盖。

**解决方法** ：为了避免这种情况，可以通过手动清除 ThreadLocal 中的数据，确保线程退出时不会带有之前任务的副本。可以通过 ThreadLocal.remove() 来清除线程局部变量的数据。

**不适用跨线程场景** ：

ThreadLocal 只能用于单个线程内的局部变量。如果想要共享数据， ThreadLocal 不适用。它并不提供线程间的数据共享机制，因此不能用于跨线程数据的传递。

**CAS原子操作——无锁🟢**

**CAS（Compare-And-Swap）**

CAS操作避免了 **使用锁带来的线程上下文切换和竞争开销**

CAS 是一种 **乐观锁机制** ，它包含三个操作数：内存位置（V）、预期值（A）和新值（B）。CAS 操作的逻辑是，如果内存位置 V 的值等于预期值 A，则将其更新为新值 B，否则不做任何操作。整个过程是 **原子性的** ，通常由硬件指令支持，如在现代处理器上， cmpxchg 指令可以实现 CAS 操作。

**CAS ABA问题**

**ABA 问题** ：如果一个值经历了多次修改，且原始值与修改后的值相同，CAS 会认为操作是成功的，但实际上可能发生了数据改变，导致程序的逻辑出错。

Java AtomicStampedReference 类可以解决ABA问题，

它通过引入时间戳（stamp）来标识值的版本，在进行CAS操作时 **不仅比较值，还比较时间戳** 。

**长时间轮询** ：在并发量非常高的情况下，CAS 可能会发生频繁的重试，导致 CPU 资源的浪费。

**只能操作单一变量** ：CAS 操作仅能保证对单个变量的操作原子性，无法在多个变量间进行原子操作，因此在需要多个值原子更新的场景下，CAS 并不适用。

**原子类（Atomic Classes） ：**

以Java为例，java.util.concurrent.atomic包提供了 **AtomicInteger、AtomicLong、AtomicBoolean、AtomicReference** 等类。这些类内部使用了 **Unsafe类** 调用 **CPU底层的CAS指令** 来实现 **原子更新** 。

例如，AtomicInteger的incrementAndGet()方法本质上是循环尝试使用CAS将值加1，直到成功为止（即自旋+CAS），这种模式称为“乐观锁”。

**用CAS为啥还用锁？**

CAS适用简单原子操作（如更新标量），但无法处理复合操作（如需保证多个变量一致性）。

锁（如synchronized）可保证临界区代码的原子性，而CAS需自旋可能浪费CPU。

**i++多线程的写操作安全🟢**

Q： **i++是原子性吗？为什么？**

**不是原子性的** 。 i++ （或 i = i + 1 ）包含了三个独立的操作：

**读 (Read)** ：从内存中读取变量 i 的当前值到 CPU 寄存器。

**改 (Modify)** ：在寄存器中将值加 1。

**写 (Write)** ：将寄存器中的新值写回内存。

在多线程环境下，这两个线程的这三个步骤可能会 **交错执行** ，导致最终结果小于预期。

**使用 synchronized** **关键字** ：通过互斥锁保证临界区的原子性。

**使用 ReentrantLock** ：显式锁，提供更灵活的控制。

**使用原子类 (Atomic Classes)** （ **最佳方案** ）：如 AtomicInteger ，利用 CAS 指令实现无锁线程安全。

AtomicInteger 等原子类的内部就是使用 **Unsafe 类提供的 CAS 操作** 来原子地更新一个 int 值。

它不断地循环尝试，直到 CAS 成功为止。这其实就是乐观锁的实现： **先计算，更新时再检查是否冲突，冲突则重试** 。

**公平锁&非公平锁 🟢**

**公平锁** 是指 **多个线程按照申请锁的顺序（FIFO）获取锁** ，即 **先来先得** 。

**实现方式** ：通过 **队列（ReentrantLock 构造参数 true）** 维护获取锁的顺序。

**优点** ： **避免线程饥饿** ，每个线程都能公平竞争，避免某些线程长期得不到锁。

**缺点** ： **性能较低** ，因为每次获取锁都需要检查等待队列，增加了开销。

**非公平锁** 允许 **线程“插队”抢占锁** ，即 **不完全按照 FIFO 顺序获取锁** ，如果锁可用，线程可以直接获取而无需排队。

**实现方式** ：默认的 ReentrantLock(false) （默认非公平）。

**优点** ：减少了线程切换的开销，提高了并发性能。

**缺点** ： **可能造成线程饥饿** ，某些线程可能长期得不到锁。

**悲观锁&乐观锁🟢**

🟢 **悲观锁** ：认为并发冲突一定会发生，所以在操作数据前先加锁（ **synchronized** 和 **ReentrantLock** ，数据库的 select ... for update 就是典型的悲观锁） **适合写多读少** 的场景。

**实现方式** ：通过加锁确保只有一个线程访问共享资源，其他线程需要等待锁释放。

**synchronized** **的行为** ：它在进入同步块之前，一定会先获取锁，如果获取不到，线程就会被 **挂起（阻塞）**

**适用场景** ：资源访问冲突较频繁，操作数据时需要保证一致性。订单处理、库存更新

🟢 **乐观锁** ：认为并发冲突不常发生，所以不在数据上加锁，而是在更新时判断此期间数据是否被他人修改过（通过版本号version或CAS算法）。 **适合读多写少** 的场景。

在Java中， AtomicInteger 等原子类使用了CAS乐观锁；

在数据库中，可以通过 where version = old_version 来实现

**实现方法** ：

**版本号机制** ：在数据表中增加一个 version 字段。读取数据时带上 version，更新时检查 version 是否未被修改。

**死锁**

死锁是指两个或多个进程在执行过程中因争夺资源而造成的一种僵局，当这些进程都在等待对方释放资源时，所有进程都无法继续执行。

防止死锁的方式包括破坏死锁的四个必要条件之一（互斥、请求和保持、不剥夺、循环等待）或者通过银行家算法进行避免。

**死锁的四个必要条件**

**互斥条件** ：每个资源要么正在被一个线程占用，要么是可用的，不能同时被多个线程占用。

**持有并等待条件** ：一个线程持有一个资源，同时等待获取其他线程持有的资源。

**不可抢占条件** ：线程已经获得的资源，其他线程不能强制抢占。

**循环等待条件** ：多个线程之间形成一种循环等待关系。

**解决办法** ：

**预防** ： **解决死锁的核心目标是破坏其中的至少一个条件** 。（如：资源一次性分配、允许剥夺、资源有序分配）。

**统一锁的获取顺序** ：确保多个线程获取锁的顺序一致。

**使用 tryLock()** **加锁超时** ：使用 tryLock() 来避免线程一直等待锁的释放。

**避免嵌套锁** ：尽量避免在一个锁内再次请求另一个锁。
