**一、如何创建线程？线程池常见参数有哪些？\<Java多线程 1148\>**

在 Java 里创建线程主要有三种方式：继承 Thread、实现 Runnable、实现 Callable。

继承 Thread 和实现 Runnable 本质上区别不大，只是 Runnable 更符合面向对象思想，因为它把任务和线程解耦。Callable 相比 Runnable 多了返回值和异常处理能力。

不过在实际生产环境中，我们基本不会直接创建线程，而是使用线程池。原因有两个：

线程创建和销毁成本比较高；

线程数量不可控容易把系统资源耗尽。

线程池可以实现线程复用，同时控制并发上限。

线程池最核心的参数有几个：

第一是核心线程数。

第二是最大线程数。

第三是任务队列。

第四是拒绝策略。

线程池的执行流程是：

如果核心线程没满，直接创建核心线程执行；

核心线程满了就进任务队列；

队列满了就创建非核心线程；

如果线程数达到最大线程数，就执行拒绝策略。

在参数设置上，CPU 密集型任务一般设置为 CPU 核数 + 1

IO 密集型可以适当调高，因为线程大部分时间在等待。

**二、什么是进程和线程？区别？ \<操作系统 1094\>**

进程是操作系统分配资源的基本单位，每个进程都有独立的地址空间。

线程是 CPU 调度的基本单位，一个进程可以有多个线程，线程之间共享进程的内存和资源。

核心区别主要有三点：

第一，进程资源独立，线程共享资源。

第二，进程创建和切换成本高，线程成本低。

第三，进程间通信需要 IPC，而线程之间可以直接通过共享内存通信。

正因为线程共享资源，所以才会有线程安全问题。

在 Java 中，线程通常是一对一映射到操作系统内核线程。

**三、请你说说 HashMap 底层原理和扩容机制 \<Java基础 969\>**

在 JDK1.8 之后，HashMap 的底层结构是数组 + 链表 + 红黑树。

插入元素时，首先会计算 key 的 hash 值，然后通过位运算定位到数组下标。如果该位置为空就直接插入；如果发生哈希冲突，就以链表形式挂在该位置。

当链表长度达到 8 并且数组容量大于等于 64 时，会转换成红黑树，避免查询复杂度退化成 O(n)。

扩容触发条件是当元素数量超过 容量 × 负载因子。默认容量 16，负载因子 0.75。

扩容时容量会翻倍，并重新分布元素。JDK1.8 做了优化，不需要重新计算 hash，只需要判断元素是否需要移动到原索引加 oldCap 的位置。

容量设计成 2 的幂，是为了让位运算代替取模运算，提高效率。

**四、Redis 如何与数据库保持双写一致？ \<分布式 895\>**

这是一个分布式一致性问题。

常见的做法是先更新数据库，再删除缓存。这种方式可以避免缓存中长期存在脏数据。

但在高并发场景下，仍然可能出现短暂不一致，因此可以采用延迟双删策略，即删除缓存后等待一小段时间再删除一次。

如果对一致性要求更高，可以引入消息队列。更新数据库后发送消息，由消费者删除缓存，从而实现最终一致性。

还有一种方案是监听数据库的 binlog，比如通过 Canal，根据数据库变更自动删除缓存。

**五、TCP 与 UDP 的核心区别 \<TCP/UDP 855\>**

连接方式：

TCP 是面向连接的协议，通信前需要通过三次握手建立连接。

UDP 是无连接协议，发送数据前不需要建立连接。

可靠性：

TCP 提供可靠传输，依靠序列号、确认应答、超时重传等机制，保证数据不丢失、不重复、不乱序。

UDP 不保证传输可靠性，不保证数据一定到达，不保证数据顺序，出现丢包也不会重传。

传输形式：

TCP 是字节流协议，数据没有明确边界。

UDP 是数据报协议，保留消息边界，按数据报进行传输。

流量控制：

TCP 具备流量控制，通过滑动窗口机制避免发送方发送速度过快导致接收方无法处理。

UDP 没有流量控制机制。

拥塞控制：

TCP 拥有拥塞控制，包含慢启动、拥塞避免等策略，防止网络出现拥塞。

UDP 没有拥塞控制机制。

首部开销：

TCP 首部开销较大，最小长度为 20 字节。

UDP 首部开销很小，固定为 8 字节。

传输效率：

TCP 建立连接、保证可靠性等操作带来额外消耗，传输效率较低，延迟较高。

UDP 无需连接、无确认重传等逻辑，传输效率高，延迟极低。

双工特性：

TCP 支持全双工通信，通信双方可以同时发送和接收数据。

UDP 支持一对一、一对多、多对多通信，但本身不维护连接状态。

适用场景：

TCP 适用于对数据可靠性要求高的场景，例如 HTTP、HTTPS、文件传输、邮件、数据库连接等。

UDP 适用于对实时性要求高、允许少量丢包的场景，例如音视频通话、直播、网络游戏、DNS 查询等。

连接关闭：

TCP 断开连接需要经过四次挥手，连接关闭后存在 TIME_WAIT 状态。

UDP 无连接概念，不需要专门的关闭流程。

**六、详细说说 Redis 的数据类型 \<Redis 847\>**

Redis 提供多种数据结构，而不仅仅是简单的 Key-Value。

最基础的是 String 类型，本质是二进制安全字符串，可以存字符串、数字甚至序列化对象。常用于缓存数据、计数器、分布式锁等场景。

List 是一个有序列表，支持两端插入删除，适合做简单消息队列或时间线。

Hash 是键值对集合，适合存储对象属性，比如用户信息。相比直接存 JSON，它可以只更新某个字段，更灵活。

Set 是无序且元素唯一的集合，常用于去重、共同好友、标签系统。

Sorted Set 在 Set 的基础上增加了 score，可以按分值排序。底层使用跳表实现，适合做排行榜、延时队列等。

除此之外还有一些特殊结构。Bitmap 适合做签到、活跃统计；HyperLogLog 用于大规模基数统计，比如 UV 统计，占用空间极小；GEO 基于有序集合实现，用于地理位置计算。

整体来看，Redis 的优势在于它把多种高效数据结构内置在内存中，使得很多业务逻辑可以直接在缓存层完成。

**七、测试用例设计的方法论你怎么落地？等价类、边界值、判定表、因果图、错误推测、场景法各给一个你写过的高质量用例 \< 测试开发 734\>**

首先是等价类划分，它主要用来覆盖输入参数的典型情况，避免穷举。我之前做用户注册接口时，针对手机号字段写过用例，有效等价类就是合法的 11 位手机号，比如 13800138000；无效等价类就包括不足 11 位、超过 11 位、带字母特殊符号、空值这些，这样用最少的用例，就能覆盖所有手机号的校验场景。

然后是边界值分析法，这个方法我用得很多，因为大部分 bug 都出在边界上。比如之前做订单金额接口，要求金额≥1 元、≤10000 元，我就专门测了 0 元（刚低于下限）、1 元（刚好下限）、10000 元（刚好上限）、10001 元（刚超上限），还有一个中间值 500 元，这样就能精准覆盖边界的校验逻辑。

接下来是判定表法，适合多条件组合的场景。我之前做下单接口时，下单需要满足三个条件：商品上架、库存充足、用户正常，我就把这三个条件的所有组合都列出来，比如上架 + 库存足 + 用户正常，就能下单；未上架 + 库存足 + 用户正常，就拒绝下单，还有其他各种组合，确保每个逻辑分支都能覆盖到，尤其是那种部分条件满足但最终失败的情况，避免有遗漏。

然后是因果图法，它比判定表更侧重条件之间的依赖约束。我之前做退款申请接口时用过，比如退款的前提是 “订单已支付、未发货、未超过退款时效”，这三个是 “因”，允许退款是 “果”；只要其中一个条件不满足，比如订单已发货，就不能退款，我会先梳理清楚这种因果约束，再设计用例，确保逻辑不会出错。

还有错误推测法，这个主要靠平时的项目经验，猜那些容易出 bug 的点。我之前做文件上传接口时，就专门设计了几个用例：上传空文件、上传超大文件、上传.jsp 这种非法后缀的文件，还有上传过程中断网，这些都是根据经验判断，后端接口容易出问题的地方，测这些能提前规避风险。

最后是场景法，适合有完整业务流程、状态流转的场景。我之前做订单支付流程时，就按正常流程和异常流程来设计用例：正常流程是创建订单→待支付→支付成功→已完成；异常流程就包括订单超时未支付自动取消、支付回调重复、支付成功但库存不足回滚订单，确保整个流程能走通，非法的状态流转也能被拦截。

其实在实际工作中，我不会单独用某一种方法，通常是先用等价类和边界值做基础覆盖，再用判定表或因果图覆盖复杂逻辑，场景法覆盖完整业务流程，最后用错误推测法补全高风险点，核心就是用最少的用例，覆盖所有关键路径和可能出 bug 的地方，确保后端接口的功能、边界、异常都能经得起测试。

**八、请你说说Array List和LinkedList的区别 \<Java 基础 683\>**

首先，底层结构不同。 Array List 底层是基于动态数组实现的，本质是一块连续内存空间。 LinkedList 底层是双向链表，每个节点存储数据以及前后指针。

其次是访问性能。 Array List 支持随机访问，通过下标访问元素时间复杂度是 O(1)，因为它是连续内存，可以直接通过地址偏移计算。 LinkedList 不支持随机访问，访问某个元素需要从头或尾遍历，时间复杂度是 O(n)。

再说插入和删除。 Array List 在尾部插入元素效率比较高，均摊时间复杂度是 O(1)，但如果在中间插入或删除，需要移动后续元素，时间复杂度是 O(n)。 LinkedList 在已知节点位置的情况下，插入和删除是 O(1)，因为只需要修改前后指针。但前提是你已经找到了那个位置，否则查找过程仍然是 O(n)。

然后是扩容机制。 Array List 有容量概念，当容量不足时会扩容，一般是原容量的 1.5 倍，并且需要把原数组复制到新数组。 LinkedList 不存在扩容问题，因为它是链式存储，按需分配。

再看内存开销。 Array List 只存数据本身，占用空间相对较少，但可能会有预留容量浪费。 LinkedList 每个节点都需要额外存两个指针，所以内存占用更大，而且不连续，对 CPU 缓存不友好。

在实际项目中，大多数情况下我会优先使用 Array List，因为读操作远多于写操作，而且数组结构对缓存友好，整体性能更稳定。 LinkedList 更多是在频繁插入删除、并且对随机访问要求不高的场景下使用，但在真实业务中使用频率远低于 ArrayList

**九、说说缓存穿透、击穿、雪崩的区别 \< 分布式 677\>**

首先是缓存穿透。

缓存穿透指的是查询一个根本不存在的数据。因为缓存里没有，数据库里也没有，每一次请求都会直接打到数据库。如果有人恶意构造大量不存在的 key，就会把数据库压垮。

它的特点是：请求的数据“根本不存在”。

常见解决方案有两个： 第一，布隆过滤器，在请求进入缓存前先判断 key 是否可能存在； 第二，对数据库中不存在的数据也缓存一个空值，并设置较短的过期时间，防止重复查询数据库。

第二是缓存击穿。

缓存击穿指的是某一个热点 key 在某一时刻刚好失效，而这时候并发请求非常高，大量请求同时打到数据库。

它的特点是： 数据是存在的，而且是热点数据，只是在某个瞬间缓存失效。

解决方案一般是： 第一，给热点 key 加互斥锁或分布式锁，只允许一个线程去加载数据库，其它线程等待； 第二，设置逻辑过期，而不是物理过期； 第三，热点数据不过期，由后台异步更新。

第三是缓存雪崩。

缓存雪崩是指大量缓存 key 在同一时间失效，或者缓存服务整体宕机，导致所有请求直接打到数据库。

它的特点是： 影响范围大，不是一个 key，而是一批 key。

常见解决方案包括： 第一，给缓存过期时间增加随机值，避免同时失效； 第二，构建多级缓存，比如本地缓存 + Redis； 第三，缓存集群高可用，比如主从 + 哨兵或集群模式； 第四，限流和降级措施，保护数据库。

**十、说说JVM的垃圾回收算法 \<JVM 657\>**

JVM 的垃圾回收核心其实可以分成两个问题：第一，怎么判断对象是不是垃圾；第二，用什么方式把垃圾回收掉。

先说第一个问题。JVM 不是用引用计数，而是用可达性分析。它会从一组 GC Roots 出发，比如栈里的局部变量、静态变量、正在运行的线程对象等，从这些根节点往下遍历，凡是还能被访问到的对象就是存活的，遍历不到的就是可以回收的对象。这种方式可以解决循环引用的问题。

第二个问题就是具体的回收算法。经典的有三种。

第一种是标记-清除。先标记所有存活对象，然后把没有标记的对象清掉。实现简单，但问题是会产生内存碎片，而且清理效率不算高。

第二种是复制算法。它把内存分成两块，每次只用一块，发生 GC 时把存活对象复制到另一块，然后把原来的空间整体清空。优点是不会有碎片，而且分配内存很快；缺点是空间利用率低。JVM 在新生代基本就是用这种思路，因为新生代对象大部分都会很快死亡，复制成本低。

第三种是标记-整理。流程是先标记存活对象，然后把这些对象往一端移动，最后清理边界外的空间。这样既没有碎片，也不需要额外一半空间，但移动对象的成本比较高。老年代一般会采用这种方式。

实际上 JVM 并不是只用某一种算法，而是采用分代收集的思想。因为对象生命周期不同，新生代对象存活率低，适合复制算法；老年代对象存活率高，更适合标记-整理或者改进版的标记-清除。

**十一、进程间通信方式有哪些？ \< 操作系统 656\>**

面试官您好，进程间通信我一般会从 **本地同一台机器** 和 **跨主机通信** 两个维度来梳理，这样思路会比较清晰。

首先是 **同一台机器内的本地 IPC** 。

第一种是 **管道** ，分为匿名管道和命名管道。

匿名管道只能用于 **有亲缘关系** 的进程，比如父子进程，是单向通信，底层依赖内核缓冲区。

命名管道可以用于 **无亲缘关系** 的进程，因为它在文件系统中有名字，其他进程可以通过名字访问。

第二种是 **消息队列** 。

它是由内核维护的消息链表，可以按类型收发结构化消息，比管道更灵活。

但缺点是受内核资源限制，消息总量和大小都有上限。

第三种是 **共享内存** 。

这是 **效率最高** 的 IPC 方式，因为多个进程直接映射同一块物理内存，数据不需要在用户态和内核态之间来回拷贝。

但它本身 **不提供同步机制** ，所以一般要和信号量一起配合使用。

第四种是 **信号量** 。

它主要不是用来传数据，而是实现 **进程间的同步与互斥** ，解决并发访问临界资源的问题，常和共享内存搭配。

第五种是 **信号** 。

它是一种异步通知机制，用来告诉进程发生了某个事件，比如异常、终止等，只能传递简单信息，不能传输大量数据。

然后是 **跨主机也能用的通信方式：Socket** 。

Socket 既可以用于本机，也可以跨机器。

本机可以用 Unix Domain Socket，性能比 TCP 更高；

跨机器就是基于 TCP 或 UDP 的网络通信，也是现在微服务里最常用的进程间通信方式。

如果从性能上简单对比：

**共享内存最快** ，然后是管道、消息队列，再是本地 Socket，跨网络的 TCP 相对最慢。

总结一下：

本地 IPC 主要有管道、消息队列、共享内存、信号量、信号；跨主机用 Socket。

实际使用时，我会根据 **是否跨机器、数据量大小、通信频率、是否需要同步** 来选择最合适的方式。

**十二、如何监控并优化慢 SQL？ \<SQL 644\>**

关于慢 SQL 排查与优化，我一般会从 **发现、定位、优化** 三个阶段来完整说明。

首先是 **如何发现慢 SQL** 。

线上最常用的就是开启数据库的 **慢查询日志** ，设置一个阈值，比如超过 500ms 或 1s 的 SQL 自动记录下来。同时生产环境一般会接入 **APM 监控** ，通过接口耗时、DB 调用耗时，快速定位是哪段 SQL 拖慢了接口。另外我也会关注监控指标，比如 QPS、响应时间、P95/P99 延迟、数据库连接数、锁等待等，这些都能辅助判断是否存在 SQL 性能问题。高并发场景下，我还会结合 **CPU、磁盘 IO、Buffer Pool 命中率** ，判断是不是 SQL 导致的瓶颈。

第二步是 **定位慢 SQL 问题** 。

我主要做三件事：

第一，用 **EXPLAIN** 查看执行计划，重点看是否走索引、扫描行数、是否全表扫描、有没有临时表、是否出现 filesort。

第二，检查 **索引是否合理** ，比如联合索引是否符合最左匹配，有没有因为函数操作、隐式类型转换导致索引失效。

第三，分析 **锁与事务** ，如果 SQL 本身不慢但经常阻塞，就要看是不是行锁、间隙锁竞争，或者长事务导致的等待。

第三步是 **优化** 。

我会从四个层面入手：

首先是 **索引优化** ，建立合适的联合索引，删除冗余、无效索引，大部分慢 SQL 都能通过索引解决。

其次是 **SQL 本身优化** ，比如避免 select \*，减少返回字段；把子查询优化为 join；避免在 where 条件里对字段做函数操作等。

然后是 **数据层优化** ，大表考虑分库分表、冷热数据分离，减少单表压力。

最后是 **架构层优化** ，比如增加 Redis 缓存热点数据，做读写分离，把查询压力分散到从库，降低主库负担。

我理解慢 SQL 优化不是一次性改完就结束，而是一个 **闭环** ：

先监控发现问题，再分析执行计划，优化后验证效果，最后持续观察指标，保证稳定。

**十三、为什么 MySQL 采用 B+ 树作为索引？ \<SQL 629\>**

MySQL InnoDB 选择 B+ 树作为索引结构，核心是适配它的底层存储特性 ——InnoDB 是以 16KB 的页为单位做磁盘 IO 的，所以查询性能的瓶颈根本不在 CPU 计算，而在磁盘 IO 的次数，这也是索引选型的核心前提。

第一点，B+ 树能大幅减少磁盘 IO 次数。因为 B+ 树是多叉平衡树，单个节点可以存储大量的 key，树高极低，哪怕是千万级的数据，树高通常也只有 2~4 层，这意味着一次查询最多只需要 2~4 次磁盘 IO；但如果用红黑树这种二叉结构，树高会急剧增加，磁盘 IO 次数也会跟着大幅上升，性能会差很多。

第二点，B+ 树极致适配范围查询和排序场景。B+ 树的所有数据都集中在叶子节点，而且叶子节点之间是通过有序双向链表连接的，像 between 范围查询、order by 排序、like 前缀匹配这些常见场景，都能直接顺序遍历叶子节点，效率极高；反观 Hash 索引，只能支持等值查询，既不支持范围查询和排序，也不支持联合索引的最左匹配，根本满足不了通用的查询需求。

第三点，B+ 树完美匹配 InnoDB 聚簇索引的特性。InnoDB 是聚簇索引架构，表的实际数据本身就存在 B+ 树的叶子节点里，这种架构要求索引必须是有序的，并且支持范围扫描，而 B+ 树的特性刚好和这个设计需求天然契合。

**十四、从「敲下一个 URL」到「页面出现在屏幕」整条链路全景 \<HTTP/HTTPS 628\>**

用户在浏览器敲下 URL 之后，浏览器首先做 **URL 解析** ，拆出协议、域名、端口和路径，这是链路的起点。

第一步是 **DNS 解析** ，把域名解析成目标服务器 IP：浏览器会依次查询浏览器缓存、系统缓存 /hosts 文件，若未命中，本地 DNS 服务器会通过 **递归查询** ，向根服务器、顶级域服务器、权威服务器做 **迭代查询** ，最终拿到 IP 并做本地缓存。

接下来 **建立网络连接** ：

若是 HTTP 协议，直接通过 **TCP 三次握手** 建立可靠连接，同时协商 MSS 和滑动窗口；

若是 HTTPS 协议，在 TCP 三次握手后，额外进行 **TLS 握手** ，完成证书校验、加密算法协商、对称密钥生成，保证数据传输安全。

连接建立后，浏览器构造 **HTTP 请求报文** （包含请求行、请求头、请求体），请求经公网到达服务端的 **负载均衡层** （如 Nginx）：Nginx 会做 TLS 终止、反向代理、负载均衡，将请求转发到后端可用的应用服务。

**后端应用服务** 处理请求：先经过中间件完成鉴权、日志、限流，再进入业务逻辑；业务层会优先查询 **缓存（如 Redis）** ，缓存未命中再访问 **数据库（如 MySQL）** ，最终将数据组装成 JSON 或渲染为 HTML，通过 HTTP 响应返回。

浏览器收到响应后，解析数据并展示页面

最后，请求完成后，TCP 通过 **四次挥手** 断开连接；若请求失败，会根据 HTTP 状态码做相应处理，TCP 层会触发重传机制保证数据可靠性。

**一句话总结** ：URL → DNS 解析 → TCP/TLS 连接 → 负载均衡 → 应用服务（中间件 + 业务 + 缓存 / 数据库） → HTTP 响应 → 浏览器解析渲染 → 页面展示。

**十五、说说Redis的持久化策略 \<Redis 611\>**

Redis 的持久化主要是 RDB 和 AOF，两者解决的是不同侧重点的问题。线上一般用混合模式。

RDB 本质是做某一时刻的全量快照。Redis 会 fork 子进程，利用写时复制把内存数据写到 dump 文件里，主线程基本不受影响。它的优点是文件小、加载快，适合做全量备份和灾备恢复。但缺点也很明显，是有时间窗口的，比如 5 分钟一次快照，中间宕机会丢数据，所以更偏冷备。

AOF 是把每条写命令追加到日志里，恢复时重放命令。它有三种刷盘策略，线上一般用 everysec，性能和安全性比较平衡，理论上最多丢 1 秒数据。相比 RDB，它更安全，但文件会变大，恢复速度也慢一些，所以需要通过 AOF rewrite 做日志压缩。

现在生产上常见的是混合持久化。启动时先用 RDB 快速恢复大部分数据，再回放少量 AOF 增量日志，既保证恢复速度，又降低数据丢失风险。

总结一下：

RDB 偏性能和恢复速度，AOF 偏数据安全，混合模式是两者的折中，也是生产环境的主流方案。

**十六、事务隔离级别有哪些？ \< 数据库锁 / 日志 607\>**

事务的四大隔离级别，主要是为了解决并发事务下的数据不一致问题。

**读未提交** 是最低级别，允许事务读到其他事务未提交的数据，会出现 **脏读** ，基本不会使用。

**读已提交** 只能读到已提交的数据，避免了脏读，但同一个事务内多次查询结果可能不一样，存在 **不可重复读** ，这是很多公司数据库的默认隔离级别。

**可重复读** 能保证同一事务内多次读取结果一致，解决了不可重复读；虽然理论上会有幻读，但 MySQL InnoDB 通过 MVCC 结合间隙锁，实际上已经解决了幻读，这也是 MySQL 的默认级别。

**串行化** 是最高级别，事务串行执行，彻底避免了所有并发问题，但并发性能最差，只用于对一致性要求极高的场景。

整体来说，隔离级别越高，一致性越强，但并发性能越低，线上业务通常使用 **可重复读** 或 **读已提交** 。

**脏读: 读到了别人未提交的数据，会回滚失效。**

**不可重复读: 同一事务内，同一行数据被修改，前后结果不一致。**

**幻读: 同一事务内，结果集行数变多 / 变少**

**十七、说说你了解的JVM内存模型 \<JVM 593\>**

JMM 即 Java 内存模型，用来解决 **多线程并发下共享变量的一致性问题** 。

它定义了 **主内存** 和 **工作内存** ：所有共享变量都存在主内存，每个线程有自己独立的工作内存；线程只能操作工作内存中的变量副本，不能直接访问其他线程的工作内存。

JMM 主要保证 **可见性、原子性、有序性** 三大特性，通过 volatile 保证可见性与有序性，synchronized 保证原子性与可见性，并通过 happens-before 规则规范指令执行顺序。简单说，JMM 是一套 **线程与主内存交互的规范** ，用来保证多线程程序运行正确。

**十八、如何评估 / 判断索引是否生效？常见索引失效场景有哪些？ \<SQL 578\>**

**一、判断索引是否生效的核心方法**

最直接且常用的是执行 EXPLAIN 查看执行计划，重点关注 4 个核心字段：

**type** ：如果是 all 代表全表扫描，索引未生效； ref、range、const 则说明索引命中；

**key** ：是否显示预期要走的索引名，为空则未命中；

**rows** ：预估扫描行数是否合理，行数接近全表则索引未有效利用；

**extra** ：若出现 using filesort、using temporary 等，说明索引没起作用，反之 using index 是覆盖索引，效果最优。

此外，也会结合慢查询日志、实际执行时间和扫描行数综合验证。

**二、索引失效的常见场景（核心是破坏有序性 / 最左匹配，或优化器评估不划算）**

**违背最左前缀原则** ：联合索引如 (a,b,c)，仅用 b/c 查询，或跳过 a 直接查 b+c，索引完全失效；

**索引列做函数 / 运算** ：比如 year(create_time)=2024 、 id+1=10 ，索引存的是原始值，运算后无法匹配；

**隐式类型转换** ：如 int 类型的 id 用 id='123' 查询，类型转换导致索引失效；

**特殊运算符 / 模糊匹配** ： !=、\<\>、not in 或 like '%xx' 前导模糊匹配，破坏 B+ 树有序性，无法走索引；

**数据选择性差** ：比如性别字段只有 2 个值，优化器会认为全表扫描比走索引更快；

**范围查询阻断后续列** ：联合索引中，范围条件（如 b\>5 ）后的字段（如 c）无法走索引，比如 a=1 and b\>5 and c=10 ，c 会失效。

**十九、说说 TCP 的三次握手 \<TCP/UDP 571\>**

TCP 三次握手的核心目的，是在客户端和服务端之间建立 **可靠的全双工连接** ，并确认双方的 **发送和接收能力都正常** ，同时同步初始序列号。

过程分为三步：

第一步，客户端发送 **SYN** 报文，携带自己的初始序列号 seq=x，发起连接请求。

第二步，服务端回复 **SYN+ACK** ，确认客户端的序号 ack=x+1，并携带自己的初始序列号 seq=y，表示同意建立连接。

第三步，客户端再回复 **ACK** 报文，确认服务端的序号 ack=y+1。

至此，双方都确认收发正常，连接正式建立。

为什么必须是三次，而不是两次？

如果只有两次握手，网络中延迟的 **历史重复连接报文** 可能会让服务端误建无效连接，浪费资源。第三次握手就是让客户端再次确认连接有效性，避免这种问题。

**二十、HTTP vs. HTTPS 有什么区别? \<HTTP/HTTPS 567\>**

面试官您好，HTTP 和 HTTPS 最核心的区别是： **HTTP 明文传输，HTTPS 是 HTTP 加了一层 TLS 加密** 。

主要有三点差异：

第一， **安全性不同** 。HTTP 是明文传输，容易被窃听、篡改和冒充；HTTPS 通过 TLS 加密保证数据机密性与完整性，并用证书验证服务器身份，能有效防范中间人攻击。

第二， **连接过程不同** 。HTTP 直接通过 TCP 三次握手建立连接；HTTPS 要在 TCP 之后再进行一次 TLS 握手，完成证书校验、加密算法协商和对称密钥协商，首次连接会稍多一点开销。

第三， **端口与性能不同** 。HTTP 默认 80 端口，HTTPS 默认 443 端口；早期 HTTPS 加解密开销较大，现在经过硬件加速和 TLS 1.3 优化，性能损耗已经很小。

另外，现代浏览器会把 HTTP 标记为 “不安全”，像 HTTP/2、Service Worker 等新特性也都要求必须使用 HTTPS。

**二十一、SQL 调优常见方法有哪些？ \<SQL 509\>**

面试官您好，我梳理的 SQL 调优思路主要分四层，由浅入深、从低成本到高成本逐步优化：

第一层是 **分析执行计划** ，这是调优的起点。核心用 EXPLAIN 查看四个关键：是否全表扫描、是否命中预期索引、预估扫描行数是否合理、是否出现 filesort 或临时表，通过执行计划快速定位性能瓶颈。

第二层是 **索引优化** ，这是解决慢 SQL 最核心的手段。比如建匹配查询场景的单列 / 联合索引、严格遵守最左前缀原则、给高选择性字段建索引（避免性别这类低区分度字段）、尽量用覆盖索引减少回表，大部分慢 SQL 都是索引未命中或设计不合理导致的。

第三层是 **SQL 写法优化** ，属于低成本改法。比如避免 select \*、不在索引列做函数 / 运算、杜绝隐式类型转换、用小表驱动大表、优化深分页（比如延迟关联）、大数据量下用 exists 替代 in 等，这些细节能显著降低执行开销。

第四层是 **架构与数据层优化** ，针对数据量极大的场景。比如用 Redis 缓存热点数据、做读写分离分散查询压力、分库分表拆分大表、归档历史数据减少单表数据量，以及更新统计信息让优化器生成更优执行计划。

**二十三、什么是索引？索引有哪些分类？ \<SQL 449\>**

索引本质上就是数据库里的“目录结构”。 它通过维护一套有序的数据结构，帮助我们快速定位数据的物理位置，从而避免全表扫描。

核心价值是 **减少扫描行数、降低 IO** 。 但代价是写操作会变慢，因为插入、更新、删除都需要维护索引结构。

索引常见可以从三个维度去理解。

第一，从数据结构上看，这是最核心的。

MySQL 默认是 B+ 树索引。它的特点是有序、数据都在叶子节点，支持等值查询、范围查询和排序，是最通用的结构。

哈希索引是基于哈希表实现的，等值查询非常快，但不支持范围和排序，所以适用场景有限。

第二，从物理存储结构上看。

在 InnoDB 里，主键索引是聚簇索引，叶子节点直接存整行数据，一张表只能有一个。

其他普通索引和联合索引属于二级索引，叶子节点存的是主键值，查询时通常需要回表。 如果查询字段刚好都在索引里，就能形成覆盖索引，避免回表。

第三，从逻辑功能上看。

有普通索引、唯一索引、主键索引、联合索引。

联合索引是多个字段组合而成，使用时必须遵守最左前缀原则。

**二十四、讲一下乐观锁和悲观锁 \<Java 多线程 429\>**

面试官您好，乐观锁和悲观锁的核心区别，是 **对并发冲突的预设态度不同** ：

首先是悲观锁，它假设 “一定会有冲突”，所以操作数据前先加锁，阻塞其他线程。比如数据库里的 select ... for update 会加行锁，其他事务必须等锁释放才能操作。优点是实现简单、数据强一致；缺点是并发性能差，易阻塞甚至死锁，适合写多、冲突概率高的场景。

然后是乐观锁，它假设 “大概率无冲突”，不提前加锁，只在更新时做冲突检测。常见两种实现：一是版本号机制，更新时带 version 条件，没匹配到就重试；二是 CAS 思想，对比旧值再更新。优点是并发性能好、无阻塞；缺点是冲突多的时候重试成本高，适合读多写少、冲突概率低的场景。

**二十五、消息队列如何保证消息不丢？ \< 分布式 420\>**

面试官您好，保证消息队列不丢消息，核心要覆盖 **生产端、Broker 端、消费端** 三个核心阶段，每个阶段都有对应的兜底策略：

第一，生产端防丢：不能 “发完即忘”，必须开启发送确认机制 —— 比如同步发送或开启 ACK，确保 Broker 接收并落盘后才返回成功；发送失败要加重试机制，极端场景下还能通过本地消息表做最终一致性兜底，保证消息必投递。

第二，Broker 端防丢：核心是 “持久化 + 高可用” 双保障。一方面消息要写入磁盘而非仅存内存，避免宕机丢失；另一方面开启主从复制、多副本同步，只有消息同步到从节点，才算真正持久化，杜绝单机故障导致的丢消息。

第三，消费端防丢：关键是关闭 offset 自动提交，遵循 “先消费处理业务，成功后再手动提交 offset” 的逻辑。如果业务处理失败，不提交 offset，消息可重新消费；同时要做业务幂等（比如用唯一业务 ID 去重），解决重复消费的问题。

**二十六、MySQL 中的 MVCC 是什么？Read View 在 MVCC 中如何工作？如果没有 MVCC 会怎样？ \< 数据库锁 / 日志 416\>**

面试官您好。

MVCC 是多版本并发控制，是 InnoDB 实现一致性读的核心机制，目的是 **在保证事务隔离的同时，让读写互不阻塞** 。

它主要依靠三个部分实现：

一是数据行的 **隐藏字段** ，记录创建和删除这条数据的事务 ID；

二是 **undo log** ，用来保存历史版本数据；

三是 **Read View** ，负责判断当前事务能看到哪个版本的数据。

当事务执行快照读时，会生成一个 Read View，它记录了 **当前系统里正在活跃、还没提交的事务** 。

可见性规则可以简单理解成：

当前事务开始前就已经提交的数据，可见；

事务开始之后才提交的数据，不可见；

还没提交的事务产生的数据，也不可见。

不同隔离级别，Read View 的生成时机不同：

**可重复读** ：事务第一次查询时生成，整个事务共用一份；

**读已提交** ：每次查询都会重新生成。

如果没有 MVCC，数据库就只能通过加读写锁保证一致性，会造成 **读写互相阻塞** ，系统并发能力会明显降低。

**二十七、设计一个支持万人同时抢购商品的秒杀系统，如何解决超卖、库存扣减和高并发请求问题 \< 系统设计题 412\>**

面试官您好。

万人秒杀系统核心解决三点：抗高并发、防止超卖、保证库存一致性。

整体思路是：限流削峰 + Redis 预扣 + MQ 异步 + 数据库兜底。

首先抗并发：

前端页面静态化 + CDN 缓存，接口层做限流。 真正的关键是把库存提前加载到 Redis，通过 Lua 脚本做原子扣减，让缓存承接瞬时高并发。

其次防止超卖：

我会做三层保障：

第一层 Redis 原子扣减库存，保证不会扣成负数； 第二层 扣减成功后写入 MQ 异步下单，削平流量峰值； 第三层 数据库更新时使用 where stock \> 0 或乐观锁做最终兜底。

第三是一致性问题：

由于 Redis 和数据库是异步的，会存在短暂不一致，所以：

MQ 要保证可靠投递

在极端高并发场景下，还可以：

本地内存标记售罄减少 Redis 压力

热点 Key 分片

分库分表扩展数据库写能力

总结一句话：

秒杀系统核心是用缓存扛流量，用消息队列削峰，用数据库兜底，通过多层保障实现高并发下的库存安全扣减。

**二十八、联合索引的存储结构与最左前缀原则 \< SQL 377 \>**

面试官您好。

联合索引本质上还是一棵 B+ 树，只是它的 key 不是单个字段，而是 **把多个字段按定义顺序拼起来的组合键** 。

比如我们建一个 (name, age) 的联合索引，这棵 B+ 树的排序规则是：

**先按 name 排序，name 相同再按 age 排序** ，整体就像字典序一样。

所以它的有序性是分层的：

第一维度是 name，第二维度是在 name 相同的前提下再按 age 排。

这一点，其实就是最左前缀原则的根本原因。

最左前缀原则，并不是 MySQL 随便定的规则，而是 **B+ 树只能从左到右按顺序匹配** 决定的。

像 where name = ? 或者 where name = ? and age = ? ，都能走索引，因为都是从最左边的 name 开始匹配。

但如果只查 where age = ? ，就用不上这个索引，因为整棵树是先按 name 排的，不知道 name，就没法定位 age 的位置，只能全表扫。

还有一个面试常考的点： **范围查询会打断后面字段的索引使用** 。

比如 name = '张三' and age \> 18 是可以走索引的；

但如果是 name \> '张三' and age = 18 ，age 就用不上索引了。

因为前面字段一旦用了范围，后面的字段就不再具备有序性，B+ 树没法继续精确匹配。

**二十九、Concurrent HashMap 线程安全的具体实现方式**

面试官您好。

Concurrent HashMap 的线程安全实现，核心是分 JDK 版本的 ——1.7 和 1.8 是两套完全不同的思路，如果是 **JDK 1.7** ，它采用的是 **分段锁（Segment）机制** ，现在面试里大家更关注 1.8 及之后的实现，我重点说这个版本。

它的核心设计思想特别好记： **读操作尽量无锁，写操作只锁最小范围** ，目的就是最大化并发效率。

先简单提下数据结构：底层还是数组 + 链表 / 红黑树，和 HashMap 基本一致，当链表长度超过 8 时会转红黑树，避免高冲突场景下查询效率降到 O (n)，这是基础。

接下来具体说线程安全的实现：

第一，读操作（get）为什么能做到无锁还安全？

因为 Concurrent HashMap 里 Node 节点的 value 和 next 指针都是用 volatile 修饰的，volatile 能保证内存可见性 —— 一个线程更新了值，其他线程立刻就能读到最新值。再加上节点插入时是通过 CAS 安全发布的，所以读操作完全不用加锁，这也是它并发性能高的关键。

第二，写操作（put）怎么保证线程安全？

这里分两种情况：

如果要写入的桶是空的，会先尝试用 CAS 把新节点放进去，CAS 成功就说明没竞争，直接写入完成；如果 CAS 失败，说明有其他线程在操作这个桶，再进入加锁逻辑。

如果桶已经有数据了，就对这个桶的 **头节点** 加 synchronized 锁 —— 注意，不是锁整个数组，只锁这一个桶！所以不同桶的写操作完全不冲突，并发度能拉满。

第三，扩容的处理也很有特点：

它不是单线程扩容，而是多线程协作完成的。通过 sizeCtl 这个控制变量标记扩容状态，多个线程可以一起迁移数据，避免了单线程扩容导致的长时间阻塞，进一步提升了并发效率。

补充一个常被问到的点：为什么 1.8 不用 1.7 的 Segment（分段锁），也不用 Reentrant Lock，反而用 synchronized？

因为 JDK 1.8 对 synchronized 做了大量优化（比如偏向锁、轻量级锁），性能已经和 Reentrant Lock 持平，甚至在低竞争场景下更好；而且 synchronized 是 JVM 层面的锁，管理成本更低，再加上我们只锁单个桶，锁粒度已经足够小，整体性价比最高。

最后总结一下：

JDK 1.8 的 Concurrent HashMap 就是靠 volatile 保证可见性、CAS 实现无锁写入、synchronized 锁单个桶，再配合红黑树优化高冲突场景，既保证了线程安全，又把并发效率做到了极致。核心就是：能不加锁就不加锁，必须加锁就只锁最小范围。

**三十、synchronized和Lock有什么区别？\<Java多线程 358\>**

面试官您好。

synchronized 和 Lock 都是解决多线程并发安全的，但核心区别在于： synchronized 是 JVM 层面的 “傻瓜式” 内置锁，简单安全； Lock 是 JDK 层面的显式锁，功能更强但需要手动控制。

我从几个核心维度说下它们的差异，这样会更清晰：

首先是 **实现层面** ：

synchronized 是 Java 关键字，属于 JVM 底层实现的锁，我们不用管底层细节；而 Lock 是一个接口（最常用的实现是 ReentrantLock），基于 AQS 框架实现，是纯 Java 代码层面的显式锁。简单说，一个是 “隐式锁”，一个是 “显式锁”。

然后是 **使用方式** ：

这是最直观的区别 —— synchronized 不用手动解锁，代码块执行完、哪怕抛异常，锁都会自动释放，用起来特别省心；但 Lock 必须手动调用 lock() 加锁，而且一定要在 finally 里调用 unlock() 解锁，一旦忘写，就可能导致死锁，使用成本更高。

接下来是 **功能特性** ，这也是面试最常问的核心：

synchronized 的功能比较单一，比如它不支持中断等待锁的线程，线程一旦等锁就只能死等；也不支持超时获取锁，更只能是非公平锁，而且只有一个隐式的条件队列来做线程通信。

但 Lock 不一样，它能支持可中断锁（ lockInterruptibly() ）、超时获取锁（ tryLock(timeout) ），还能手动设置公平锁，甚至可以创建多个 Condition 条件变量，精细化控制线程的等待和唤醒，功能灵活度差很多。

再说说 **性能** ：

很多人会觉得 Lock 一定比 synchronized 快，但其实 JDK 1.6 之后，synchronized 做了大量优化 —— 比如偏向锁、轻量级锁、自旋锁这些，低竞争场景下性能已经和 ReentrantLock 持平，甚至更好；只有在高竞争场景下，Lock 的可控性和扩展性才更有优势。

最后总结下 **适用场景** ：

如果只是简单的同步控制，比如普通的方法 / 代码块同步，优先用 synchronized，代码简洁还不容易出错；但如果业务需要可中断锁、超时控制、公平锁，或者多条件队列的线程通信，就必须用 ReentrantLock 这类 Lock 实现了。

简单来说，两者的选择核心是：简单场景选 synchronized 省成本，复杂并发控制选 Lock 提能力。

**三十一、说说volatile的用法及原理。**

面试官您好。

volatile 关键解决两个问题： **保证可见性** ，以及 **禁止指令重排序** 。但它不保证原子性。

我分三个点说。

第一，保证可见性。

在 Java 内存模型里，每个线程都有自己的工作内存，线程对变量的读写，可能只是在自己的缓存里操作，不一定立刻同步到主内存。

如果一个变量用 volatile 修饰，那么：

一个线程对它的写操作，会立刻刷新到主内存

其他线程每次读取时，都会从主内存拿最新值

所以它非常适合做“状态标志位”，比如线程停止标志、开关控制等场景。

第二，禁止指令重排序。

这是面试里经常会问到的点，比如双重检查单例为什么必须加 volatile。

对象创建在底层大概分三步：

分配内存

初始化对象

把引用赋值给变量

如果发生重排序，2 和 3 可能交换顺序，导致别的线程拿到一个“还没初始化完成”的对象。

volatile 会在读写前后插入内存屏障，禁止这种重排序，保证执行顺序对其他线程可见。

第三，它不能保证原子性。

比如 count++ 是读、改、写三个步骤，即使用 volatile 修饰，也可能在多线程下丢数据。

如果涉及复合操作，就必须用 synchronized、Lock 或原子类。

总结一句话：

volatile 适合解决“可见性”和“有序性”问题，但不解决“原子性”问题。

**三十二、说说线程的创建方式**

面试官您好。

线程的创建方式我一般分成两类来说： **直接创建线程** 和 **通过线程池创建线程** 。实际开发中，重点其实是线程池。

**第一类：直接创建线程（基础方式）**

第一种是继承 Thread 类，重写 run() 方法，然后调用 start() 。

这种方式最简单，但线程和任务耦合在一起，而且 Java 是单继承，扩展性不好，所以现在基本很少用。

第二种是实现 Runnable 接口。

这是更常见的方式，把任务逻辑和线程本身解耦。 不过它没有返回值，也不能直接抛出受检异常。

第三种是实现 Callable 接口，配合 Future 或 FutureTask 使用。

这种方式可以：

有返回值

抛出异常

通过 Future.get() 获取执行结果

这是对 Runnable 的增强版本。

**第二类：线程池方式（生产环境主流）**

在实际项目中，基本不会手动 new Thread ，而是通过线程池来创建线程，比如使用 ExecutorService 。

原因很简单：

线程创建和销毁成本高

线程池可以复用线程

可以控制最大并发数

可以统一管理任务队列和拒绝策略

线程池底层核心实现是 ThreadPoolExecutor 。

**三十三、建索引时需注意哪些事项？**

面试官您好。

建索引其实不是越多越好，而是要围绕“查询场景”和“写入成本”去权衡。我一般从几个核心点来说。

第一，索引要建在“真正高频使用”的字段上。

优先考虑：

where 条件中经常出现的字段

join 关联字段

排序、分组字段

同时要看字段的区分度。区分度越高，过滤效果越好。

像性别这种只有两个值的字段，即使建了索引，优化器也可能不用。

第二，控制索引数量。

索引本质是空间换时间。 每多一个索引，插入、更新、删除时都要额外维护一次 B+ 树。

在写多读少的业务里，索引过多反而会拖慢整体性能。

第三，联合索引要按查询条件设计。

联合索引要遵循最左前缀原则，所以字段顺序很关键。

一般会把：

过滤性强、区分度高的字段放前面

等值查询字段放在范围查询字段前面

否则可能导致后面的字段用不上索引。

第四，避免索引失效。

比如：

在索引列上做函数计算

隐式类型转换

前缀模糊查询 like '%xxx'

在联合索引中，范围查询之后的字段无法继续利用索引

所以建索引前一定要结合实际 SQL 来分析，而不是凭感觉加。

第五，考虑覆盖索引。

如果查询的字段都在索引里，就可以避免回表，提高性能。 有时候为了避免回表，可以适当做索引优化设计。

第六，主键设计要合理。

在 InnoDB 中主键是聚簇索引，建议使用自增、尽量短的主键。 如果主键是随机字符串，会导致页分裂频繁，影响写性能。

**三十四、Redis中的Zset怎么实现的?**

面试官您好。

Redis 的 Zset（有序集合）核心诉求很明确：既要能快速根据元素（member）查分值（score），又要能按分值排序、做范围查询。为了同时满足这两个需求，它底层不是单一结构，而是 **哈希表 + 跳表** 的组合，我拆开来讲会更清楚：

首先说哈希表（dict）的作用：

它就是存 member → score 的映射关系，相当于给每个元素做了个 “快速索引”。比如我们执行 ZSCORE key member 查某个元素的分值，或者用 ZISMEMBER 判断元素是否存在时，哈希表能保证 O (1) 的查询效率，这是单靠有序结构做不到的。

然后是跳表（skiplist），这是支撑 Zset “有序” 特性的核心：

跳表可以理解成 “多层有序链表”—— 底层是完整的有序链表，上层是层层精简的 “索引层”，查找时不用从头遍历，而是从高层索引快速跳跃，平均时间复杂度能到 O (log n)。它主要解决两个问题：一是让整个集合按 score 有序排列；二是支持各种范围 / 排名查询，比如 ZRANGEBYSCORE （按分值范围查）、 ZRANGE （按排名查），这些操作靠跳表实现会非常高效。

所以这两套结构是 “并行维护” 的：

查单个元素的分值、判断元素是否存在，靠哈希表；要排序、做范围 / 排名查询，就靠跳表。插入或删除元素时，Redis 会同时更新哈希表和跳表，保证数据一致性。

这里有个常被问到的点：为什么选跳表而不是红黑树？

理论上红黑树也能做到 O (log n) 的查找和排序，但从工程实现角度，跳表的优势很明显：

一是代码实现比红黑树简单太多，逻辑更清晰，维护成本低；

二是跳表做范围查询更自然 —— 比如要查分值在 10-100 之间的元素，跳表可以快速定位到 10 的位置，然后顺着底层链表遍历到 100 即可，而红黑树做范围查询需要额外的遍历逻辑，效率和代码复杂度都不占优

所以 Redis 最终选了跳表。

还有个容易被忽略的内存优化细节：

Redis 不会一上来就用 “哈希表 + 跳表” 这种相对占内存的结构。当 Zset 里的元素数量少、且 member/score 的长度都比较小时，它会先用 listpack 这种紧凑结构来节省内存；只有当元素数量或长度超过阈值（比如元素数超过 128 个），才会升级成哈希表 + 跳表的组合结构，这也是 Redis 做内存优化的一个典型思路

**三十五、TCP 协议如何保证可靠传输？**

面试官您好。

TCP 能保证可靠传输，本质上是通过一整套机制配合实现的。我一般会从 **“不丢、不乱、不重、不快”** 四个角度来讲。

第一，保证数据不丢 —— 确认应答 + 重传机制。

TCP 发送数据后，接收方必须返回 ACK 确认。 如果发送方在一定时间内没有收到 ACK，就会触发 **超时重传** 。

另外还有 **快速重传** ：如果连续收到 3 个重复 ACK，说明中间某段数据丢了，会立即重传，而不等超时。

通过 ACK + 重传机制，TCP 能保证数据最终一定送达。

第二，保证数据有序 —— 序列号机制。

TCP 是面向字节流的，每个字节都有序列号。 即使网络中出现乱序到达，接收方也会根据序列号重新排序后再交给应用层。

如果某个序列号缺失，就会等待或触发重传。

第三，保证数据不重复 —— 序列号去重。

如果某段数据因为网络问题被重复发送，接收方会根据序列号识别重复数据并丢弃。

第四，保证不会压垮接收方 —— 流量控制。

TCP 使用滑动窗口机制。 接收方会告诉发送方自己的“接收窗口大小”，发送方根据这个窗口来控制发送速率。

如果接收方处理不过来，窗口变小，发送方会减慢速度。

第五，保证不会压垮网络 —— 拥塞控制。

TCP 还会根据网络状况动态调整发送速率。

包括：

慢启动

拥塞避免

快重传

快恢复

当发生丢包时，TCP 会认为网络拥塞，从而主动降低发送速度。

**三十六、分布式锁的原理和常见的实现有哪些？**

面试官您好。

分布式锁的核心诉求特别明确：把单机环境下的 “互斥” 能力扩展到多机器的分布式系统中，保证同一时间只有一个节点能执行临界代码。它的本质不是 “锁本身”，而是 **靠一个共享存储来记录锁状态，再通过原子操作控制这个状态** ，我从原理、实现方式和核心要求三个方面说，会更清晰：

首先说分布式锁的基本原理：

不管用什么技术实现，核心都是找一个 “所有节点都能访问的共享存储”（比如 Redis、数据库、Zookeeper），流程就三步：尝试加锁（往共享存储里写一个唯一标识）→ 执行业务逻辑 → 释放锁（删掉这个标识）。

这里有三个绝对不能少的关键点：一是加锁必须是原子操作，否则多节点同时加锁会失效；二是一定要给锁设过期时间，防止节点宕机导致死锁；三是释放锁时要校验身份（比如用唯一 value 匹配），避免误删其他节点的锁。简单说，分布式锁的核心就是 “用原子操作管控共享资源的访问权”。

然后说最常见的三种实现方式，各有适配场景：

第一种是基于数据库：核心是利用唯一索引 —— 插入一条唯一记录当锁，插入成功就是拿到锁，删除记录就是释放锁。优点是实现特别简单，强一致性也够；但缺点很明显，数据库性能扛不住高并发，而且锁的超时、重试这些逻辑要自己写，适合并发量低的场景。

第二种是基于 Redis（现在最主流的方式）：

加锁用的是 SET key value NX PX 过期时间 这个命令 ——NX 表示 “只有 key 不存在时才设置”，保证互斥；PX 是设置毫秒级过期时间，防死锁；value 要设成节点 + 线程的唯一标识（比如 UUID），为了后续释放锁时校验。

释放锁不能直接 DEL，必须用 Lua 脚本先判断 value 是否匹配，再删除，这一步也是为了保证原子性，避免误删。

这种方式的优点是性能极高、实现简单，适配高并发；但有个小问题 ——Redis 主从切换时可能丢锁（比如主节点加锁后还没同步给从节点就宕机），所以强一致性不如 Zookeeper。

第三种是基于 Zookeeper：

靠临时顺序节点实现 —— 所有客户端都去创建同一个前缀的临时顺序节点，序号最小的那个客户端拿到锁；没拿到锁的客户端，就监听前一个序号的节点，等它释放（比如节点删除）再抢锁。

优点是强一致性极好，而且临时节点的特性是 “客户端宕机就自动删除”，天然防死锁；但缺点是性能比 Redis 低，而且 Zookeeper 本身需要集群运维，成本更高。

最后补充一个关键点：一个合格的分布式锁必须满足四个条件 —— 互斥性（核心）、防死锁（过期 / 临时节点）、不误删（身份校验）、高可用（共享存储要集群）。

**面试官：能说说你对 AOP 的理解吗？**

好的。AOP 的全称是面向切面编程，是对面向对象编程（OOP）的补充。

通俗来讲：传统面向对象编程中，若要给多个方法添加日志记录、权限校验、事务管理等通用功能，需在每个方法中重复编写相同代码，导致代码冗余且维护成本高。而 AOP 的核心思想是将这些通用功能抽取为 **切面** ，通过配置让切面自动 “织入” 到目标方法的执行流程中，实现业务逻辑与通用功能的解耦。

举个例子：做蛋糕时，蛋糕本身是核心业务，涂奶油、撒糖粉等装饰步骤就是切面。无需把装饰步骤写进每个蛋糕的配方，而是做好蛋糕后统一完成装饰，这和 AOP 抽离通用逻辑、统一织入的思路一致。

**面试官：那你们项目中是怎么使用 AOP 的？**

我们项目主要在三个场景应用了 AOP 思想：

**JWT 令牌验证拦截器**

项目中的 JWTInterceptor 类实现了 HandlerInterceptor 接口，在第 45 行的 preHandle 方法中，会在请求到达控制器前校验请求头中的 Authorization 令牌有效性：先获取令牌并解析出用户 ID，再查询 Redis 验证令牌是否匹配，匹配则放行，不匹配返回 401 未授权。

该拦截器在 WebConfig 第 16 行注册，拦截所有路径；同时第 23-42 行定义了白名单，注册、登录等接口无需令牌校验可直接放行。

这是典型的 AOP 应用：将权限校验逻辑从业务代码中抽离，统一在拦截器中处理，所有控制器方法无需重复编写校验代码。

**全局异常处理**

GlobalExceptionHandler 类中第 21 行的 @RestControllerAdvice 注解本质基于 AOP 实现：

第 25 行用 @ExceptionHandler 标注方法，专门处理 BusinessException 业务异常；

第 31 行处理 RuntimeException 运行时异常；

第 36 行处理参数校验异常。

优势在于：Service 或 Controller 层抛出异常后，无需在每个地方写try-catch，Spring 会自动拦截异常，交由对应方法统一处理并返回标准化错误响应。

**事务管理**

多个 Service 实现类中都用到了 @Transactional 注解（如 VideoServiceImpl 第 89 行、336 行， UserServiceImpl 第 136 行， FollowServiceImpl 第 49 行、87 行），该注解同样基于 AOP 实现：Spring 会在方法执行前开启事务，执行成功则提交，抛出异常则回滚，无需手动编写事务开启、提交、回滚的代码。

**面试官：AOP 的实现原理是什么？**

AOP 底层核心是 **动态代理** ，Spring 支持两种动态代理方式：

**JDK 动态代理** ：若目标对象实现了接口，Spring 会通过 JDK 自带的 Proxy 类创建代理对象。代理对象实现与目标对象相同的接口，调用接口方法时，会先执行切面逻辑，再调用目标对象的真实方法。

**CGLIB 动态代理** ：若目标对象未实现接口，Spring 会通过 CGLIB 库创建代理对象 —— 通过继承目标类、重写方法的方式实现代理。

具体执行流程：调用被 AOP 增强的方法时，实际调用的是代理对象的方法。代理对象会按配置的切面顺序，先执行前置通知，再执行目标方法，接着执行后置通知；若出现异常则执行异常通知，最后执行最终通知。

以项目中的拦截器为例：虽未通过 @Aspect 注解实现，但原理类似 —— 请求进入时，Spring 先调用拦截器的 preHandle 方法（相当于前置通知），返回 true 则继续执行控制器方法，返回 false 则中断请求。

**面试官：AOP 有哪些应用场景？**

AOP 的应用场景十分广泛，核心适用于处理横切多个模块的通用功能，主要包括：

**日志记录** ：方法执行前后自动记录日志（方法名、参数、返回值、执行时间等），无需在每个方法中重复编写日志代码；

**权限校验** ：如项目中的 JWT 拦截器，统一验证用户身份和权限，避免接口级别的重复校验；

**事务管理** ：通过 @Transactional 注解自动管理事务的开启、提交、回滚，保证数据一致性；

**性能监控** ：方法执行前后记录时间戳，计算执行耗时，定位性能瓶颈；

**异常处理** ：如全局异常处理器，统一捕获和处理异常，返回友好的错误信息；

**缓存管理** ：方法执行前先查询缓存，有缓存则直接返回，无缓存则执行方法并将结果存入缓存；

**参数校验** ：方法执行前自动校验参数合法性，不合法则直接返回错误，无需进入业务逻辑。

总的来说，AOP 让代码更简洁、易维护，符合单一职责原则 —— 业务代码专注于核心逻辑，技术性通用功能交由切面统一处理。

**三十八、Spring容器启动流程**

**一、整体启动流程（两大阶段）**

Spring Boot 启动分为两个核心阶段：

**new SpringApplication()** **阶段** ：完成启动前的准备与配置。

**run()** **阶段** ：执行实际的启动逻辑，加载上下文并启动服务。

**二、 new SpringApplication() 阶段（初始化配置）**

这个阶段主要是为后续的 run() 方法做准备，核心步骤如下：

推断应用类型

根据 classpath 下的依赖（如 spring-boot-starter-web ），自动判断是 Web 应用（Servlet/Reactive）还是普通应用。

设置初始化器

加载并注册所有 ApplicationContextInitializer ，用于在上下文刷新前进行初始化。

设置启动监听器

加载并注册所有 SpringApplicationRunListener ，用于监听启动过程中的各个事件。

确定主应用类

查找并确定包含 main() 方法的主类，作为应用的入口。

**三、 run() 阶段（核心启动）**

这是启动的核心流程，按顺序执行以下步骤：

准备环境

加载并配置 Environment ，包括配置文件（ application.properties/yml ）、命令行参数、系统属性等。

创建 ApplicationContext

根据应用类型，创建对应的 ApplicationContext （如 AnnotationConfigServletWebServerApplicationContext ）。

刷新 ApplicationContext

这是 Spring 容器的核心步骤，完成 Bean 的扫描、创建、依赖注入和初始化。

启动嵌入式 Web 服务器

如果是 Web 应用，会启动内置的 Tomcat、Jetty 或 Undertow 服务器。

发布 started 事件

通知所有监听器，应用已启动。

执行 callRunners

调用所有实现了 CommandLineRunner 和 ApplicationRunner 接口的 Bean，执行启动后的自定义逻辑。

发布 ready 事件

通知所有监听器，应用已准备就绪，可以接收请求。

**三十九、 IoC理解**

**一、核心定义**

IoC（控制反转）是一种设计思想，核心是将对象的创建、依赖管理的控制权，从程序员手写代码转移到 IoC 容器（如 Spring 容器），由容器统一管理，实现对象解耦。

**二、解决的核心问题**

消除代码紧耦合：无需手动 new 依赖对象，修改依赖实现时不用改动业务代码；

简化开发：容器自动完成对象创建、注入、生命周期管理，减少重复代码；

提高扩展性：新增依赖实现只需配置，无需修改核心业务逻辑。

**三、实现方式**

Spring 中 IoC 主要通过 **DI（依赖注入）** 实现，常见注入方式：

构造器注入（推荐，保证依赖不可变）；

Setter 注入（灵活，支持可选依赖）；

注解注入（如 @Autowired ，简化配置）。

**四、生活化举例**

比如开发订单服务时，订单服务依赖支付服务：

无 IoC：手动 new 支付宝支付对象 ，改微信支付要改代码；

有 IoC：只需告诉容器 “订单服务需要支付服务”，容器自动注入指定的支付实现，改实现只需改配置

**面试官：能讲讲 Spring 中的 Bean 循环依赖问题吗？**

好的。Bean 循环依赖指的是 Spring 容器中两个或多个 Bean 互相持有对方的引用，形成依赖闭环。比如 A 依赖 B，B 又依赖 A，就会产生循环依赖。

结合我们项目的实际代码来看：视频服务实现类 VideoServiceImpl 中，第 49 行注入了 UserService 、第 86 行注入了 FollowService ； UserServiceImpl 的第 82 行又注入了 FollowService ；而 FollowServiceImpl 的第 41 行又注入了 UserService 。如果此时 UserService 再依赖 VideoService ，就会形成完整的依赖循环。

**面试官：那 Spring 是怎么解决这个问题的？**

Spring 主要通过 **三级缓存机制** 解决循环依赖问题，我用通俗的方式解释：

第一级缓存（单例池 singletonObjects ）：存放完全初始化完成、可直接使用的 Bean；

第二级缓存（早期 Bean 缓存 earlySingletonObjects ）：存放已实例化但未完成属性注入的 Bean 对象；

第三级缓存（对象工厂缓存 singletonFactories ）：存放用于生成早期 Bean 实例的对象工厂。

具体执行流程（以 A 依赖 B、B 依赖 A 为例）：

Spring 先创建 A 的实例（仅完成实例化，属性未注入），并将这个 “半成品” A 放入三级缓存；

开始为 A 注入属性，发现需要依赖 B，于是转而创建 B；

创建 B 的实例（同样仅实例化），放入三级缓存；

为 B 注入属性时，发现需要依赖 A，此时 Spring 从缓存中取出半成品 A 注入给 B；

B 拿到 A 的引用后完成初始化，成为完整 Bean；

B 返回给 A 完成属性注入，最终 A 也完成初始化。

**面试官：你刚才提到项目中用了 @Lazy 注解，这个是做什么的？**

是的，我们项目里有多处用到 @Lazy 注解：比如 VideoServiceImpl 中第 65 行、70 行、74 行、78 行，注入 BulletService 、 LikeService 、 FavoriteService 、 CoinService 时都加了该注解； UserServiceImpl 的第 82 行注入 FollowService 时也用到了。

@Lazy 注解的核心作用是 **延迟加载** ：加了该注解后，Spring 不会在容器启动时立即注入真实的 Bean 实例，而是注入一个代理对象，直到第一次真正调用该 Bean 的方法时，才会去获取并初始化真实 Bean。

这样做有两个核心好处：

避免循环依赖：延迟注入打破了即时依赖的链条，通过代理对象规避了循环依赖导致的启动失败；

提升启动速度：对于初始化耗时、非必用的 Bean，延迟加载能减少容器启动时的初始化工作量，加快应用启动。

我们项目中给这些服务加 @Lazy ，正是因为 VideoService 和点赞、收藏、投币等服务间可能存在潜在的相互依赖，以此避免循环依赖引发的启动问题。

**面试官：那是不是所有循环依赖 Spring 都能解决？**

并不是。Spring 的三级缓存仅能解决 **单例 Bean 的 setter 注入** 方式的循环依赖，以下几种情况无法解决：

构造器注入的循环依赖：构造器注入要求实例化时就传入依赖，此时 Bean 还未实例化，没有半成品对象可缓存，因此无法解决；

原型（prototype）作用域的 Bean：原型 Bean 每次获取都会创建新实例，Spring 不会缓存这类 Bean，无法通过缓存打破依赖闭环；

多例 Bean 之间的循环依赖：原理与原型作用域一致，无缓存机制支撑，无法解决。

因此实际开发中，解决循环依赖的最优方案是 **优化代码设计，从根源避免循环依赖** ，常用手段包括：

像项目中这样使用 @Lazy 延迟加载；

重构代码，将公共逻辑抽取到第三方类中，解耦相互依赖的 Bean；

使用事件机制（如 Spring 事件）替代直接依赖，实现解耦；

改用 setter 注入（而非构造器注入），适配 Spring 的缓存解决机制。

这样既能保证代码质量，也能从根本上规避循环依赖带来的潜在问题。
