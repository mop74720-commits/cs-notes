    网络模型

    TCP/IP 四层模型

    应用层 :提供应用程序与网络通信的接口，负责数据的编码、解码和表示。

    HTTP/HTTPS （超文本传输协议） FTP （文件传输协议） DNS （域名解析协议）

    常用工具： curl 、浏览器开发者工具。

    传输层 :提供可靠或不可靠的数据传输，进行流量控制、差错校验等。

    TCP （可靠传输，面向连接） UDP （用户数据报协议，不可靠传输，无连接）

    工具： netstat 、 ss 、 telnet 。

    网络层 :负责数据包的寻址、路由选择和转发，不保证数据可靠性。

    IP （互联网协议，提供寻址和数据包转发） ICMP （Internet 控制消息协议，常用于 ping 命令）

    工具： ping 、 traceroute

    数据链路层 :管理物理连接方式，负责数据帧的封装、传输和校验。

    在同一网段内通信，如 以太网（Ethernet） Wi-Fi（无线局域网协议）

    工具： ifconfig 、 ip addr 。

    七层模型（OSI模型） ：

    物理层 ：传输原始比特流。

    数据链路层 ：提供节点间的数据传输，包括MAC地址、帧的定义。

    网络层 ：负责路径选择、路由传输，包括IP地址。

    传输层 ：提供端到端的数据传输，包括 TCP、UDP 协议。

    会话层 ：管理会话（建立、维持和终止会话）。

    表示层 ：负责数据格式的转换、加密、压缩等。

    应用层 ：提供应用程序服务，如HTTP、FTP等。

    TCP vs UDP

    TCP

    「TCP 是一个 面向连接、可靠传输 的传输层协议。它主要解决的问题是—— 网络传输的可靠性、有序性、以及流量控制和拥塞控制 。」

    TCP （传输控制协议， 可靠传输 ，面向连接）

    面向连接 ：在发送数据之前，客户端和服务器必须先建立连接（三次握手）。

    可靠性高 ：提供数据的 确认机制（ACK）、重传机制和流量控制 ，保证数据的完整性和顺序性。

    有序性 ：通过 序列号（SEQ）和确认号（ACK） 保证数据顺序到达。

    流量控制 ：通过 滑动窗口 ，防止接收端被撑爆。

    拥塞控制 ：通过算法如 慢启动、拥塞避免、快重传、快恢复 ，防止网络拥堵。

    场景 ：适用于需要数据可靠传输的场景，如网页浏览（HTTP/HTTPS）、邮件传输（SMTP）。

    UDP （用户数据报协议， 不可靠传输 ，无连接）

    无连接 ：发送数据前不需要建立连接，直接传输。

    不可靠 ：不提供数据确认和重传机制，数据可能会丢失、重复或乱序。

    速度较快 ：由于没有连接建立和确认过程，适合对时延敏感的应用。

    场景 ：适用于对实时性要求高的场景，如 视频会议、在线游戏、DNS查询 。

    TCP 安全传输机制

    三次握手建立连接 ：客户端和服务器端通过三次握手建立连接，确保双方都能正常通信。

    序列号和确认应答 ：TCP通过序列号和确认应答机制来保证数据的可靠传输。发送方将每个数据包都标记一个序列号，接收方通过确认应答来告知发送方数据已经接收到。

    确认应答机制（ACK） ：TCP中的确认应答是指接收方在成功接收到数据段后，向发送方返回一个确认消息，表示已成功接收的数据段编号。例如，如果接收方收到序列号为100到199的数据段，则会返回一个ACK=200的消息，表示下一个期望接收的数据段从序列号200开始。

    流量控制 ：TCP通过滑动窗口机制来进行流量控制，确保发送方和接收方之间的数据传输速度匹配，避免数据丢失或溢出。

    拥塞控制 ：TCP通过拥塞窗口机制来进行拥塞控制，避免网络拥塞导致数据丢失或传输延迟。

    超时重传 ：TCP通过超时重传机制来保证数据传输的可靠性，当发送方在规定时间内没有收到确认应答时，会重新发送数据包。

    📌TCP超时重传机制

    由于网络环境复杂，数据段可能在网络中丢失、损坏或延迟。为了应对这种情况，TCP引入了超时重传机制。发送方在发送数据段后会启动一个计时器，如果在计时器超时前没有收到对应的ACK，则认为该数据段丢失，触发重传。

    快速重传机制 ：除了超时重传外，TCP还支持快速重传机制。当发送方连续收到三个重复的ACK时，可以推断中间某个数据段丢失，从而立即重传丢失的数据段而无需等待超时。

    📌TCP拥塞控制

    避免数据填满整个网络，导致 丢包、时延增加 等问题。

    TCP 通过 自适应调整发送速率 ，防止拥塞恶化。

    TCP 拥塞控制的 4 大算法

    慢启动（Slow Start）

    发送方 指数增长 发送数据（每收到一个 ACK，cwnd +1）。

    直到达到慢启动门限（ssthresh），进入 拥塞避免阶段 。

    拥塞避免（Congestion Avoidance）

    线性增长 cwnd（每次 ACK，cwnd 增加 1/cwnd）。

    控制增长速率，避免过快填满网络。

    拥塞发生（Congestion Occurs）

    超时重传 ：

    发生超时 -> cwnd 直接降为 1，ssthresh 变为原 cwnd 的一半，重新慢启动。

    快速重传 （3 次重复 ACK）：

    cwnd 减半，不降到 1，而是进入 快速恢复 。

    快速恢复（Fast Recovery）

    避免回到慢启动：

    cwnd 设为 ssthresh +3（因为仍有 3 个包已收到）。

    继续线性增加 cwnd，直到收到新 ACK，进入拥塞避免。

    📌TCP流量控制

    流量控制的主要通过 接收窗口 来实现防止接收方因为数据接收过快导致缓冲区溢出

    接收窗口大小的控制 ：接收方根据自身的缓冲区空间动态调整接收窗口的大小，发送方基于此窗口大小来控制发送的数据量。

    TCP 滑动窗口 ：发送方可以在不等待确认的情况下发送多个数据包，发送窗口不断“滑动”，但发送的字节总数不能超过接收方的接收窗口大小。

    暂停发送机制 ：当接收方的缓冲区满了，接收窗口为0时，发送方会暂停发送数据，直到接收方通知它有了新的空间。

    📌UDP 如何实现可靠——QUIC 协议

    QUIC通过在 应用层 封装数据包，并 通过UDP协议 进行传输，实现了类似于 TCP 的可靠传输机制。

    多路复用 ：QUIC 支持多个独立的流，避免了 TCP 中的队头阻塞问题，流之间互不影响，从而提高了并发处理能力。

    拥塞控制和流量控制 ：QUIC 内建拥塞控制和流量控制机制，根据网络状况动态调整传输速率，避免网络拥堵。

    加密 ：QUIC 使用 TLS 1.3 进行内置加密，提供安全性并减少延迟。

    连接建立优化 ：QUIC 支持 0 RTT 或 1 RTT 的连接建立，相比 TCP 的三次握手，显著减少了连接建立的延迟。

    重传机制 ：QUIC 实现了高效的丢包恢复机制，通过 ACK 和快速重传保证数据可靠传输。

    📌应用层怎么解决UDP的错包问题？

    UDP 是一种无连接的协议，它本身没有内建的机制来保证数据的可靠性。因此， 应用层需要采取额外措施来解决 UDP 数据包丢失、错乱等问题 ：

    重传机制 ：在应用层实现重传机制。例如，在发送方为每个数据包加上序列号，接收方检测丢失的数据包，并向发送方请求重传。

    确认机制（ACK） ：发送方在发送数据包后，等待接收方的确认 (ACK)。如果在规定时间内未收到 ACK，发送方会重新发送该数据包。

    排序机制 ：为数据包添加序列号，接收方根据序列号重新排序数据包，避免数据包乱序。

    超时机制 ：在应用层设置超时时间，在超时未收到数据包时进行重发，避免因数据丢失而造成应用异

    TCP 三次握手

    「TCP 建立连接时用的是 三次握手 ，主要是为了解决双方 收发能力是否正常 的问题。」

    第一次 ：客户端发送SYN报文 SYN = 1, seq = x （表示我要连接你了，我这边初始序列号是 x）

    第二次 ：服务器收到 SYN报文，发送SYN-ACK报文: SYN = 1, ACK = x+1, seq = y （表示我收到了你的请求，并且我也准备好了）

    服务端随机初始化自己的序号，将此序号填入 TCP 首部的「序号」字段中，

    其次把 TCP 首部的「确认应答号」字段填入 client_isn + 1, 接着把 SYN 和 ACK 标志位置为 1。最后把该报文发给客户端

    第三次 ：客户端 A 收到 SYN-ACK 后，再次发送 ACK = y+1 ,表示收到服务端的状态是正常的确认，并准备发送数据

    第三次握手是可以携带数据的，前两次握手是不可以携带数据的

    为什么需要三次握手建立连接？

    防止已失效的连接请求被服务器误接收（解决“旧连接”问题）

    如果采用 两次握手 ，假设客户端 A 发送了 SYN 请求，如果网络延迟或丢包，A 以为请求失败重新发起新的连接，而服务器 B 接收到这个历史 SYN 后，直接建立连接（两次握手），则可能导致错误连接，数据传输异常。

    三次握手主要是为了保证 客户端和服务端的发送和接收能力都正常

    避免资源浪费

    如果客户端发送的 SYN 报文在网络中阻塞了，重复发送多次 SYN 报文，服务端不清楚客户端是否收到了自己回复的 ACK报文，所以服务端每收到一个 SYN 就只能先主动建立一个连接 ，就会 建立多个冗余的无效链接造成不必要的资源浪费。

    同步双方初始序列号 ，避免数据包乱序问题。

    TCP 协议的通信双方， 都必须维护一个「序列号」，接收方可以根据数据包的序列号按序接收；

    当客户端发送携带「初始序列号」的 SYN 报文的时候，需要服务端回一个 ACK 应答报文表示客户端的 SYN 报文已被服务端成功接收，当服务端发送「初始序列号」给客户端同理， 这样一来一回，才能确保双方的初始序列号能被可靠的同步

    能不能四次握手？

    四次握手 只会增加一次 ACK ，并不会提供额外的可靠性，增加了网络开销。

    三次握手已经足够确保双方的收发能力，安全性够用了。

    大量SYN包发送给服务端

    有可能会导致TCP 半连接队列打满，这样 当 TCP 半连接队列满了，后续再在收到 SYN 报文就会丢弃 ，导致客户端无法和服务端建立连接。

    避免 SYN 攻击方式，可以有以下四种方法：

    调大 netdev_max_backlog；

    增大 TCP 半连接队列；

    开启 tcp_syncookies；

    减少 SYN+ACK 重传次数

    TCP 怎么判别包重复/丢包/乱序？

    每个包有 序列号 seq 和确认号 ack

    TCP 是 面向字节流 的，接收端通过 ack 确认号 知道是否接收完整

    乱序 → TCP 缓存后重排；丢包 → 通过超时/重复 ACK 检测到，触发重传

    TCP 四次挥手

    为什么要四次？因为 TCP 是全双工的，关闭要分两边，不能合并成一次。 总结：四次挥手是因为 TCP 的双向通信要分别关闭。 ”

    TCP 连接是全双工的（双向通信） ，所以 关闭连接需要双方都同意并释放资源 。

    数据发送和接收是独立的 ，所以 必须确保两端的数据都传输完毕后才能完全断开连接 。

    客户端 发送 FIN ，请求断开连接（ 主动关闭 ）。

    服务器 回复 ACK ，表示收到了 FIN 请求，但此时 可能仍有数据要发送 ，所以连接仍然保持。

    服务器 处理完所有数据后，发送 FIN ，表示也要断开（ 被动关闭 ）。

    客户端 回复 ACK ，进入 TIME_WAIT 状态，确保服务器收到 ACK 后再彻底关闭连接。

    ACK FIN为什么分开发

    如果是三次挥手：客户端 FIN ，服务器 ACK + FIN ，客户端 ACK ，立刻关闭连接。

    服务端应用程序可能还有数据要发送

    所以 ACK 和 FIN 分开，以确保服务器数据完全发送完毕 。

    是否要发送第三次挥手的控制权不在内核，而是在被动关闭方服务端的应用程序，因为应用程序可能还有数据要发送，由应用程序调用了关闭连接的函数，内核就会发送 FIN 报文了

    TIME_WAIT为什么需要 2MSL？

    TCP 四次挥手过程回顾：

    主动关闭方发送 FIN → 进入 FIN_WAIT_1

    被动关闭方回应 ACK → 主动方进入 FIN_WAIT_2

    被动关闭方发送 FIN → 主动方回应 ACK 并进入 TIME_WAIT

    经过 2MSL 时间后，彻底关闭连接，释放资源

    四次挥手里，最后一个 ACK 的一方会进入 TIME_WAIT 状态，一般是主动断开连接的那一方。

    保持 2 倍最大报文寿命（2MSL）既保证可靠关闭，又避免旧报文干扰新连接。

    TIME_WAIT 也被称为 2MSL 等待状态 。

    谁进入这个状态？ 主动关闭连接的一方 。比如，客户端调用 close() 方法，或者服务端主动断开了连接。

    持续时间？ 通常是 2 倍的最大报文段生存时间（2MSL） 。在 Linux 上，MSL 通常默认为 60 秒，所以 TIME_WAIT 会持续 120 秒 。

    确保最后的 ACK 能够被服务器接收（可靠性保障）

    在 TCP 四次挥手过程中，客户端发送最后的 ACK ，服务器就进入 CLOSED 状态，认为连接已经完全关闭。

    但这个 ACK 可能丢失，如果服务器没收到，就会 重发 FIN 。

    客户端在 TIME_WAIT 状态，可以 重传 ACK ，保证对方正确关闭连接。

    防止旧连接的数据影响新连接 （避免端口复用问题）

    在 TCP 连接关闭后，可能仍有 延迟的旧数据包 在网络中传输。

    TIME_WAIT 持续 2 倍的 MSL（Maximum Segment Lifetime） ，确保 所有旧数据包都过期，避免影响新连接 。

    2 * MSL 确保 所有可能的延迟报文都已消失 ，不会影响新连接。

    确保 FIN 被正确收到

    如果客户端发送的 ACK 丢失，服务器会 重发 FIN 。

    2 * MSL 内，客户端仍可接收 FIN，并重新发送 ACK ，确保服务器正常关闭。

    如果立即重用相同的 端口和 IP，可能会导致新连接收到旧连接的过期数据，导致数据混乱。

    📌场景：服务端出现大量的timewait

    “ TIME_WAIT 是 TCP 四次挥手中正常的状态，表示连接已经关闭， 确保最后一个 ACK 能送达 。】

    但如果服务端 主动关闭连接（即先发 FIN） ，就会产生很多 TIME_WAIT ，时间一久占资源。”

    1. HTTP 没有使用长连接

    默认情况下，HTTP/1.0 不会使用长连接 ，每个请求完成后，服务器会主动关闭连接,进入 TIME_WAIT 状态。

    解决方案：启用长连接（Keep-Alive） ， HTTP 头中使用 Connection: keep-alive 使连接复用，减少频繁建立和关闭 TCP 连接的开销。

    2. HTTP 长连接超时或长连接的请求数量达到上限

    即使开启了 Keep-Alive， 如果长时间没有新的请求 ，服务器就会主动关闭连接，从而进入 TIME_WAIT 状态。

    **解决方案：**调整 Keep-Alive 超时时间， 适当延长 超时时间，减少连接频繁关闭的次数。

    在高并发场景下， 使用连接池 ，复用 TCP 连接，减少不必要的连接创建与销毁。

    有些服务器（如 Nginx）会对 单个 TCP 连接的请求数量 做限制,达到上限后，服务器会主动关闭连接进入 TIME_WAIT。

    解决方案：

    提高 keepalive_requests 限制 ，减少 TCP 连接的频繁关闭。

    优化负载均衡策略 ，让请求更均匀地分布到不同的连接上。

    TIME_WAIT 过多如何优化

    解决思路主要是“ 减少主动关闭的频率 ”和“ 让系统能快速重用 TIME_WAIT 状态的资源 ”。

    1. 应用层优化（首选，最根本）

    使用连接池 ：对于需要频繁通信的组件（如数据库连接、微服务间调用、爬虫等），务必使用连接池。这可以极大地减少 TCP 连接的创建和销毁次数。

    启用长连接（Keep-Alive） ：

    Web 服务 ：确保 Web 服务器（Nginx）和后端应用（Tomcat）之间、以及客户端和 Web 服务器之间都启用了 HTTP Keep-Alive。

    修改服务端配置 ：例如，在 Nginx 的 upstream 配置中设置 keepalive 参数，保持与后端服务的长连接。

    使用负载均衡 让不同服务器处理连接，减少单机的 TIME_WAIT 连接数

    TCP 的RST

    RST（Reset 标志）用于 强制终止 TCP 连接 ，通常在以下情况下出现：

    端口未监听 ：客户端连接到一个没有服务的端口，服务器返回 RST。

    异常连接中断 ：如进程崩溃，服务器直接关闭连接。

    TCP 超时或数据异常 ：检测到错误数据包后，TCP 可能会发送 RST 强制关闭连接。

    防止半开连接 ：如果一方已经关闭连接，但另一方仍然发送数据，可能会触发 RST。

    TCP 的长连接和短连接

    TCP 的长连接是建立一次连接后复用该连接进行多次通信，适用于高并发、频繁通信的场景，比如 Redis、数据库连接池。短连接是每次通信都新建连接，用完立即断开，适合低频请求减少服务器连接占用，比如邮件服务。虽然短连接更简单安全，但在高并发下，长连接能有效减少连接开销，提高吞吐量。

    短连接（一次性连接）

    每次通信都 新建一个 TCP 连接 ，任务完成后 立即关闭 连接。

    HTTP 1.0 默认短连接

    访问频率低、请求间隔长的应用（如数据库查询、REST API 调用）

    缺点：频繁创建 & 释放 TCP 连接， 开销大 （三次握手 + 四次挥手）。

    长连接（Keep-Alive）

    TCP 连接 建立后持续保持，不主动关闭 ，多个请求可复用该连接。

    HTTP 1.1，MySQL 客户端 默认 Keep-Alive

    缺点： 占用服务器资源 （如文件描述符、内存），需定期心跳检测是否断开。

    TCP 粘包 & 拆包问题

    TCP 是 流式协议 ，它没有边界概念。一次 send() 和一次 recv() 的数据量不一定一一对应，导致多个包可能被合并（粘包）或被拆分（拆包）。

    什么是 TCP 粘包 & 拆包？

    粘包 ：多个小数据包被合并成一个大数据包发送。

    拆包 ：一个大数据包被拆分成多个小数据包接收。

    解决方法

    方法 1：固定长度协议 ：发送端约定 固定数据长度 ，接收端按照固定大小读取。

    优点 ：实现简单，适用于定长数据场景。

    缺点 ：不适用于变长数据，可能浪费带宽。

    方法 2：使用特定分隔符 ：在每个数据包末尾添加特殊分隔符（如 \n 、 | ）。

    适用于文本协议 （如 HTTP、FTP）。

    方法 3：自定义消息结构

    方案 ：在数据包前添加 固定长度的消息头 ，指定后续消息体的大小，接收端先解析消息头，再读取消息体。

    TCP 网络编程底层方法

    常见的 Linux TCP 网络编程 API ：

    socket() - 创建 socket 文件描述符。

    bind() - 绑定 IP 和端口。

    listen() - 监听连接（服务器端）。

    accept() - 接收客户端连接（服务器端）。

    connect() - 连接到服务器（客户端）。

    send() / recv() - 发送和接收数据（流式传输）。

    sendto() / recvfrom() - UDP 发送和接收数据（无连接）。

    setsockopt() - 设置 socket 选项（如 SO_REUSEADDR ）。

    shutdown() - 关闭 TCP 连接的读/写方向。

    close() - 关闭 socket 释放资源。

    **UDP 使用 connect() **

    UDP 是 无连接的协议 ，但仍然可以调用 connect() 绑定远程地址：

    不使用 connect() ：

    每次 sendto()/recvfrom() 需要指定对方的 IP:Port 。

    适用于 多个客户端通信 ，更灵活。

    使用 connect() ：

    只和一个目标 IP:Port 通信， send()/recv() 无需每次提供地址。

    屏蔽非目标地址的数据包 ，提高安全性和效率。

    适用于 固定目标的 UDP 连接 （如 DNS 查询、VoIP）。

    怎么判断一个 socket fd 可读

    可以使用 多路复用机制 来监听 socket 是否可读：

    select()

    poll()

    epoll() （Linux 推荐，性能更高）

    如果 select/poll/epoll 监听到 socket 变为可读，说明：

    有新的数据可读 （客户端发送数据到服务器）。

    对端关闭了连接 （ recv() 返回 0）。

    有新的客户端连接 （对于监听 socket）。

    HTTP

    HTTP是 无状态、基于请求-响应 的协议，主要用于 客户端（浏览器）与服务器 之间通信。

    无状态（Stateless） ：每个请求都是独立的，服务器不会记住之前的状态（但可以用 Cookie、Session 维持状态）。

    无连接（短连接） ：默认每次请求 TCP 连接后 ，服务器返回数据后 立即断开 （除非 Keep-Alive ）。

    基于请求-响应 ：客户端发起请求，服务器返回数据，没有 主动推送 能力（相比 WebSocket）。

    1.0/1.1/2.0/3.0

    Http1.0：第一个HTTP协议版本

    HTTP/1.0 每次请求都需要建立一个 新的 TCP 连接 。

    TCP 三次握手 + 四次挥手开销大，效率低。

    多个资源请求（如 HTML 页面 + CSS + JS + 图片）会导致大量 TCP 连接的建立和关闭，增加延迟。

    Http1.1：引入了 长连接 ，即可以在一个TCP连接上传送多个HTTP请求和响应，提高了性能。

    长连接是通过Connection: keep-alive头部来实现，即在 一个TCP连接上可以传输多个HTTP请求和响应 ；

    仍然存在队头阻塞问题 ：

    即使一个连接上可以顺序发送多个请求， 一个请求处理慢会阻塞后续请求 。

    多个资源请求仍可能需要额外 TCP 连接才能避免阻塞。

    Http2.0：通过 多路复用 来实现 长连接 ，避免了HTTP1.x的队头阻塞问题，提高了并发性能。

    HTTP/2.0 解决了应用层的队头阻塞 ，即多个请求在同一连接上可以交错发送和响应。

    但是 TCP 本身仍存在队头阻塞问题 ：

    如果 TCP 包丢失，后续数据包必须等待丢失包重传。

    所以 HTTP/2.0 在一个 TCP 连接上仍然会受到 TCP 层队头阻塞的影响。

    Http3.0则是基于QUIC协议，加密传输，减少了握手时间，提高了安全性和性能。

    使用 QUIC（基于 UDP） 的原因：彻底解决传输层队头阻塞。

    HTTP1.1 优化用Keep-Alive

    默认情况下，每次 HTTP 请求都会建立 & 断开 TCP 连接 ， Keep-Alive 可以 复用 TCP 连接 ，减少 三次握手 的开销，提高性能。

    开启 Keep-Alive 后，TCP 连接不会立即关闭，多个 HTTP 请求可以 共用 同一条连接。

    减少连接建立 & 释放的开销 ，提高请求吞吐量。

    适用于 HTTP/1.1 （默认开启），在 HTTP/2 中由 多路复用 取代。

    HTTP/1.1 vs HTTP2.0

    HTTP/1.1

    文本协议，每个请求/响应都是明文文本。

    每个连接一次只能发送一个请求 （除非使用管线化，但存在阻塞问题）。

    队头阻塞（Head-of-line blocking） ：一个请求慢会阻塞后续请求。

    HTTP/2.0

    二进制协议，所有数据分为 帧（frame） ，通过 流（stream） 复用同一TCP连接。

    支持 多路复用（Multiplexing） ：同一连接上可以并行发送多个请求和响应。

    解决了HTTP/1.1的队头阻塞问题

    WebSocket

    解决服务器频繁推送

    场景：* 如果服务器需要频繁推送数据到客户端，HTTP 本身是 请求-响应模式 ，无法满足 主动推送* 的需求。

    WebSocket（最佳方案）

    全双工通信 ，服务器和客户端 都可以主动发送数据 。

    基于 TCP 长连接 ，避免 HTTP 请求的 开销 。

    适用于：实时聊天、在线游戏、弹幕系统 。

    WebSocket全双工

    HTTP和WebSocket都是基于TCP的应用层协议，但它们的通信模式不同。

    HTTP/1.1的keep-alive虽然复用连接，但仍然是半双工。比如，客户端发送多个请求时，可以在同一个连接上顺序处理，但请求和响应必须按顺序进行，也就是可能有队头阻塞的问题。HTTP即使是keep-alive模式还是基于请求-响应模式，服务端不能主动推送数据，只能由客户端发起请求。

    WebSocket的持久连接。WebSocket是 真正的全双工通信 ，连接一旦建立，客户端和服务端都可以随时发送数据，不需要等待对方的请求。它的握手阶段是通过HTTP升级协议完成的，之后就一直保持连接，直到一方关闭。这种方式适合实时应用，比如聊天室或实时游戏，因为数据可以即时双向传输

    HTTP 半双工模拟全双工

    半双工协议 ： HTTP 是典型的半双工。虽然基于TCP（全双工），但其 请求-响应 的模型决定了同一时刻只能由客户端主动发起请求，服务器响应，通信是交替进行的。

    如何模拟全双工 ：在用户侧（浏览器），可以通过 HTTP长轮询（Long Polling） 或 SSE（Server-Sent Events） 来模拟服务器向客户端的“推送”能力，再结合普通的HTTP请求实现客户端到服务器的通信，从而在应用层模拟出类似全双工的效果，但这比真正的WebSocket效率低。

    HTTP长轮询

    客户端 ：发送一个HTTP请求到服务器。

    服务器 ： 持有这个连接不立即返回 ，直到：

    a) 有数据需要推送给客户端 ：此时立即返回响应。

    b) 请求超时 ：达到一个设定的超时时间（如30秒）后，返回一个无数据的响应。

    客户端 ：只要收到响应（无论哪种情况），就 立即发起一个新的请求 ，从而维持一个几乎常开的连接。

    SSE

    如何模拟 ：这是一个HTML5标准，允许服务器通过一个 保持打开的HTTP连接 ，持续地向客户端发送文本数据流（如JSON）。客户端使用 EventSource API来接收处理。

    特点 ：

    它是 真正的“服务器推送” ，但仍然是基于HTTP的半双工协议。

    单向通道 ：它只支持服务器向客户端的单向推送。如果客户端需要发送数据，仍需另外发起普通的HTTP请求（如Ajax）。这样组合起来，就在应用层模拟了全双工。

    HTTPS

    HTTP vs HTTPS

    HTTPS 与 HTTP 区别 ：

    HTTPS = HTTP + TLS，具备 加密、身份验证、防篡改 能力；

    HTTPS 通过 SSL/TLS 握手建立安全信道 ，保证数据在传输过程中的安全性；

    缺点是有一定的计算和延迟开销（但可以优化）。
    HTTP HTTPS
    安全性 明文传输，容易被监听、劫持 加密传输，防止窃听和篡改
    加密协议 无加密 使用 SSL/TLS 进行数据加密
    身份认证 无身份认证，可能遭遇中间人攻击 由 CA 机构颁发 SSL/TLS 证书
    数据完整性 无校验，可能被篡改 具备完整性校验，防止数据篡改
    默认端口 80 443

    HTTPS 的加密过程

    HTTPS 中的 非对称加密 过程主要用于建立安全连接的初始阶段，即 TLS 握手过程。非对称加密使用一对密钥（公钥和私钥），其中公钥用于加密数据，私钥用于解密数据。在 HTTPS 连接中，客户端使用服务器的公钥加密一个预主密钥（pre-master secret），然后发送给服务器。服务器使用自己的私钥进行解密。

    一旦密钥协商完成，后续的数据传输就使用该 对称密钥 进行加密和解密，因为对称加密效率更高。

    客户端 -> 服务器：请求 HTTPS 连接

    服务器返回证书

    客户端验证证书

    客户端生成对称密钥（AES）

    客户端用公钥加密对称密钥，发送给服务器

    服务器解密，使用对称密钥加密通信

    HTTPS 的握手过程

    “HTTPS 握手一般是 TLS 四次交互：

    客户端发起 ClientHello，带上支持的加密算法、随机数；

    服务端回 ServerHello，选择算法，返回证书、公钥、随机数；

    客户端校验证书，用公钥加密一个对称密钥（Pre-master Key）发给服务端；

    双方根据随机数生成 对称密钥 ，进入加密通信。 总结：HTTPS 通过非对称加密交换对称密钥，再用对称加密传输数据。 ”

    HTTPS why后续还是用对称加密？

    回答示例：
    “主要是性能和效率问题：

    非对称加密 （RSA/ECC）很慢，适合交换少量密钥；

    对称加密 （AES/ChaCha20）速度快，适合大规模数据传输。 总结：非对称用来‘安全交换密钥’，对称用来‘高效传输数据’。 ”

    一定安全吗？如何破解？
    不完全安全 。破解方法包括：

    中间人攻击 (MITM) ：如果客户端不严格验证证书（如接受自签名证书），攻击者可以伪造证书进行拦截。

    降级攻击 ：攻击者干扰握手过程，迫使双方使用不安全的旧版本或弱加密算法。

    窃取服务器私钥 ：如果服务器私钥泄露，所有通信都可被解密。

    破解弱随机数 ：如果生成的随机数A、B或Pre-Master Secret不够随机，会话密钥可能被暴力破解。

    DNS 服务解析

    DNS是用于将 域名（如 www.google.com）转换为 IP 地址 的系统。

    当用户在浏览器输入 www.example.com 时，DNS 解析过程如下：

    ① 查询本地缓存

    浏览器缓存 ：浏览器首先检查是否有 www.example.com 的 DNS 解析记录。

    操作系统缓存 ：如果浏览器没有找到，会询问操作系统（ hosts 文件或 DNS 缓存）。

    本地 DNS 服务器缓存 ：如果本机没有找到，则向本地 DNS 服务器（ISP 提供）请求。

    ② 递归查询（如果本地 DNS 服务器缓存缓存无结果）

    查询根 DNS 服务器

    例如，根服务器返回 .com 顶级域 DNS 服务器的地址。

    查询顶级域（TLD）DNS 服务器

    .com 服务器返回 example.com 的权威 DNS 服务器地址。

    查询权威 DNS 服务器

    权威 DNS 服务器返回 www.example.com 的最终 IP 地址（如 192.0.2.1 ）。

    本地 DNS 服务器缓存结果 ，然后返回给客户端。

    一个 URL 从输入浏览器到服务器会发生什么？

    输入网址到页面出来，大概经历了 DNS 解析 → 建立连接（TCP 三次握手）→ 发起 HTTP 请求 → 服务器响应 → 浏览器解析页面 这么几个步骤。

    输入网址 （比如 www.baidu.com ）

    浏览器检查缓存有没有 DNS 解析记录

    没有的话就发起 DNS 查询 → 获取 IP 地址（A 记录）

    查询顺序：浏览器缓存 → 系统缓存 → hosts 文件 → 本地 DNS → 根域名服务器……

    建立 TCP 连接 （三次握手）

    用 IP 和端口（一般是 80/443）建立 TCP 连接

    如果是 HTTPS，还有 TLS 握手阶段（涉及证书、公钥私钥、对称密钥协商等）

    发送 HTTP 请求 （GET/POST）

    把请求行、请求头等信息打包成报文发给服务器

    服务器处理请求，返回 HTTP 响应

    里面包含状态码、响应头、响应体（可能是 HTML/CSS/JS）

    浏览器解析响应

    加载 HTML → 解析 CSS → 执行 JS → 发起二次请求（图片、JS、CSS）→ 页面渲染

    路由器传输过程中的协议？

    ARP（地址解析协议） ：将 IP 地址转换为 MAC 地址。

    ICMP（Internet 控制消息协议） ：用于网络诊断（如 ping）。

    IP（Internet Protocol） ：负责数据包的寻址和路由。

    TCP/UDP（传输层协议） ：确保数据传输的可靠性（TCP）或低延迟（UDP）。

    HTTP/HTTPS（应用层协议） ：处理 Web 访问。

    为什么数据包到了网卡就知道要发送给网关

    操作系统会维护 路由表 ，通过 route -n 或 ip route 命令可以查看。

    当数据包到达网卡：

    如果目标 IP 在本地子网，则直接发送。

    如果目标 IP 不在本地子网，则根据路由表，将数据包发往默认网关（通常是路由器）

    HTTP无状态

    HTTP是 无状态的，这意味着每个请求都是独立的 ，服务器不会在多个请求之间保留关于客户端状态的信息。

    在每个HTTP请求中，服务器不会记住之前的请求或会话状态，因此每个请求都是相互独立的。

    虽然HTTP本身是无状态的，但可以通过一些机制来实现状态保持，其中最常见的方式是 使用Cookie和Session来跟踪用户状态 。

    通过在客户端存储会话信息或状态信息，服务器可以识别和跟踪特定用户的状态，以提供一定程度的状态保持功能。

    Session/Cookie/Token

    在 Web 认证中，这三者用于管理用户状态，主要区别如下：

    Cookie （客户端存储）

    由服务器生成，存储在 客户端 中，主要用于保存一些用户状态或会话信息比如 Session ID。每次请求时，浏览器会自动携带 Cookie 发送给服务器。

    Cookie 由于存储在客户端，容易受到 XSS（跨站脚本攻击）和 CSRF（跨站请求伪造）攻击。

    因此一般会通过 HttpOnly 防止 JavaScript 访问， Secure 只允许 HTTPS 传输等方式提高安全性。

    Session （服务器存储）

    服务器为每个用户创建 Session，并生成唯一的 Session ID ，通过 Cookie 传递给客户端。

    当用户请求时，服务器根据 Session ID 查找用户信息，进行身份验证。

    服务器存储用户状态，安全性高，但增加了服务器内存消耗。

    适用于 Web 端用户身份管理，但在高并发场景下需要优化（如使用 Redis 存储 Session）。

    Token （无状态认证）

    Token 是一种无状态认证方式，常见的如 JWT 。当用户登录时，服务器生成 Token 并返回给客户端，客户端之后的请求都带上这个 Token，服务器无需存储用户状态，而是直接解析 Token 获取用户信息。

    Redis + Token（JWT 方案）

    服务器不再维护 Session ，而是让客户端存储 JWT Token ，JWT 本身携带用户信息。

    适用于 “无状态鉴权” ，减少 Redis 依赖，提高性能。

    流程示意：

    用户登录，服务器生成 JWT Token （包含用户信息、过期时间）。

    Token 发送给用户，存储在 Cookie 或 Header 中。

    用户请求时携带 Token ，服务器解析 JWT ，验证身份并处理请求。

    不依赖 Redis ，解析 Token 即可完成认证

    根据场景如何选择

    单机应用 → 本地 Session （无需考虑负载均衡）。

    小型分布式应用 → Sticky Session （Nginx ip_hash 方式）。

    高并发、大流量系统 （如电商、社交） → Redis 共享 Session（推荐） 。

    容器化（Kubernetes）环境 ：推荐 Redis ，因为容器随时可能被销毁，Session 需要独立存储。

    单点登录（SSO）→ JWT 方案 JWT 可跨域认证，多个系统无需共享 Session，解析 Token 即可。

    移动端/前后端分离→ JWT 方案 前端直接存 Token，后端无状态处理，无需维护 Session

    Netty网络通信框架

    Netty 是一个高性能、异步的网络通信框架，能够处理大量的并发连接。

    线程模型 ： 主从Reactor多线程模型 。BossGroup负责接收连接，WorkerGroup负责处理I/O读写，业务逻辑可交由其他线程池处理。

    Reactor 模式 ：

    Netty 使用了 Reactor 模式 ，该模式将 I/O 操作与应用逻辑解耦。Reactor 模式通过一个单独的线程处理所有 I/O 事件（比如读、写等），从而减少了线程切换的开销，并避免了每个连接都创建一个独立线程的高成本。这样可以让高并发的网络请求得到更高效的处理。

    零拷贝（Zero-Copy） ：

    零拷贝 是指在处理数据时，尽可能避免多次内存复制。Netty 利用零拷贝技术，如通过 DirectByteBuffer 来避免内存的多次拷贝，从而提高 I/O 操作的效率。

    在数据传输过程中，Netty 通过底层的操作系统直接读写操作系统的 I/O 缓冲区，避免了数据的多次拷贝，提升了 I/O 性能。

    内存管理（堆外内存） ：

    Netty 使用了 ByteBuf 类来进行内存管理。

    ByteBuf 主要分为两种类型的内存： 堆内存 （Heap Memory）和 堆外内存 （Direct Memory）。其中， 堆外内存 是 Netty 性能的关键之一，它能够减少内存的复制和 GC 的开销。

    堆外内存是直接分配在操作系统的内存区域，不会受到 JVM 堆内存的垃圾回收机制的影响，从而减少了内存管理的开销，并且堆外内存直接与操作系统的 I/O 设备进行交互，进一步提升了性能。

    通过使用堆外内存，Netty 可以通过操作系统直接进行 I/O 操作而无需进行额外的内存拷贝，从而大幅度提高了 I/O 操作的效率。

    内存池 ：

    Netty 使用 内存池 来管理 ByteBuf 。内存池通过将小块的内存预分配并重复使用，减少了内存分配和释放的频率，从而减少了 GC 的负担，并且提高了内存的使用效率。

    RPC通信

    RPC用于 在不同服务或进程之间进行远程方法调用 ，让远程调用像本地调用一样透明。

    RPC基于HTTP/2 ，支持多路复用（一个连接并行多个请求）、头部压缩、二进制编码（Protobuf），比HTTP/1.1的文本JSON格式 性能更高、延迟更低 。

    效率 ：Protobuf序列化后体积比JSON小得多，网络传输效率高。

    服务提供方（Server） ：提供可调用的方法（例如 getUser(id) ）。

    服务调用方（Client） ：远程调用 Server 提供的方法。

    序列化 ：请求和响应需要进行 序列化 ，如 JSON、Protobuf、Hessian 等。

    网络通信 ：通过 TCP/HTTP 发送数据（Netty、HTTP、gRPC）。

    反序列化 ：接收端解析数据，返回结果。

    RPC 和 HTTP 区别

    选择 RPC 是为了 高性能、高效率的服务间调用 ，常用于微服务集群内部。

    选择 HTTP （特别是RESTful）是为了 通用、开放、易调试的API接口 ，常用于对外提供开放API或前后端交互。
    特性 gRPC (基于HTTP/2) 传统HTTP API (如RESTful)
    协议 通常基于 TCP ，并可选择更高效的 二进制序列化 协议（如 gRPC 用 Protobuf，Dubbo 用 Hessian2）。 性能更高，延迟更低 。 基于 应用层协议 （HTTP/1.1, HTTP/2）。早期 HTTP/1.1 是文本协议，有队头阻塞问题，性能较低。 HTTP/2 是多路复用的二进制协议，性能大幅提升
    数据格式 Protocol Buffers (二进制) JSON/XML (文本)
    通信模式 支持 一元调用、客户端流、服务端流、双向流 主要是 请求-响应
    代码生成 通过Protobuf文件 强类型 自动生成 需依赖Swagger/OpenAPI，弱类型
    性能 高 （二进制、多路复用、头部压缩） 相对较低 （文本、队头阻塞）

    协议层

    同时支持 HTTP 协议 ，方便和外部系统互通。

    序列化方式

    Protobuf

    它的核心功能是：

    把结构化数据（对象、消息）序列化为二进制格式，便于存储和网络传输。

    反序列化时再把二进制还原为原始数据结构。

    网络故障

    网络故障怎么排查？

    从 网络模型 入手排查：

    排查网络问题时，我一般先从应用层入手，如果发现无法连接会向下排查，配合 tcpdump 抓包分析。

    应用层 （如 HTTP、DNS）处理具体业务；我们开发常调的是 curl 、 postman 。

    传输层 （TCP/UDP）保证可靠或快速传输，用 netstat 、 ss 检查连接状态。

    网络层 （IP、ICMP）负责寻址、路由，排查可用 ping 、 traceroute 。

    链路层 处理 MAC 地址， ifconfig 、 tcpdump 、 wireshark 用于抓包。

    对这些层的理解可以帮助我快速排查服务连通性，比如 ping 不通说明网络层断， telnet 不通说明端口没开。

    换个说法，给一个服务，怎么知道这个服务正常运行？

    客户端自查（C端） ：

    网络连通性 ： ping 看是否能通，延迟和丢包率如何。

    DNS解析 ： nslookup 看域名解析是否正确。

    应用层检查 ： curl 接口是否返回200，返回结果是否合理

    服务端排查（B端） - 这是重点 ：

    监控与日志 ：

    进程存在 ： ps , top , systemctl status

    日志无报错 ：无异常日志、无频繁重启

    查看 应用监控 （APM工具如SkyWalking）：确认请求是否到达目标服务、在哪个环节耗时最长。

    确定网络层有问题，用Shell工具排查ip+端口通不通

    网络分层角度：

    网络连通性 ： ping 看能不能到达 IP

    路由路径 ： traceroute ip 或 mtr

    端口可达性 （传输层）： telnet ip port 或 nc ip port

    如果 telnet 成功，则 TCP 三次握手成功，说明服务监听正常

    traceroute

    traceroute 是一个用于网络故障排查的命令行工具，它能够帮助我们追踪数据包从源主机到目标主机的路径，显示中间经过的所有路由器（跳点）。

    traceroute 基于 ICMP协议和TTL 字段来工作：

    每发送一个数据包， traceroute 设置该数据包的 TTL（生存时间） 为一个小的值（通常从 1 开始）。

    当数据包经过每个路由器时，TTL 会减少，直到 TTL 为 0。此时，路由器会丢弃该数据包并发送一个 ICMP 超时 消息回源主机。

    通过逐步增加 TTL， traceroute 可以逐个显示经过的路由器的 IP 地址，并计算每一跳的延迟。

    作用

    网络排障： 如果无法连接到远程服务器， traceroute 可以帮助分析在哪一跳发生了问题。

    延迟问题定位： 当遇到慢速连接时，可以通过 traceroute 找到哪一跳的延迟过高，帮助识别瓶颈。

    tcpdump 抓包分析

    在排查网络问题时，我会首选 tcpdump 做轻量抓包， 命令行方便过滤关键字段 ，如：

    Shell
    # 抓取eth0网卡的所有流量
    tcpdump -i eth0

    # 抓取特定端口的HTTP流量（例如80端口）
    tcpdump -i eth0 port 80 -w http.pcap

    # 过滤目标IP和协议（如抓取192.168.1.100的ICMP包）
    tcpdump -i eth0 dst 192.168.1.100 and icmp

    # 显示详细数据（-v/-vv）并ASCII解码（-A）
    tcpdump -vv -A port 443

    抓完后也可以用 -w 导出 .pcap 文件用 Wireshark 可视化分析。

    Wireshark 能对 TCP stream 进行重组，方便查看完整 HTTP 请求或 TLS 握手。

    我自己排查接口请求超时时，就用这套流程定位是请求没发出去，还是没收到返回

    分析步骤：

    抓指定端口/协议的数据包

    结合 wireshark 分析 TCP 握手、是否有重传、RTT

    Wireshark 支持 TCP流重组（TCP Stream Reassembly）

    能还原完整的应用层协议，如 HTTP 报文

    适用于调试应用协议、查看 POST 请求体等

    看服务是否响应、是否断连、中间有无阻塞

    wireshark数据包重组

    Wireshark会对数据包进行重组，目的是为了呈现完整的应用层数据。

    TCP重组 ：一个大的HTTP响应可能被分成多个TCP报文段。Wireshark会根据TCP序列号将它们正确地重新组装，让你在 Follow TCP Stream 中看到完整的HTTP响应体。

    HTTP重组 ：对于 Transfer-Encoding: chunked 的分块传输，Wireshark会自动将分块重组为完整的消息体。

    好处 ：极大简化了分析难度，让我们可以直接关注应用层协议（如HTTP、MySQL、Redis协议）的语义，而不必手动拼接数据包。

    网络各层协议栈功能 + 常用协议工具

    答法结构：从上往下讲分层，分别说功能、协议、工具。

    网络协议栈常见是五层或七层模型，我理解从应用层到底层每层功能解耦，便于开发、维护和排查问题。

    1. 应用层 ：直接与用户交互，协议如 HTTP/HTTPS、DNS、FTP 等。常用工具： curl 、浏览器开发者工具。 2. 传输层 ：提供端到端的数据传输，可靠性由 TCP 实现，UDP适合低延迟应用。工具： netstat 、 ss 、 telnet 。 3. 网络层 ：负责寻址和路径选择，核心协议是 IP、ICMP。工具： ping 、 traceroute 。 4. 数据链路层 ：在同一网段内通信，如 Ethernet、ARP。工具： ifconfig 、 ip addr 。 5. 物理层 ：数据以电信号方式传输，涉及网线、光纤等。

    TCP 如何保证可靠传输？

    答法结构：三大机制：确认重传、滑动窗口、拥塞控制

    TCP 是面向连接的协议，主要靠以下机制保证可靠性：

    确认与重传 ：每个报文段都有序号和确认号，丢包后超时或收到重复 ACK 会触发重传。

    滑动窗口 ：用于流量控制，接收方通过通告窗口大小，限制发送方的速率。

    拥塞控制 ：通过慢启动、拥塞避免、快速重传和快速恢复等算法动态调整拥塞窗口，防止网络拥塞。

    HTTPS 是加密的，那平时怎么调试？

    答法结构：Fiddler / Charles + 浏览器工具 + curl

    虽然 HTTPS 加密了内容，但我们可以通过如下方式调试：

    Fiddler / Charles ：通过安装根证书，模拟中间人解密 HTTPS 报文，查看请求详情；

    浏览器 DevTools ：查看 HTTPS 请求的 Headers、状态码等；

    curl -v / -k ：手动测试接口响应及握手过程；

    若是公司内测接口，也可配置服务器支持双向 TLS 或输出日志辅助调试。
