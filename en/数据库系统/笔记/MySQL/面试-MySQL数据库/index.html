    索引

    索引机制

    索引是 数据库中的数据结构 ，用于 加速查询 ，其作用类似于书的目录，帮助 MySQL 快速定位数据 。

    ✅ 提高查询效率 ：避免全表扫描，大幅减少 I/O 操作。 ✅ 加速排序 ：索引本身是 有序结构 ，支持 ORDER BY 、 GROUP BY 。 ✅ 优化 WHERE 条件查询 ：索引可以加快 WHERE 过滤数据的速度。 ✅ 提高连接查询效率 ：索引减少 JOIN 关联表的计算量。

    占用额外的存储空间，并且在执行插入、更新和删除操作时需要维护索引结构，这会增加写操作的开销。
    场景 示例（以用户表为例） 索引类型建议
    业务高频查询的列 SELECT * FROM users WHERE email = 'xxx@xxx' 普通索引 / 唯一索引
    用于排序 / 分组的列 SELECT age FROM users ORDER BY age 普通索引
    外键关联的列 JOIN orders ON users.id = orders.user_id 普通索引
    唯一约束的列 user_id （主键）、 phone （唯一标识） 主键索引 / 唯一索引
    文本搜索（全文检索） MATCH (content) AGAINST ('关键词') 全文索引（MySQL

    索引可用的数据结构

    Hash索引 ：Hash索引使用散列函数将索引键映射到一个散列值，并将该散列值与索引项关联。Hash索引适用于等值查询，可以在O(1)时间复杂度内进行查找。然而， Hash****索引不适用于范围查询 ，也不能排序，并且对于散列冲突（不同键值映射到同一个散列值）的处理方式需要额外的开销。、

    平衡二叉树 ：查询时间O（logn）, 但是如果范围查询， 比如说查找大于5， 它要回溯遍历所有范围内的节点。并且插入和删除都需要对数进行调整，耗费资源和时间

    B树 ，多叉树结构，每个节点可以包含多个键和对应的数据，相比于平衡二叉树的高度变矮，但是依旧没有解决回旋查找的问题

    B+树 ，相比于b树，非叶子节点只存 关键字信息 ，所有具体数据都存在叶子结点中。叶子节点通过链表连接，形成有序的数据序列，便于范围查询和遍历操作

    索引分类

    MySQL可以按照四个角度来分类索引。

    按「数据结构」分类： B+tree索引、Hash索引、Full-text索引 。

    按「物理存储」分类： 聚簇索引（主键索引）、二级索引（辅助索引） 。

    按「字段特性」分类： 主键索引、唯一索引、普通索引、前缀索引 。

    按「字段个数」分类： 单列索引、联合索引 。

    MySQL 索引类型
    索引类型 特点及适用场景
    B+树索引 默认索引，支持全值匹配、范围查询、最左前缀原则。适用于大部分场景（如主键、普通索引）。
    哈希索引 仅支持等值查询（=, IN），内存存储，适用于精确查找（如 MEMORY 引擎）。
    全文索引 对文本内容分词索引，支持关键词搜索（如 MATCH ... AGAINST ）。
    空间索引 用于地理数据（GIS），支持空间对象查询（如点、线、面）。
    联合索引 多列组合索引，遵循最左前缀原则（如 INDEX (a, b, c) 可用 WHERE a=1 AND b=2 ）。
    覆盖索引 查询字段全部在索引中，无需回表（如 SELECT a FROM t WHERE a=1 ）。

    哈希索引

    哈希索引只适用于等值查询 （ = ），查找快但不支持 范围查询 （ BETWEEN ）。

    哈希索引无序，无法利用有序性优化 ORDER BY 和 GROUP BY 。

    哈希冲突会降低查询效率 。

    B 树索引 VS B+ 树 索引

    B+ 树的叶子节点存储全部数据，查询范围更高效

    B+ 树的所有数据都存储在叶子节点，并且叶子节点之间有 链表指针 ，支持 范围查询 和 全表扫描

    B 树每个节点都存数据，导致范围查询效率低。

    B+ 树的层数更低，磁盘 IO 更少

    B+ 树的 非叶子节点 仅存储索引，不存储数据，使得一个节点可以容纳更多的索引值，从而降低树的高度（减少磁盘 I/O）。

    B 树的非叶子节点存数据，占用更大，导致树的高度更高，查询时磁盘 I/O 次数更多。

    B+ 树更适合数据库索引的顺序存取

    B+ 树的叶子节点采用 链表 结构，可以 顺序遍历 ，适合范围查询（如 BETWEEN 查询）。

    B 树需要 中序遍历 才能获取所有数据，效率低。

    没有 B+树之前是怎么查找的？

    顺序扫描（全表扫描） ：

    没有索引时，只能 从头到尾 扫描整张表。

    时间复杂度 O(n)，在千万级别的数据中，查询效率极低。

    二叉查找树 / 红黑树 ：

    红黑树是二叉平衡树，IO 次数多，深度更深
    红黑树虽然旋转成本低、查询效率高查找复杂度 O(log n)

    但它是二叉结构，树高更高， 每次查找需要更多次磁盘访问 ，不适合数据库这样频繁查磁盘的场景

    B+ 树索引

    MySQL 主要使用 B+ 树 作为索引结构：

    B+树是为 磁盘优化设计的多路搜索树 ，相比于传统的二叉树或红黑树，有 更低的磁盘 I/O、更稳定的查询性能、更快的范围查询

    高效查询 ：

    B+ 树提供了 O(log N) 的查询时间复杂度，适合高效查找。

    只有 叶子节点（通过 双向链表 相连） 存储完整数据，

    **所有索引节点（非叶子节点）**仅存储键值，

    范围查询（BETWEEN、ORDER BY、GROUP BY）可以 顺序遍历 查询快

    插入删除稳定 ：B+ 树是一种自平衡的树结构，B+ 树的非叶子节点不存数据，只存索引，调整时仅仅是修改索引，而数据存储在叶子节点中，不受影响。

    范围查询优化 ：B+ 树的叶子节点是 有序的并且通过双向链表相连 ，范围查询只需要遍历叶子节点链表即可

    （红黑树需要进行中序遍历，效率较低）

    磁盘I/O优化：数据库索引涉及磁盘存取（I/O） ，B+树的 每个节点可以存储多个键值对 ，减少了树的高度从而 减少了磁盘I/O次数 。查询数据时需要从磁盘读取数据块到内存，树的高度越低，读取的数据块就越少。

    **全表扫描：**B+树可以方便地进行全表扫描，因为叶子节点包含了所有的数据，而红黑树不适合全表扫描。

    B+树的核心优势是“矮胖”，减少了磁盘I/O次数；并且叶子节点形成有序链表，极大优化了范围查询。

    劣势

    需要整树平衡 ：插入和删除操作可能需要分裂和合并节点，以维持树的平衡，这会带来一定的开销。但对于读多写少的OLTP场景，这个代价是值得的。

    B+ 树的自平衡树性

    B+ 树是一是 N叉平衡查找树 ，意味着 从根节点到任意叶子节点的路径长度相同 ，因此它的查找时间复杂度是 O(log N) ，其中 N 是树中的节点数。

    B+ 树的自平衡性体现在其通过 节点分裂与合并 的机制，始终保持树的高度平衡，确保查询效率稳定。以下是其核心原理：

    节点容量限制

    每个节点最多包含 M 个键值（M 为阶数），最少包含 ⌈M/2⌉ 个键值（根节点除外）。

    当插入导致节点超过容量上限时， 分裂 为两个节点，中间键值提升到父节点。

    当删除导致节点低于容量下限时， 合并 相邻兄弟节点或借用兄弟节点的键值。

    平衡效果

    所有叶子节点位于同一层，查询路径长度一致。

    分裂与合并操作自动调整树的高度，避免退化为链表。

    B+ 树索引分类

    聚簇索引 ：主键索引，叶子节点存完整数据行。

    非聚簇索引 ：辅助索引，叶子节点存主键 ID，需要回表查询。

    唯一索引 ：约束唯一性，防止重复数据。

    联合索引 ：多个列组成的索引，遵循 最左匹配原则 。

    Q：B+树叶子节点链表一定是放的是key和值吗？

    答：是的，但“值”的具体内容取决于它是哪种类型的索引。

    B+树叶子节点组成的双向链表里，每个节点都包含 键（Key） 和 值（Value） 。但“值”的含义不同：

    在聚簇索引（Clustered Index）中：

    Key ：就是表的主键值。

    Value ：是 该主键对应的整行数据 。

    所以，聚簇索引的叶子节点直接包含了全部数据。

    在非聚簇索引/二级索引（Secondary Index）中：

    Key ：是该索引定义的那个列的值（比如你在 name 字段上建的索引，Key就是具体的名字）。

    Value ：是 该行数据对应的主键值 。

    所以，二级索引的叶子节点不包含完整数据，只包含一个指向主键的“指针”。

    结论： 叶子节点链表存放的是 索引键 + 对应的数据“指针” 。这个“指针”在聚簇索引里是 数据本身 ，在非聚簇索引里是 主键ID

    聚簇索引和非聚簇索引

    聚簇索引 ： 表数据本身就是一颗B+树 。这颗B+树的叶子节点存储的是 完整的行数据 。一个表 只能有一个 聚簇索引（InnoDB中通常是主键）。

    非聚簇索引 ： 独立于数据之外的另一颗B+树 。这颗B+树的叶子节点存储的 不是完整数据，而是主键值（聚簇索引的键） ，查询需 回表 查询。一个表 可以有多个 非聚簇索引。

    聚簇索引 （如InnoDB的主键索引）

    InnoDB的 主键 是以 聚簇索引 的形式存储的，即 叶子节点存储整行数据 ，找到索引就能找到数据

    对于 范围查询和排序查询 ，聚簇索引通常更有效率，因为它避免了额外的寻址开销。

    主键索引结构为 B+ 树 ，叶子节点直接存储完整的行数据，使用主键索引查询时不需要额外访问数据行。但是进行数据删除或者修改时，需要跟新索引树，增加系统开销

    非聚簇索引（二级索引）

    非聚簇索引的叶子节点不包含完整的数据行，而是 主键值

    数据行本身存储在 聚簇索引 中，需要额外回表效率比较低。

    但数据删除或者修改时不需要更新索引树。

    非聚簇索引在使用 覆盖索引 进行查询时效率更高，不需要读取完整的数据行

    覆盖索引：索引"覆盖"了查询所需的数据 叶节点存储了完整的数据即查询结果不需要进行回表查询

    回表查询📌

    什么时候回表* ：当查询的字段无法在普通索引的叶子节点上完全获取时（即未实现 覆盖索引* ），MySQL就需要根据普通索引上找到的主键值，再回到聚簇索引中去查找完整的记录行。这个过程就是回表。

    回表指的是 查询使用了非聚簇索引，但因为需要获取完整行数据，必须回到聚簇索引查询数据 ，增加了一次 I/O 操作，影响查询效率。

    查询时：

    先搜索非聚簇索引 ，找到对应的主键值。

    再根据主键值查询聚簇索引 ，获取完整的数据行。

    这个过程称为 回表 （即需要回到聚簇索引进行二次查询）。

    回表优化策略

    覆盖索引 ：如果查询的字段 全部在非聚簇索引里 ，则可以 直接返回数据 ，避免回表（ EXPLAIN 里 Extra 显示 Using index ）。

    减少二级索引的使用 ，使用 主键查询 。

    覆盖索引

    覆盖索引 (Covering Index) ：解决的是索引的 查询效率 (Performance) 问题，指一个查询 只需要通过遍历索引就能拿到所有需要的数据 ，而无需回表 (Back to Table) 查询数据行。

    换句话说，覆盖索引包含了查询所需的全部信息，无需从数据表中再次查找数据。

    Q：可使用覆盖索引情况

    覆盖索引的前提是索引中的字段能完全满足查询条件。具体来说，包括以下几个方面：

    查询的字段 全部在索引中。

    查询条件 （WHERE 子句中的字段）也在索引中。

    排序字段 （ORDER BY 子句中的字段）也在索引中。

    分组字段 （GROUP BY 子句中的字段）也在索引中。

    Q：回表不可避免情况

    如果查询字段必须访问 主键索引 才能获取，则无法避免回表

    Q：一次查询最少要读几次磁盘？

    主键索引查询 （无需回表）：

    需要 1 次磁盘 IO （直接访问 B+ 树的叶子节点获取数据）。

    二级索引查询（回表） ：

    先搜索 二级索引 ，读取 索引页 （1 次 IO）。

    再通过 主键索引 读取 数据页 （1 次 IO）。

    最少需要 2 次磁盘 IO 。

    怎么设计聚簇索引和非聚簇索引？

    答：这是一个索引设计的策略问题，遵循以下原则：

    聚簇索引的分配：

    首选方案 ：毫无争议地交给 主键（PRIMARY KEY） 。

    为什么聚簇索引必须给主键？

    唯一性保证 ：主键唯一地标识了一行数据，这符合聚簇索引“数据物理存储顺序与索引顺序一致”的要求。

    性能最佳 ：主键查询是最高频、最核心的访问路径。用聚簇索引来服务主键查询，速度最快（一次查找就能拿到数据）。

    备选方案 ：如果表没有定义主键，InnoDB会选择一个唯一的非空索引（UNIQUE NOT NULL）来代替。如果连这个都没有，则会自动生成一个隐藏的 row-id 作为聚簇索引。

    非聚簇索引的分配：为查询服务 。

    为什么非聚簇索引要按需创建、谨慎分配？

    空间代价 ：每个索引都是一棵B+树，都会占用额外的磁盘空间。索引越多，空间开销越大。

    时间代价（主要影响写操作） ：每次执行 INSERT 、 UPDATE 、 DELETE 操作时， 数据库不仅要更新表数据，还要更新所有相关的索引 。每个额外的索引都会降低写操作的速度。

    优化原则 ：因此，索引不是越多越好。它的创建必须基于实际的、高频的查询需求，用 空间和写的代价来换取读的性能提升 。如果一个索引很少被用到，那它就是纯粹的负担。

    基于高频查询条件（WHERE子句） ：为 WHERE , JOIN ON , GROUP BY , ORDER BY 后面频繁出现的列创建索引。

    例如： SELECT * FROM users WHERE phone_number = '123...'; 就在 phone_number 上建索引。

    使用联合索引（复合索引） ：为多个经常一起作为查询条件的列创建联合索引。 注意顺序原则（最左前缀原则） 。

    例如： SELECT * FROM orders WHERE user_id = 10 AND status = 'completed'; 可以创建联合索引 (user_id, status) 。

    创建覆盖索引 ：如果某个查询只需要返回索引列包含的字段，可以创建专门的非聚簇索引来避免回表。

    例如： SELECT user_id, age FROM profiles WHERE age > 25; 可以创建索引 (age, user_id) ，这样只需要扫描索引就能得到结果，无需回表查整行数据。

    联合索引

    MySQL 中的 联合索引 是一个包含多个列的索引。底层结构类似于 B+ 树，其中每个索引项是由多个列的值组成，按照联合索引的列的顺序进行排序。联合索引能够加速涉及多个列的查询，但只要查询条件中的前缀列有索引，查询性能才会得到优化。

    联合索引排序规则

    非叶子节点：存储索引列 (A, B, C) 的值及子节点指针，按以下顺序排序：

    先按 A 升序排序；

    当 A 相等 时，按 B 升序排序；

    当 A 和 B 都相等 时，按 C 升序排序。

    叶子节点 ：存储完整的索引列 (A, B, C) 的值，以及对应的 数据行指针 （如主键值，用于回表查询数据）。 叶子节点内的数据按 (A, B, C) 的顺序整体排序，形成一个有序链表（B + 树的叶子节点双向链接）

    范围查询对后续列的影响

    若某一列使用范围查询其右侧的列无法再使用索引的有序性：

    A>1 AND B=2 AND C=3 ，索引仅用到 A 的范围查询，B 和 C 虽在条件中，但 B 的等值查询需在 A 的每个分片内单独匹配（效率降低）。

    A=2 AND B=1 AND C>1 ，A 和 B 是等值条件，C 是范围条件，C 右侧无列，因此不影响索引使用。

    存储开销与空间效率

    联合索引的每个节点需存储多个列的值，因此比单列索引占用更多存储空间。

    但在查询时，若 条件覆盖索引列（即 “覆盖索引”） ，可避免回表提升效率（如 SELECT A,B,C FROM table WHERE A=2 AND B=1 AND C>1 ）

    最左前缀匹配原则📌

    最左匹配原则是指在 使用联合索引 时，数据库从索引的最左列开始匹配，如果查询条件中没有使用索引的最左列，则无法有效利用该复合索引。

    在 MySQL 的 B+ 树索引中查询时会 优先匹配索引的最左列 ，只有按照索引的 最左边的列 进行查询，索引才能被有效利用。

    原因：在B树索引结构中，索引数据是按照键值的顺序存储的，每个叶子节点上的键值都是有序的。这种有序性使得在进行范围查询时，无法直接利用后面的索引。

    最左前缀原则 ：MySQL 中的 联合索引 ( col1, col2, col3 )， 生效情况 ：查询条件必须从联合索引的 最左列开始 且 连续 （可以不打乱顺序）。 失效情况 ：查询条件 没有包含最左列 或 跳过了中间的列 。

    索引必须从最左列开始匹配，否则索引失效 。

    遇到范围查询 ( >、\<、BETWEEN、LIKE ) 后，索引匹配停止 ，后续列无法使用索引。

    不能跳过索引中的列，否则索引失效 （如 WHERE age = 25 无法用到 (name, age, city) ）。

    LIKE 查询 ：

    LIKE 'A%' 可使用索引 ✅

    LIKE '%A%' 无法使用索引 ❌

    避免索引列上的函数和隐式类型转换 （如 UPPER(name) 或 age='25' ）。

    例子：

    有效示例 （假设索引为 (a, b, c) ）：

    WHERE a = 1 ✅ (使用a)

    WHERE a = 1 AND b = 2 ✅ (使用a,b)

    WHERE a = 1 AND b = 2 AND c = 3 ✅ (使用a,b,c)

    WHERE a = 1 AND c = 3 ✅ (使用a，c作为过滤条件，但只用到了a)

    失效/部分失效示例 ：

    WHERE b = 2 ❌ (缺少最左列a)

    WHERE b = 2 AND c = 3 ❌ (缺少最左列a)

    WHERE a = 1 AND c = 3 ⚠️ ( 部分生效 ：只用到了索引中的列 a ， c 无法用于快速查找，只能用于过滤。)

    WHERE a = 1 AND b > 10 AND c = 3 ⚠️ ( 部分生效 ：范围查询 b > 10 之后，索引列 c 就失效了，无法用于快速查找。)

    设计索引

    选择合适列：

    高选择性列（如唯一ID）优先。

    频繁出现在 WHERE 、 JOIN 、 ORDER BY 中的列。

    联合索引优化：

    最左前缀原则 ：索引(a, b, c)可优化 a=1 、 a=1 AND b=2 ，但无法优化 b=2 。

    列顺序 ：区分度高的列放左侧，等值查询列在前，范围列在后。

    避免冗余索引：

    索引(a)和索引(a, b)重复，后者可替代前者。

    覆盖索引：

    索引包含查询字段，避免回表（如 SELECT a, b FROM t WHERE c=1 ，索引(c, a, b)）。

    索引失效场景：

    对列进行函数操作（ WHERE YEAR(date) = 2023 ）。

    类型转换（ WHERE id = '100' ，id为整型）。

    前导通配符LIKE（ LIKE '%abc' ）。

    索引失效情况

    索引列参与计算 ：如果对索引列使用函数或进行运算，如 LEFT(name, 3) = 'Tom' ，索引失效。

    OR 连接某列无索引 ：OR` 连接的多个查询条件中，某个字段未建立索引，会导致全表扫描。

    隐式类型转换 ：当索引列数据类型与查询条件类型不一致，如 VARCHAR 和 INT 进行比较，会导致索引失效。

    LIKE 查询前置 % 号 ：LIKE '%keyword'` 使索引失效，必须扫描所有记录。

    范围查询导致联合索引失效 ：在联合索引中，使用范围查询（如 > , \< ）后，后续索引列无法生效。

    索引未被 MySQL 选中 ：MySQL 可能因为低选择性或优化器策略，选择全表扫描而不是索引扫描。

    索引优化方法

    最左前缀匹配原则 ：联合索引必须从最左字段开始匹配，否则索引失效。

    使用覆盖索引（减少回表查询） ：让查询的字段都包含在索引中，直接从索引获取数据，提高查询效率。

    优化 ORDER BY 和 GROUP BY ：确保排序字段在索引中，避免额外的排序操作。

    选择合适的数据类型 ：优先使用 INT 代替 VARCHAR ，减少索引存储空间，提高查询速度。

    减少 SELECT * ，只查询必要字段 ：避免不必要的数据加载，提高查询效率。

    合理创建索引，避免索引过多 ：索引过多会影响插入、更新、删除操作的性能，索引应根据查询需求建立。

    使用 EXPLAIN 分析执行计划 ：通过 EXPLAIN 语句检查 SQL 是否使用索引，优化查询策略。

    存储引擎

    MySQL 常见的有：InnoDB、MyISAM...存储引擎

    InnoDB 支持 事务、行级锁、崩溃恢复 ，适用于现代 Web 应用的高并发需求。

    MyISAM 缺乏事务机制和并发控制 ，不适合高写入场景，查询速度快适合读操作较多的场景，所以从 MySQL 5.5 开始就默认用 InnoDB 了

    InnoDB （事务型存储引擎）

    InnoDB引擎在事务支持、并发性能、崩溃恢复等方面具有优势，因此被MySQL选择为默认的存储引擎。

    事务支持 ：InnoDB引擎提供了对事务的支持，可以进行ACID（原子性、一致性、隔离性、持久性）属性的操作。Myisam存储引擎是不支持事务的。

    并发性能(行级锁) ：InnoDB引擎采用了行级锁定的机制，可以提供更好的并发性能，Myisam存储引擎只支持表锁，锁的粒度比较大。

    崩溃恢复 ：InnoDB引引擎通过 redolog 日志实现了崩溃恢复，可以在数据库发生异常情况（如断电）时，通过日志文件进行恢复，保证数据的持久性和一致性。Myisam是不支持崩溃恢复的。

    InnoDB 索引

    InnoDB 使用 B+ 树作为索引结构，索引主要有两类：

    B+ 树适合范围查找，以及磁盘 I/O 效率高，B+ 树的叶子节点 天然有链表结构 ，范围查找很快；

    主键索引（聚簇索引） 叶子节点存完整行数据，查询高效。

    二级索引（普通索引） 叶子节点存主键 ID而不是行数据，查询可能需要回表（先查索引，再根据主键查主键索引）。

    使用主键索引查询最快，非主键索引查询可能需要回表，覆盖索引可避免回表，提高查询性能

    主键设计建议

    主键适合：唯一性强、不会变、越短越好；

    建议使用自增 ID 作为主键，自增 ID 写入是 顺序的 ，不会频繁打乱 B+ 树结构；

    尽量避免用 UUID / 雪花 ID 做主键，因为插入会“打散”B+ 树，影响写入效率。

    UUID 不是递增的

    MySQL 中索引的数据结构是 B+Tree，索引树上的节点的数据是有序的，而如果使用 UUID 作为主键，因为无法保证每次产生的 UUID 有序，新的 UUID 可能需要插入到索引树的中间去，这样会频繁地导致 页分裂 ，使性能下降。

    UUID 字符串长太占用内存

    每个 UUID 由 36 个字符组成，在字符串进行比较时，需要从前往后比较，字符串越长性能越差，会导致索引树的高度越大，在索引搜索的时候，发生的磁盘 IO 次数越多，性能越差。

    MyISAM （非事务型存储引擎）

    特点 ：

    不支持事务 ：MyISAM 不支持事务，不符合 ACID 原则。

    表级锁 ：MyISAM 使用表级锁，对于大多数简单查询的应用来说效率较高，但在高并发场景下性能会受到影响。

    支持全文索引 ：MyISAM 支持全文索引，可以用来进行高效的全文搜索。

    事务

    事务机制

    定义 ： 事务（Transaction）是由一组 SQL 语句组成的一个逻辑执行单元，这些语句要么全部执行成功并提交，要么全部执行失败并回滚，不会出现部分成功、部分失败的情况。

    作用 ： MySQL 使用事务机制来保证数据库操作的 一致性（Consistency） 、 完整性（Integrity） 和 持久性（Durability）

    实现机制 ：

    日志 ：依赖 Redo Log （重做日志）保证持久性， Undo Log （回滚日志）保证原子性。

    锁机制 ：行锁、表锁、MVCC（多版本并发控制）保证隔离性。

    存储引擎 ：InnoDB 是 MySQL 默认支持事务的存储引擎。

    事务的 ACID

    ACID 是事务的四个基本特性：

    A ：原子性（Atomicity），事务要么全部执行，要么全部不执行。

    C ：一致性（Consistency），事务必须使数据库从一个一致的状态转变到另一个一致的状态。

    I ：隔离性（Isolation），事务的执行不应该受到其他事务的干扰。

    D ：持久性（Durability），一旦事务提交，其结果就是永久性的。

    事务隔离级别

    事务隔离级别用来解决**并发事务（同一时间多线程的请求）**所产生的问题：
    隔离级别 能解决的问题 可能出现的问题 实现方式
    读未提交 无 脏读、不可重复读、幻读 几乎无锁，最高并发，数据风险大
    **读已提交 ** 避免脏读 不可重复读、幻读 读时加 行级共享锁 ，读完立即释放
    **可重复读 ** 避免脏读、不可重复读 幻读 (MySQL InnoDB 通过 MVCC 解决了幻读) 事务期间读到的行内容固定
    **串行化 ** 避免所有问题 并发性能极差 所有读写都串行，等价于加表级锁

    🔴 脏读vs不可重复读vs幻读

    脏读 (Dirty Read)

    一个事务读到了另一个事务还未提交的数据。

    如果对方回滚，这部分数据就是“脏”的。

    举例：事务 A 修改余额 100→200，但没提交；事务 B 读到余额=200；结果 A 回滚，B 读到的是错的。

    不可重复读 (Non-repeatable Read)

    一个事务两次读取同一条记录，结果不一致。

    原因是另一个事务中途修改并提交了这条记录。

    幻读 (Phantom Read)

    一个事务两次执行范围查询，结果集的行数不一样。

    原因是另一个事务插入或删除了满足条件的新行。

    🟢 InnoDB 在 RR 避免幻读

    MySQL InnoDB 的 可重复读 = MVCC + Next-Key Lock

    MVCC（多版本并发控制）

    在 RR 隔离级别下， 快照读 （普通 SELECT ，不加锁的）使用 一致性视图 (Read View) 。

    事务启动时生成一致性视图（Read View），后续读取基于该视图的快照。

    新插入的数据（事务 ID 更大）对当前事务不可见。

    ✅ 例子：事务 A 在开始时拍了“快照”，事务 B 插入的新数据不在这个快照里，所以事务 A 的查询结果不会变。

    Next-Key Lock（记录锁 + 间隙锁）

    如果事务是 当前读 （例如 SELECT ... FOR UPDATE 或 UPDATE 、 DELETE ），InnoDB 会加锁。

    锁不仅锁住现有的记录，还会锁住“记录之间的间隙”，防止其他事务往间隙里插入新行。

    ✅ 例子：事务 A 在扫描 amount > 100 的时候，会给这个范围加 间隙锁 ，事务 B 就不能插入 amount=200 的新行，从而避免幻读。

    可重复读的锁机制

    InnoDB 在 可重复读（Repeatable Read） 隔离级别下，通过 多版本并发控制（MVCC） 和 锁机制 的结合，实现了对脏读、不可重复读和幻读的严格隔离。

    📝 总结 (面试版)**

    在 可重复读 (RR) 隔离级别下：

    普通 SELECT → 用 MVCC ，无锁，通过一致性视图避免幻读。

    带锁查询 / 更新 / 删除 → 用 Next-Key Lock（记录锁+间隙锁） ，阻止插入新数据，避免幻读。

    快照读 (Snapshot Read) —— 普通 SELECT

    机制 ：使用 MVCC（多版本并发控制） ，不加锁。

    基于 MVCC ：通过 ReadView 读取已提交的历史版本，无需加锁。

    事务启动时会生成一个 一致性视图 (Read View) ，后面即使有其他事务插入新行，当前事务因为用的是“历史快照”，也看不到。

    当前读 (Current Read) —— 带锁的读/写操作

    以下操作属于当前读：

    SELECT ... FOR UPDATE / SELECT ... LOCK IN SHARE MODE

    UPDATE / DELETE / INSERT （会隐式加锁）

    RR 下的当前读锁机制 = 行锁 (Record Lock) + 间隙锁 (Gap Lock) = Next-Key Lock

    显式加锁 ：当前读（如** SELECT ... FOR UPDATE 或 UPDATE 语句**）会在 扫描到的索引记录上加锁 。

    对于 唯一索引且查询条件精确匹配 的情况， 临键锁退化为记录锁（行锁）

    对于 范围查询或非唯一索 引，可能加 间隙锁或临键锁 ，以防止其他事务插入或修改范围内的数据。

    当范围查询的最大值不存在时，比如id>18但表中最大的id是20， 临键锁会退化为间隙锁

    当查询是非唯一索引的范围查询，或者匹配到多个记录时，临键锁不会退化。

    MVCC

    MVCC多版本并发控制->隔离性

    MVCC是 InnoDB 实现 并发读一致性（非阻塞读） 的一种机制，它通过 给每一行数据保存多个版本 ，实现 读写不互相阻塞实现高并发读写 的一种机制。

    原理

    MVCC 通过 Undo Log 维护数据的历史版本，结合 Read View 实现事务的隔离性。

    Undo Log（回滚日志） ：保存数据的历史版本

    每次更新/删除都会生成一条 undo log。

    undo log 保存的是 老版本 数据，MVCC 通过它来“读到旧版本”。

    Read View（可见性视图） ：决定事务能看到哪些版本

    每个事务开启时会生成自己的 Read View，里面记录 当前活动事务的 ID 。

    它保存了哪些事务是已经提交的，哪些是未提交的。查询时会根据这些 ID 判断哪些版本“对当前事务可见”

    ReadView数据结构

    m_ids：当前活跃事务ID列表。

    min_trx_id：最小活跃事务ID。

    max_trx_id：预分配下一个事务ID。

    creator_trx_id：创建该ReadView的事务ID。

    MVCC 依赖的数据结构：

    每行数据的两个隐式字段

    事务ID ：表示哪个事务正在修改这行数据。这个字段可以帮助数据库判断一个数据行是由哪个事务修改的，进而决定数据的版本。

    回滚指针（Undo日志的指针） ：指向回滚段（undo log），用于保存该数据行修改前的状态。当事务回滚时，数据库可以通过回滚日志恢复数据的原始状态。

    当多个事务并发修改同一数据时，每个事务都会在数据行中保存自己操作的数据版本，并且通过回滚指针连接到修改前的版本。

    **SELECT FOR UPDATE会绕过 MVCC **

    SELECT ... FOR UPDATE 是一种 当前读（Current Read） ， 不会使用 MVCC 的一致性读机制 ，而是 读取最新的数据版本，并加上排它锁 ，确保其他事务不能同时修改这行数据

    锁类型 ：对扫描到的记录加 排他锁（X锁） ，其他事务无法修改或加锁。

    应用场景 ：需要显式锁定数据（如避免并发修改）。

    MVCC解决原子性 持久性？

    MVCC是为了提升数据库的 并发性能 ，主要解决 读写冲突、提高事务隔离性 。

    它本身 不直接解决原子性和持久性 ，而是配合其他机制实现完整的事务特性（ACID）
    特性 是否由 MVCC 负责 解释
    原子性 ❌ 不是 由 undo log（回滚日志）+事务机制 保证，要么全部成功要么全部失败。
    一致性 ✅ 间接支持 保证读到的数据一致，比如不会读到一半修改的数据。
    隔离性 ✅ 核心作用 MVCC 主要是为了解决并发读写带来的事务隔离问题（如不可重复读、幻读）。
    持久性 ❌ 不负责 持久性由 redo log（重做日志） 和磁盘写入机制保证

    MySQL解决并发问题

    1.锁机制

    一种 悲观 的并发控制机制。我操作的时候，默认别人会来抢，所以我先“锁”住数据，不让别人动。

    Mysql提供了多种锁机制来保证数据的一致性，包括行级锁、表级锁、页级锁等。通过锁机制，可以在读写操作时对数据进行加锁，确保同时只有一个操作能够访问或修改数据。

    2.多版本并发控制 (MVCC)

    一种 乐观 的并发控制机制。我操作的时候，默认冲突很少发生。通过保存数据的历史版本，让读写操作可以无锁地并发进行。

    MVCC 是 InnoDB 实现高并发的重要技术，它使得 读不加锁，读写不冲突 。在 读已提交 (READ COMMITTED) 和 可重复读 (REPEATABLE-READ) 隔离级别下工作。它通过在数据库中保 存不同版本的数据 来实现不同事务之间的隔离。在读取数据时，Mysql会根据事务的隔离级别来选择合适的数据版本，从而保证数据的一致性。

    锁

    MySQL的锁机制
    锁类型 锁定范围 特点 应用场景
    全局锁 整个数据库实例 通过 FLUSH TABLES WITH READ LOCK 锁定所有表，阻塞所有写操作。 全库逻辑备份（ mysqldump ）。
    表级锁 整张表 锁定开销小，并发度低。分为 表共享读锁 和 表独占写锁 。 MyISAM 引擎默认锁机制。
    行级锁 单行或多行数据 锁定开销大，并发度高。InnoDB 引擎支持，包括记录锁、间隙锁、临键锁等。 高并发事务场景

    按锁粒度分类

    全局锁 ：通过flush tables with read lock 语句会将整个数据库就处于只读状态了，这时其他线程执行以下操作，增删改或者表结构修改都会阻塞。全局锁主要应用于做 全库逻辑备份 ，这样在备份数据库期间，不会因为数据或表结构的更新，而出现备份文件的数据与预期的不一样。

    表级锁 ：

    **表锁：**通过lock tables 可以对表加表锁，**MyISAM引擎只支持表级锁 **

    共享读锁允许多个事务同时读取表，读锁是共享的，但阻止写入操作，

    独占写锁则只允许一个事务进行读写，写锁是排他的，其他事务无法访问

    MyISAM 的默认锁机制 ：

    执行 SELECT 前自动加共享读锁，执行 INSERT/UPDATE/DELETE 前自动加独占写锁。高并发写入时性能差（写锁阻塞其他所有操作）。

    元数据锁（MDL）

    作用 ：防止 表结构 被修改（如 ALTER TABLE ）时，其他事务正在访问表数据。

    CRUD操作加 MDL 读锁（共享）。

    对表结构变更 ALTER TABLE 操作操作加 MDL 写锁（排他）。

    示例 ：长事务未提交时，修改表结构会被阻塞。

    意向锁 ：当执行插入、更新、删除操作，需要先对表加上「意向独占锁」，然后对该记录加独占锁。 意向锁的目的是为了快速判断表里是否有记录被加锁 。

    行级锁 ：InnoDB 引擎是支持行级锁的，而 MyISAM 引擎并不支持行级锁。

    按锁模式分类
    锁模式 特点 兼容性
    共享锁（S锁） 允许其他事务读，但禁止写（ SELECT ... LOCK IN SHARE MODE ）。 与共享锁兼容，与排他锁互斥。
    排他锁（X锁） 禁止其他事务读和写（ SELECT ... FOR UPDATE ）。 与所有锁互斥（包括共享锁和其他排他锁）。
    意向共享锁（IS） 表级锁，表明事务准备对表中的行加共享锁。 与其他意向锁兼容，与表级排他锁互斥。
    意向排他锁（IX） 表级锁，表明事务准备对表中的行加排他锁。 与其他意向锁兼容，与表级共享锁互斥。

    InnoDB 行锁分类

    InnoDB默认使用行级锁（记录锁、间隙锁等），支持更高并发。
    锁类型 锁定范围 作用 示例场景
    记录锁 锁定索引中的 单行记录 。 防止其他事务修改或删除该行。 SELECT * FROM t WHERE id=1 FOR UPDATE;
    间隙锁 锁定索引记录的 间隙 （区间）。 防止其他事务在区间内插入数据，解决幻读。 SELECT * FROM t WHERE id>10 AND id\<20 FOR UPDATE;
    临键锁 记录锁 + 间隙锁 ，锁定左开右闭区间。 默认行锁模式，同时防止当前记录被修改和间隙插入。 范围查询 WHERE id BETWEEN 5 AND 10 。
    插入意向锁 锁定待插入的间隙。 允许不同事务在同一个间隙的不同位置插入数据，减少锁冲突。 并发插入不同数据到同一区间。
    自增锁 表级锁，针对自增列。 保证自增字段值的唯一性（MySQL 8.0 优化为轻量级锁）。 批量插入自增主键数据。

    SELECT ... FOR UPDATE 锁行为

    存在对应行 ：加行级排他锁（X锁）。

    不存在对应行：

    若通过唯一索引查询，加 间隙锁（Gap Lock） ，锁定可能插入该行的区间。

    若通过非唯一索引或无索引查询，加表级锁（性能差，需避免）。

    乐观锁/悲观锁

    悲观锁 ：是数据库提供的锁机制，如行锁或表锁。在InnoDB中，使用 SELECT ... FOR UPDATE 语句会对选中的行加**行级锁，**阻止其他事务修改这些行。MyISAM任何写操作都会锁定整个表。

    乐观锁 ： 乐观锁不是数据库内置的锁机制，它是一种并发控制方法 。

    它假设所有事务处理时各自之间互不影响，各事务能够在不产生锁的情况下处理各自影响的那部分数据。在提交数据更新之前，每个事务会先检查在该事务读取数据后，有没有其他事务又修改了该数据。如果其他事务有更新的话，正在提交的事务会进行回滚。一般用 记录数据版本 来实现乐观锁。

    INSERT 语句涉及的锁

    行级锁 ：对于InnoDB引擎， INSERT 操作会对插入的行加上排他锁（X Lock）。

    元数据锁 ：会加锁表的元数据，确保在插入时表结构不会发生变化。

    对于InnoDB的 INSERT 操作，通常是会锁住目标行以及表的元数据

    MySQL 插入并发问题🟢

    MySQL中处理并发插入更新的方法：

    INSERT ... ON DUPLICATE KEY UPDATE ：原子操作，自动处理存在性判断和更新。

    如果必须加锁，可以：

    查询时 SELECT ... FOR UPDATE

    或使用悲观锁方式控制并发

    建立唯一约束防止并发插入重复:确保字段有唯一约束，避免并发导致重复。

    1.INSERT ... ON DUPLICATE KEY UPDATE（推荐）

    原子操作 ：MySQL 提供的语法糖，保证插入/更新的原子性，无需显式加锁。

    使用场景 ：唯一键冲突时触发更新，无并发问题。

    SQL
    INSERT INTO users (id, name, age)
    VALUES (1001, 'Alice', 30)
    ON DUPLICATE KEY UPDATE name = 'Alice', age = 30;

    底层原理 ：

    MySQL 先尝试插入，若发现唯一键冲突（如主键或唯一索引），则转为更新操作。

    整个过程在存储引擎层通过 行级锁 保证原子性，其他事务无法干扰。

    2.SELECT ... FOR UPDATE + 事务（悲观锁）

    适用场景 ：需要先查询再判断是否存在，需显式控制锁。

    SQL
    -- 事务1
    BEGIN;
    SELECT * FROM users WHERE id = 1001 FOR UPDATE; -- 加行锁
    -- 若存在则更新，否则插入
    INSERT INTO users (id, name, age) VALUES (1001, 'Alice', 30);
    COMMIT;

    -- 事务2在事务1提交前会被阻塞

    底层原理 ：

    FOR UPDATE 对符合条件的行加 排他锁（X锁） ，其他事务无法修改或加锁。

    若查询不存在的行：

    若通过唯一索引查询，InnoDB 会加 间隙锁（Gap Lock） ，锁定该键值的区间，防止其他事务插入导致幻读。

    例如，若表中已有 id=1000 和 id=1002 ，查询 id=1001 会锁定区间 (1000, 1002) 。

    3.乐观锁（版本号控制）

    适用场景 ：低并发冲突场景，通过版本号避免加锁。

    SQL
    -- 先查询当前版本
    SELECT id, name, version FROM users WHERE id = 1001;

    -- 更新时加条件判断：检查版本号
    UPDATE users
    SET name = 'Alice', version = version + 1
    WHERE id = 1001 AND version = 2;

    -- 若影响行数为0，说明版本冲突，需重试

    限制 ：无法直接解决“不存在则插入”问题，需结合业务逻辑处理

    日志

    Undolog

    == 事务日志（InnoDB 特有） ==

    记录事务执行时 数据的逻辑修改 ，主要作用是支持事务的回滚操作以及MVCC。

    核心作用 ：

    事务回滚（Rollback） ：这是最直观的作用。记录数据被修改前的值，以便事务执行失败或显式调用 ROLLBACK 时，将数据恢复原样。

    实现MVCC（多版本并发控制） ：这是更重要的作用。当某个事务需要读取一行数据，但这行数据正在被另一个未提交的事务修改时，InnoDB会通过Undo Log读取这行数据的旧版本快照，从而实现 非锁定读 （Read View机制），保证了隔离性（如RR级别下的可重复读）。

    Redolog

    == 事务日志（InnoDB 特有） ==

    记录的是 物理日志（数据页修改） ，事务执行时就会写入，保证 事务的持久性（D in ACID 。

    是 Innodb 存储引擎层 生成的日志，核心目的是解决数据库在崩溃后如何快速恢复的问题。

    崩溃恢复时，MySQL 会读取 Redo Log 来重做已经提交的事务，确保这些修改被持久化到数据库中。

    Binlog

    Binlog二进制日志用于记录所有对 数据库执行的更改操作 （如 INSERT、UPDATE、DELETE、DDL 等）的日志文件。

    它以 二进制格式 存储，主要包含事件（Event）的形式，记录了 数据库逻辑层面的变更，不记录查询操作（如 SELECT）

    作用：

    主从复制 ：从库通过 Binlog 实现数据同步。

    数据恢复 ：结合全量备份 + Binlog，可以恢复到任意时间点。

    Binlog 与 Redo Log 的区别：

    Redo Log 是 InnoDB 特有的，保证 崩溃恢复 。

    Binlog 是 MySQL Server 层 的，保证 复制 & 恢复 。

    ACID特性与日志的关系🟢

    原子性：由Undo Log实现。如果事务失败，可以通过Undo Log撤销已执行的操作。

    一致性：由Undo Log和Redo Log共同实现。Undo Log保证事务回滚后数据一致，Redo Log保证事务提交后数据一致。

    隔离性：主要通过MVCC机制实现，而MVCC依赖于Undo Log。

    持久性：由Redo Log实现。即使系统崩溃，也可以通过Redo Log恢复数据。

    Q：为什么 Bin Log 不能用于崩溃恢复？

    记录粒度不同 ：Bin Log 记录的是逻辑操作（如 SQL），而崩溃恢复需要精确到物理数据页的修改。

    示例：一条 UPDATE 语句可能修改多个数据页，Bin Log 无法确保所有物理修改原子性恢复。

    Q：如何保证 RedoLog 和 BinLog 的一致性？

    两阶段提交（2PC） ：

    Prepare 阶段 ：Redo Log 写入并刷盘，事务标记为 Prepare 状态。

    Commit 阶段 ：Bin Log 写入并刷盘，Redo Log 标记为 Commit 状态。

    崩溃恢复逻辑 ：

    若 Redo Log 为 Prepare 但 Bin Log 不完整：回滚事务。

    若 Redo Log 为 Prepare 且 Bin Log 完整：提交事务。

    Update事务提交日志过程

    写 Undo Log ：记录修改前的数据（用于回滚或 MVCC）。

    修改内存数据页 ：在 Buffer Pool 中更新数据。

    写 Redo Log ：将数据页的物理修改写入 Redo Log Buffer，并刷盘（确保持久性）。

    写 Bin Log ：将逻辑操作（SQL 语句）写入 Bin Log 文件并刷盘。

    提交确认 ：通过两阶段提交协议确保 Redo Log 和 Bin Log 的一致性。

    Q：MYSQL如何持久化

    MySQL主要通过InnoDB存储引擎的redo log（重做日志）和undo log（回滚日志）来实现持久化。

    redo log记录了 数据的物理修改操作 ，用于在数据库崩溃恢复时，将未完成的事务对数据的修改重新应用，保证事务的持久性。

    undo log记录了 数据修改前的状态 ，用于在事务回滚时，将数据恢复到修改前的状态，同时也用于实现MVCC（多版本并发控制）。

    崩溃恢复过程

    Redo Log 重做 ：读取 Redo Log，重放所有已提交但未写入数据页的物理操作。

    Undo Log 回滚 ：检查未提交的事务，使用 Undo Log 回滚其修改。

    Q：MySQL执行更新语句流程

    解析 SQL 语句 ：MySQL 解析器会对 SQL 语句进行解析，检查语法和语义，确定要操作的表和数据。

    查询缓存（如果启用） ：检查是否开启了查询缓存，如果开启且查询结果存在缓存，则直接返回缓存数据。

    锁定行 ：根据事务的隔离级别，MySQL 会在更新操作中对相关行加锁（如行级锁）。

    执行更新 ：MySQL 更新数据，执行数据页修改，将数据写入内存中的缓冲池。

    写入 redo log（写前日志） ：为了保证事务的持久性，MySQL 会将更新操作先写入 redo log（也叫重做日志）中。

    提交事务 ：事务完成后，如果是自动提交事务，数据库会提交并将数据写入磁盘。

    binlog 写入 ：如果启用了 binlog（用于主从复制），MySQL 会将更新操作写入 binlog 中。

    Q：MySQL执行查询语句过程

    SQL 解析 ：MySQL 首先解析查询 SQL，检查语法是否正确，并生成相应的查询计划。

    查询优化 ：优化器（Optimizer）会选择最优的执行计划（可能会选择不同的索引）。

    执行查询 ：查询执行引擎开始从数据表中读取数据。

    返回结果 ：执行结果返回给客户端。

    优化

    性能调优方案

    MySQL调优是一个系统工程，遵循“ 数据库 -> SQL -> 架构 ”的优化路径。

    数据库层面 ：

    配置合理的 缓冲池大小（ innodb_buffer_pool_size ） ，通常设为机器物理内存的50%-70%。

    配置合理的日志文件大小。

    SQL与索引层面（最有效） ：

    使用 EXPLAIN 分析SQL ：关注 type （至少 range 级别）、 key （使用的索引）、 rows （扫描行数）、 Extra （是否Using filesort/temporary）。

    创建合适的索引 ：在 WHERE , ORDER BY , GROUP BY , JOIN 的列上创建索引。

    避免索引失效 ：避免对索引列进行函数计算、类型转换、使用 != 等。

    SQL改写 ：避免 SELECT * ；优化复杂查询（如用JOIN代替子查询）；优化分页（使用 WHERE id > ? LIMIT ? 替代 LIMIT m, n ）。

    架构层面 ：

    读写分离 ：主库负责写，从库负责读。

    分库分表 ：当单表数据量过大时（如千万级），进行水平或垂直拆分。这是最后的大招。

    慢查询常见原因

    慢查询的直接原因是： 数据库需要扫描大量的数据行才能找到所需的结果 。底层原因可细分为：

    缺乏有效索引 (最常见) ： WHERE , ORDER BY , GROUP BY 子句中的列没有索引，导致全表扫描 (Full Table Scan)。

    索引失效 ：

    违反了 最左前缀原则 。

    对索引列进行了 函数操作 （如 WHERE YEAR(create_time) = 2023 ）或 表达式计算 。

    使用了 隐式类型转换 （如字符串列用数字查询）。

    使用了 != 、 NOT IN 、 IS NULL 、 IS NOT NULL （并非绝对，优化器会根据数据分布决定）。

    模糊查询 LIKE 以 % 开头 （如 LIKE '%abc' ）。

    索引选择性差 ：索引列的值重复率非常高（如“性别”列），即使用了索引，也需要回表扫描大量数据，可能不如全表扫描快。

    查询优化器选错索引 ：优化器基于统计信息（如基数 Cardinality）选择执行计划。如果统计信息不准确，它可能错误地选择了更耗时的索引甚至全表扫描。

    表数据量过大 ：即使有索引，深度分页查询（ LIMIT 1000000, 10 ）也需要遍历大量索引条目。

    锁等待 ：查询被其他事务持有的锁阻塞，导致执行时间变长。

    慢查询怎么排查🟢

    定位慢SQL可以通过以下方法：

    开启慢查询日志 ：在MySQL中，可以通过修改配置文件（如 my.cnf 或 my.ini ），设置 slow_query_log = 1 开启慢查询日志，并设置 long_query_time 来指定慢查询的时间阈值（如超过1秒的查询）

    使用 EXPLAIN 命令来分析SQL语句的执行计划 。 EXPLAIN 会展示SQL语句是如何执行的，包括表的连接顺序、使用的索引等信息，通过分析这些信息可以找出性能瓶颈。例如：

    Explain的结果里面有哪些字段判断是否走了索引

    type ：（访问类型，优选 ref / range ，避免 ALL ）。

    如果为index或range等，表示使用了索引。

    key ： 显示实际使用的索引名称。

    rows ：预估扫描的行数，行数少可能表示有效使用索引。

    Extra ：额外信息，非常关键，常见值包括：

    Using where ：使用了 WHERE 条件过滤数据。

    Using index ： → 表示覆盖索引，保持现状或扩展覆盖索引范围。

    Using index condition ：使用了索引条件下推（ICP）。

    Using temporary ：需要创建临时表来处理查询

    为 GROUP BY 字段添加索引。

    使用覆盖索引，避免回表查询。

    Using filesort ：需要进行文件排序（如 ORDER BY 非索引字段），性能较差。

    → 检查排序字段索引：为排序字段添加联合索引（确保索引顺序与排序一致）。

    减少排序数据量（如分页查询时先过滤再排序）。

    Using join buffer ：使用了连接缓存（BNL 优化）。

    慢 SQL优化方案

    创建合适的索引 ：根据 查询条件，在相关字段上创建索引 。例如，如果经常按照 某个字段进行查询 ，就在该字段上创建 单字段索引 ；若 查询条件涉及多个字段 ，考虑创建 组合索引 。但要注意索引并非越多越好，过多索引会增加数据插入、更新和删除的开销，因为每次数据变更都需要更新索引结构。

    优化查询语句SQL ：

    只查询需要的字段，避免使用 SELECT *

    拆分 复杂查询 ，用临时表缓存中间结果。

    使用 EXISTS 替代 IN ，避免全量查询。

    优化表结构 ：确保 表的字段数据类型选择合理 ，尽量使用占用空间小的数据类型，如能用 tinyint 就不用 int 。同时，避免表中存在过多的冗余字段，减少数据存储量和数据更新时的一致性维护成本。

    如何保高并发下的写入性能？

    考点 ： 高并发写入 MySQL 方案 最佳方案 ：

    分库分表 ：避免单库单表写入压力过大，利用 水平分片 提升写入能力。

    异步写入 ：用 MQ 先写入队列，后台异步写入 MySQL ，防止高并发打爆数据库。

    Redis 预写入 ：先写入 Redis，然后异步同步到数据库，适用于 计数、点赞、排行榜等场景 。

    最佳回答

    采用 批量插入 + 分库分表 + MQ 异步写入 ，确保高并发下 MySQL 不会成为瓶颈，同时利用 Redis 缓存热点数据，减少数据库压力。归档日志（Binlog）

    Binlog 记录了 所有的 SQL 语句，尤其是对数据库执行的增、删、改操作的日志 。Binlog 主要用于 主从复制 和 数据备份 。与 Redo Log 和 Undo Log 不同，Binlog 是 逻辑日志 ，它记录的是执行的 SQL 操作或行级别的修改（行事件）。Binlog 在事务提交之后写入，因此它不保证持久性，而是提供了一种增量备份的方式。

    主从复制 ：在 MySQL 的主从架构中，主服务器会将 Binlog 发送到从服务器，从服务器根据 Binlog 来同步主服务器的数据。

    数据备份 ：Binlog 提供了数据库修改的日志记录，可以用于增量备份，帮助恢复数据到某个特定时间点。

    数据表过大 有什么方法？

    分库分表是最后的“大招”，之前可以尝试很多优化：

    归档和历史化 ：将冷数据（如一年前的订单）迁移到历史表或便宜的归档存储中，让主表只保留热数据。

    分区表 (Partitioning) ：将一张大表在物理上分割成多个更小的、更易管理的部分（分区），但对应用透明逻辑上还是一张表。常用于按时间范围分区。

    垂直拆分 ：将不常用的、文本长度大的列拆分到另一张表中（一对一关系），减少主表的宽度，让每页数据能存放更多行。

    极致索引优化 ：确保所有查询都有高效的索引，并大量使用覆盖索引避免回表。

    硬件/基础设施升级 ：更快的 SSD、更大的内存（让缓冲池 Buffer Pool 能缓存更多数据）。

    查询优化 ：重构复杂查询，避免深度分页（用 WHERE id > ? LIMIT n 代替 LIMIT m, n ）

    分库分表策略

    分库分表是为 提高数据库的并发处理能力和查询性能 。

    分库方式：

    垂直分库 ：按业务拆分（如用户库、订单库）。

    水平分库 ：按分片键（如用户ID哈希）分布到不同库。

    分表方式：

    垂直分表 ：将大字段拆分到单独表。

    水平分表 ：按分片键将数据分散到多个表（如按时间分表）。

    主键设置 ：分库分表后，自增主键会导致ID冲突

    使用分布式ID生成算法（雪花算法、Redis自增）。

    Snowflake算法：

    生成64位全局唯一ID，结构： 时间戳(41位) + 机器ID(10位) + 序列号(12位) 。

    优点：趋势递增，适合索引；缺点：时钟回拨需处理。

    Redis自增ID：

    利用Redis的 INCR 命令生成连续ID。

    示例：每个分片维护一个Redis键，如 incr:order

    路由ID ：通过分片键计算数据应存储的库或表

    （如 user_id % 分库数 ）计算目标库/表。

    水平分表如何保证数据均匀分布？

    选择合理的分片键 （Sharding Key）：

    避免选择自增 ID 作为分片键，否则新数据会集中插入到一个分片，导致数据倾斜。

    选择业务相关但分布均匀的字段，如 user_id 、 order_id 。

    哈希分片 ： 通过 user_id % N 方式确保数据均匀分布，但难扩展。

    预分片 + 动态迁移 ： 预先创建足够的分片，并支持数据迁移，扩展时减少数据迁移成本。

    混合分片策略 ： 结合时间分片+哈希分片，例如 order_202401_xx ，保证数据按时间分片，同时避免数据倾斜。

    常见的分库分表策略
    分片策略 适用场景 优缺点
    哈希取模 用户表、订单表 均匀分布数据，但扩展性差
    范围分片 时间表、日志表 适合时间查询，但数据倾斜可能性大
    时间分片 订单、日志、监控数据 方便清理历史数据，但难查全量数据
    业务拆分 业务独立的表 业务解耦，减少耦合，但查询可能变复杂
    映射路由表 复杂业务 灵活扩展，但依赖路由表管理

    场景题：分库分表设计避免读扩散

    现在有一个订单表 做了分库分表 我需要支持商家订单查询也要支持美团订单号查询 如何设计才能不会出现读扩散问题

    问题核心 ：如何让两个不同的查询条件（商家ID、美团订单号）都能直接定位到唯一的分片，而不是扫描所有分片（读扩散）。

    四种方案都非常经典，我们来总结一下：

    基因法 (Genetic Algorithm) :

    原理 ：在生成美团订单号时，将分片键（商家ID）的哈希值取几位（基因）嵌入到订单号中（如后缀）。

    优点 ：无冗余存储，查询性能最佳。

    缺点 ：订单号有业务含义；后期分片数变更极其困难（致命缺点）。

    冗余到ES :

    原理 ：主库按商家ID分片，同时将数据异步同步到Elasticsearch，ES以美团订单号为Key。

    优点 ：灵活性高，可支持更多复杂查询；与DB解耦。

    缺点 ：架构复杂，引入延迟，运维成本高。

    ==路由表 (Mapping Table):==

    原理 ：单独建一张小表，存储 美团订单号 -> 商家ID 的映射关系。该表自身按美团订单号分片。

    优点 ：业务订单号纯净，方案简单通用。

    缺点 ：需要二次查询（可引入缓存缓解）。

    双写冗余表 :

    原理 ：存两份数据，一份按商家ID分片，另一份按美团订单号分片。

    优点 ：两种查询都是单分片操作，性能极致。

    缺点 ：存储和写入成本翻倍；数据一致性最难保证。

    最推荐方案 ： 路由表 + 缓存
    这是一个在复杂性、性能和成本之间取得最佳平衡的方案。查询时，先用美团订单号查路由表（或优先查缓存）得到商家ID，再用商家ID直达主表分片，完美避免读扩散。

    架构

    MySQL主从同步

    主从复制与读写分离

    核心思想 ：通过复制技术（Replication）将一个数据库服务器（主库）的数据同步到多个其他服务器（从库）。应用将 写操作 （INSERT, UPDATE, DELETE）指向主库，将 读操作 （SELECT）分散到多个从库。

    工作流程 :MySQL主从同步的原理是基于二进制日志（Binary Log）的异步复制机制。

    主库记录变更 ：主库（Master）将数据变更操作（如INSERT、UPDATE、DELETE）记录到二进制日志中，

    从库拉取日志 ：从库（Slave）通过I/O线程连接主库并拉取这些日志，写入本地的中继日志（Relay Log），

    从库应用日志 ：然后由SQL线程读取中继日志并重放这些操作，从而保持与主库的数据一致。

    同步方式

    异步复制(MySQL 默认模式) ：👉 主库执行事务后直接返回成功，不管从库有没有同步完成。

    主库上执行事务操作的线程不会等待复制 binlog 的线程同步完成，主库执行完操作后就会返回成功

    ⚠️一旦主库挂掉，从库可能丢数据。

    优点 ：性能好，延迟低。

    缺点 ：一致性差。

    半同步复制 ：主库需要等待至少 一个从库确认已接收到 Binlog 才返回成功，能在一定程度上避免数据丢失。

    同步复制 ：所有的从库都必须执行完相应的操作后，主库才返回。

    主从延迟处理方法

    强制走主库方案 ：对于大事务或资源密集型操作，直接在主库上执行，避免从库的额外延迟
