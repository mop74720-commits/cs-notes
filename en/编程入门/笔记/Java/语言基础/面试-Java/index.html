    JAVA基础

    JAVA与C++

    C++偏底层

    编译型语言 ：直接编译为机器码，运行效率高，但依赖特定平台。

    手动内存管理 ：通过 new / delete 或智能指针显式管理内存，灵活性高但易引发内存泄漏。

    Java 是跨平台语言

    解释型语言 ：编译为字节码（ .class 文件），通过 JVM（Java 虚拟机）解释执行**，实现跨平台（"Write Once, Run Anywhere"）。**

    编译成字节码后，JVM 在不同平台上都能运行，实现了“一次编译，到处运行”；

    自动内存管理 ：依赖垃圾回收（GC）机制，开发者无需手动释放内存，但可能引入 GC 停顿。

    总结就是： C++ 性能更强，Java 开发更快、更安全、跨平台 。”

    Java泛型

    Java泛型 (Generics) ：一种参数化类型机制。允许在定义类、接口、方法时使用类型参数（如 \<T> ），在使用时再指定具体的类型。它提供了 编译时类型安全检查 ，并消除了绝大部分的类型强制转换。

    伪泛型 (Type Erasure) ：Java的泛型是通过 类型擦除 来实现的，这被称为“伪泛型”。

    什么是类型擦除 ：编译器在编译期间会 移除所有泛型类型信息 。 List\<String> 和 List\<Integer> 在编译后都会变成原始的 List （ 原始类型，Raw Type ）。类型参数 \<T> 会被替换为它的 上限 （如 \<T extends Number> 中的 Number ，若无上限则替换为 Object ）。

    为什么这么设计 ： 为了向后兼容 。泛型是在Java 5中引入的。为了让使用老版本JDK编写的庞大存量代码（Raw Type代码）能继续在新版本的JVM上运行，Java设计团队选择了类型擦除这条路径。这样，泛型代码编译后与为泛型出现前编写的代码是二进制兼容的，不需要改变JVM。

    简单来说：Java的泛型只是编译器的“魔法”，它通过擦除在编译期进行类型检查，并在需要时插入强制类型转换的代码，运行时并无泛型的概念。这与C#等语言的“真泛型”（运行时保留类型信息）有本质区别。

    基本类型

    Java 共有 8 种基本数据类型，包括 byte 、 short 、 int 、 long 、 float 、 double 、 char 和 boolean ，

    它们 存储在栈上，访问速度快更高效，不能为 null （数据库查询时，如果对查询结果直接赋值为空，那么基本数据类型会返回异常），也不能用于泛型。

    整型 byte (8位)，short (16位)，int (32位)，long (64位) 0 Byte, Short, Integer, Long
    浮点型 float (32位)，double (64位) 0.0f / 0.0 Float, Double

    List\<int)>可以吗?（考泛型）

    不可以 。

    原因 ：Java的泛型只支持 引用类型 ，不支持基本数据类型（ int , char , boolean 等）。泛型在编译后会进行 类型擦除 ，所有泛型参数都会变成 Object 。而基本数据类型无法直接转换为 Object 。

    解决方案 ：使用基本数据类型对应的 包装类 。

    包装类型

    对应的包装类型分别是 Byte 、 Short 、 Integer 、 Long 、 Float 、 Double 、 Character 和 Boolean ，

    它们是 对象，存储在堆上，支持泛型，可以为 null ，但性能比基本类型差。

    【使用注意事项】

    一般来说，优先使用基本类型，性能更高，不会有 NullPointerException 空指针异常 ；

    如果需要 存入集合或需要 null 值 ，就用包装类型。

    此外，比较包装类型时，避免使用 == ，应使用 equals() 方法。

    Integer

    Integer对应的是int类型的包装类，就是把int类型包装成Object对象，比如Integer有parseInt()等方法来专门处理int类型相关的数据。

    在Java中，基本类型和 引用类型 不能直接进行转换，必须使用包装类来实现。

    例如，将一个int类型的值转换为String类型，必须先将其转换为Integer类型，然后再转换为String类型。

    Java集合中只能存储对象，而不能存储基本数据类型。因此，如果知道int类型的数据存储在集合中，必须使用Integer包装类。

    例如，假设我们有一个列表，我们想要计算列表中所有元素的和。如果我们使用基本数据类型int，我们需要使用一个循环来遍历列表，把每个元素相加。但是，如果我们使用Integer包装类，我们可以使用直接stream()方法来计算所有元素的和。

    装箱和拆箱

    自动装箱 ：基本类型 → 包装类（如 int → Integer ）；

    自动拆箱 ：包装类 → 基本类型（如 Integer → int ）

    Java 提供了自动装箱和拆箱机制，基本类型和包装类型可以自动转换，

    例如 Integer a = 100 是自动装箱，而 int b = a 是自动拆箱。但要注意，包装类型如果为 null ，拆箱时会抛 NullPointerException 。

    部分包装类型会缓存 -128 ~ 127 之间的值，比如 Integer ，超出这个范围则会创建新的对象，

    Integer x = 127; Integer y = 127; x == y 为 true 使用自动装箱（比如直接赋值）创建Integer对象时，如果值在-128到127之间范围内，会直接使用缓存中的对象，而不是新建一个实例。所以，x和y实际上指向的是同一个缓存对象

    Integer x = 128; Integer y = 128; 为 false

    Integer x = 127; Int y = 127; x == y 为 true

    当包装类和基本类型进行==比较时，包装类会被拆箱，比较的是数值本身，而不是对象引用。

    对象复制方式：深拷贝和浅拷贝

    浅拷⻉ ：浅拷贝只复制对象的基本数据类型和对象引用，但不复制引用对象，本身会在堆上创建⼀个新的对象（区别于引⽤拷⻉的⼀点）

    如果原对象包含 引用类型数据 ，浅拷贝后，新对象和原对象会指向同一块内存地址。

    修改新对象中的引用类型数据会影响原对象。

    深拷⻉ ：深拷⻉会完全复制整个对象，包括这个对象所包含的内部对象。

    新对象和原对象不共享任何引用类型数据。

    修改新对象不会影响原对象。

    引⽤拷⻉: 两个不同的引⽤指向同⼀个对象

    object

    Object 类的方法

    Object 是所有 Java 类的父类，它提供了一些基础方法：

    hashCode() ：计算对象的哈希值，在 HashMap 等集合中用于确定存储位置。

    equals(Object obj) ：比较两个对象是否相等，在集合中用于去重（如 HashSet ）。

    toString() ：返回对象的字符串表示，默认是地址，但可以重写提供更友好的信息。

    clone() ：创建对象的浅拷贝，要求类实现 Cloneable 接口。

    finalize() ：垃圾回收前调用，不建议使用。

    getClass() ：返回对象的 Class 对象，用于反射。

    wait() / notify() / notifyAll() ：用于线程同步，必须在 synchronized 代码块中使用。

    equals() 和 ==

    == 用于 比较两个变量的值 ，但 比较的内容取决于变量的类型 ：

    基本数据类型 （ int 、 double 、 char 等）：比较的是 数值 是否相等。

    引用数据类型 （ String 、 List 、 Object 等）：比较的是 对象的内存地址 （即是否是同一个对象）

    equals() 方法

    equals() 默认继承自 Object ，它的默认比较 对象的内存地址 ，即等价于 == 。 但许多类（如 String 、 Integer 、 List 等） 重写了 equals() 方法 ，用于比较 对象的值 。

    String

    String 是 Java 不可变（Immutable）对象，底层由 char[] 数组存储 。

    String 重要特点

    不可变 ： String 一旦创建，不能修改 ，所有修改操作都会创建新对象

    被 final 修饰；

    内部使用 char[] 并不暴露；

    安全性高（如被哈希表等依赖）；

    便于字符串常量池共享，提高性能。

    字符串常量池 （String Pool）： 相同字符串只存一份，节省内存

    + 号拼接优化 ：编译器会优化 String 拼接，等价于 StringBuilder

    支持 intern() ：手动把字符串加入字符串池

    字符串常量池

    JVM 中专门为**字符串（String 类）**创建的 运行时常量池 ，位于方法区（JDK8 之后为元空间）， 用于复用相同的字符串常量，节省内存 。

    🌟 特点：

    字面量方式 "abc" 会被自动放入常量池；

    new String("abc") 会创建两个对象（一个在常量池，一个在堆上）；

    intern() 方法：手动将字符串放入常量池

    new String("abc")

    "abc" 在字符串常量池中创建 （如果池中不存在）。

    **池中已有对象 "abc"**的引用 → 只创建 堆中的 String 对象 。 创建了 1 个对象。

    池中没有对象 "abc"的引用 → 先在 字符串常量池 创建 "abc" ，再创建 堆中的 String 对象 。 创建了 2 个对象。

    + 运算优化(拼接优化)

    常量拼接 ：编译时优化，结果是常量池中的对象；

    String str3 = "str" + "ing";

    在编译时会进行常量折叠 String str3 = "string"，随后将string加入到常量池中

    如果String 用final修饰 String 会被编译器当做常量来处理 就变成第一种情况

    变量拼接 ：运行时动态拼接，会创建新对象；

    String str4 = str1 + str2

    运行时创建 StringBuilder，会产生新对象

    特别的，如果String 用final修饰，会被编译器当做常量来处理

    循环拼接 ：字符串建议使用 StringBuilder ！

    如果循环+进行字符串拼接，都会创建 新的 String 对象 ，造成内存浪费

    🟢 StringBuffer vs. StringBuilder

    可变性

    String是不可变类 ，内部的value值被final所修饰，每次修改String值使都会产生新对象，

    StringBuffer 和 StringBuilder都是可变的， 允许修改内容，不会创建新对象

    安全性

    String 中的对象是 不可变，线程安全 。

    StringBuffer 线程安全（方法加 synchronized）

    对⽅法加了同步锁或者对调⽤的⽅法加了同步锁synchronized。

    适用场景： 单线程环境 下，对字符串操作

    StringBuilder**⾮线程安全的**,没有对⽅法进⾏加同步锁。

    适用场景：**多线程环境下，**对字符串操作

    性能方面： String\<StringBuffer\<StringBuilder

    存储：

    String存储在 字符串常量池 中，重复创建相同值的字符串时，会直接引用池中的对象，避免重复分配内存。

    StringBuilder、StringBuffer 在 堆内存 中

    Lambda 表达式

    Lambda 表达式是 Java 8 引入的一种新特性，用于 创建匿名函数 ，让代码更加简洁和易读。简化函数式接口（只有一个抽象方法的接口）的使用。其基本语法有以下两种形式：

    (parameters) -> expression ：当 Lambda 体只有一个表达式时使用，表达式的结果会作为返回值。

    (parameters) -> { statements; } ：当 Lambda 体包含多条语句时，需要使用大括号将语句括起来，若有返回值则需要使用 return 语句。

    传统的匿名内部类实现方式代码较为冗长，而 Lambda 表达式可以用更简洁的语法实现相同的功能。

    反射

    反射

    反射是 Java 语言提供的一种 动态机制 ，允许程序 在运行时获取类的信息 ，包括类的构造函数、方法、字段等，并可以 动态地创建对象、调用方法和访问字段 。

    通过反射，我们可以在运行时加载类、检查类的结构以及实例化对象，而 不需要在编译时就确定具体的类 。Java 反射提供了 在运行时操作类和对象的能力 ，是 各种框架底层的基础 ，但由于反射涉及到动态解析和调用，性能相对较低，避免滥用影响性能和安全性。

    反射的应用场景

    框架底层核心：

    Spring 框架：

    AOP（面向切面编程） ：动态生成代理对象，执行前置、后置逻辑。

    异常类

    Java异常体系结构：

    Error表示严重系统问题，如OutOfMemoryError，一般不处理。

    Exception是普通异常，分为：

    运行时异常

    定义 ：RuntimeException不需要显式捕获，编译器不会强制要求处理。通常是 编程错误 （如空指针、数组越界等）。

    程序运行过程中抛出 ，可能导致程序终止

    IllegalArgumentException （非法参数）

    Q：自定义业务异常继承哪个类

    在Java开发中，自定义业务异常通常继承自RuntimeException类，即运行时异常。这种做法使得异常不需要强制在方法签名中使用throws声明，便于在业务层灵活处理。当然，也可以继承Exception类来创建受检异常（checked exception），但在实际企业开发中，业务异常更常见的是继承RuntimeException。

    首先明确异常的分类：Java中异常分为Error、Exception两大类，而Exception又分为受检异常（checked exception）和非受检异常（unchecked exception，即继承自RuntimeException的异常）。业务异常属于程序正常流程中可预期的错误情况，如参数校验失败、用户不存在、余额不足等，这类异常通常不需要强制捕获，因此更适合定义为非受检异常。因此，最佳实践是让自定义业务异常继承RuntimeException。

    非运行时异常

    定义 ：非运行时异常是 Exception 及其子类（但不包括 RuntimeException ） ，必须 显式处理 （ try-catch 或 throws ），通常是 外部因素引起 （如文件、网络、数据库异常）。

    特点 ：

    必须处理 ，否则代码编译不通过

    程序可预见的异常 ，一般可恢复

    适用于 I/O、数据库、网络等外部操作

    常见非运行时异常 ：

    IOException （文件读写异常）

    SQLException （数据库异常）

    InterruptedException （线程中断异常）

    ClassNotFoundException （类未找到）

    JNI

    是什么 ：是Java平台提供的一个标准编程接口，允许 Java代码调用本地代码 （通常是C/C++），也允许本地代码调用Java代码。

    做了什么功能/为什么需要它 ：

    访问系统特定功能 ：调用操作系统底层API或硬件功能，这些是纯Java无法实现的。

    重用现有库 ：重用那些用C/C++写的、成熟且高效的现有库，避免重复造轮子。

    提升性能 ：在极端追求性能的场景下（如复杂的数学计算、图形处理），用C/C++实现的本地代码可能比Java更快。

    缺点 ： 破坏了Java的跨平台性 （需要为不同平台编译不同的本地库），引入了复杂性，且容易导致内存泄漏和JVM崩溃。

    设计模式

    1. 创建型模式（解决对象创建问题）

    单例模式（Singleton） ：确保 全局只有一个实例 ，如 Spring 管理的 Bean、Redis 连接池、日志管理器等。

    工厂模式（Factory） ：通过工厂类创建对象，屏蔽具体实现，如 BeanFactory 创建 Spring Bean、 JDBC 连接工厂。

    建造者模式（Builder） ：复杂对象的逐步构建，如 StringBuilder 、 Lombok @Builder 。

    原型模式 ：通过 克隆 创建对象，避免重复创建，如 clone() 方法。

    2. 结构型模式（解决对象访问的问题）

    适配器模式（Adapter） ：使 接口不兼容的类可以协同工作 ，如 SpringMVC 适配 HandlerAdapter 处理不同类型的请求。

    装饰器模式（Decorator） ： 动态扩展对象功能 ，如 Java IO 流（ BufferedReader 包装 FileReader ）。

    代理模式（Proxy） ：通过代理类 控制对目标对象的访问 ，如 Spring AOP（JDK 动态代理 / CGLIB 代理） 。

    3. 行为型模式（解决对象的行为）

    策略模式（Strategy） ：定义一组算法并 动态选择 ，如 SpringSecurity 认证策略。

    模板方法模式（Template Method） ：在父类中定义 算法框架 ，子类实现具体逻辑，如 JdbcTemplate 封装数据库访问流程。

    责任链模式（Chain of Responsibility） ：多个对象按顺序处理请求，如 Spring 拦截器链、Netty 处理链、Filter 过滤器链 。

    策略模式

    策略模式则是关于对象的行为，允许定义一系列算法，并将每个算法封装在独立的类中，允许客户端在运行时选择具体的算法或行为。

    策略模式的结构：

    Context （上下文）：用来存储一个策略对象，并利用这个策略对象来执行相应的算法。

    Strategy （策略接口）：定义了所有支持的算法的方法，通常是一个接口或抽象类。

    ConcreteStrategy （具体策略）：实现具体的算法或行为。

    模板方法模式

    在父类中定义 算法框架 ，子类实现具体逻辑，允许子类在不改变算法结构的情况下，重新定义该算法的某些特定步骤。

    模板方法模式的结构：

    AbstractClass （抽象类）：定义了一个模板方法，包含了算法的骨架，并调用一些 抽象方法 来实现可变的部分。

    ConcreteClass （具体类）：继承 AbstractClass ，并实现其中的 抽象方法 来完成具体的操作。

    网络I/O模型🟢

    同步阻塞I/O (BIO)

    BIO (Blocking I/O) 同步阻塞I/O 一个连接一个线程 。线程在等待数据时会被 挂起 （阻塞），直到数据准备好。。

    工作流程 ：

    应用程序调用 read 系统调用，向内核请求数据。

    内核开始准备数据（数据可能还没从网络上完全到达）。

    应用程序 一直等待 （阻塞），直到内核将数据完全准备好，并复制到应用进程的缓冲区。

    内核返回结果，应用程序才继续处理。

    特点 ： 简单 ，但性能极差。每个连接都需要一个独立的线程全程等待，大量线程会消耗巨大资源，上下文切换开销大。 是Java传统 Socket 的默认模式。

    同步非阻塞I/O (NIO)

    一个线程处理多个连接。线程会轮询询问多个连接是否有数据就绪，不会在等待时被阻塞。

    工作流程 ：

    应用程序将Socket设置为 非阻塞 模式，然后调用 read 。

    如果内核数据没准备好， 立即返回一个错误 （如 EWOULDBLOCK ），而不是阻塞程序。

    应用程序 不断轮询 内核，询问数据是否准备好。

    直到某次轮询得到数据已准备好的信号，此时再进行真正的数据读取（该阶段依然是阻塞的，即等待数据从内核空间拷贝到用户空间）。

    特点 ：将 等待数据准备 的阶段变成了非阻塞，但轮询消耗大量CPU资源。编程复杂度高，实践中一般不直接使用。

    Netty

    Netty ：一个高性能的 NIO客户端/服务器框架 。是对Java NIO的优雅封装，简化了开发。

    核心组件 ： Channel , EventLoop , ChannelHandler , ChannelPipeline 。

    线程模型 ： 主从Reactor多线程模型 。BossGroup负责接收连接，WorkerGroup负责处理I/O读写，业务逻辑可交由其他线程池处理。

    I/O多路复用

    NIO的优化版 。用 Selector (选择器) 来监听多个连接的事件（如数据可读）。只有数据就绪的连接才会被处理。

    工作流程 ：

    应用程序首先告诉内核（通过 select 、 poll 、 epoll 等系统调用）它要监听哪些Socket的描述符。

    然后应用程序阻塞在 select / epoll 调用上，而不是阻塞在真正的I/O系统调用上。

    内核监视所有被注册的Socket。当任何一个Socket的数据准备好时，内核就返回“可读”事件。

    应用程序收到通知后，再调用 read 操作， 此时数据一定已准备好，可以高效地读取 。

    特点 ：这是 同步I/O ，因为真正的 read 操作还是应用程序自己发的。它的最大优势是 一个线程可以同时处理成千上万个网络连接 。 select / poll / epoll 是其不同实现， epoll 是Linux下性能最好的方案。 这是Nginx、Node.js、Java NIO和现代Tomcat高并发的基础。

    异步I/O (AIO)

    你发起一个I/O请求，然后就可以去干别的事了。操作系统帮你处理好数据后，会回调通知你。

    工作流程 ：

    应用程序发起一个 aio_read 系统调用，并提供一个缓冲区。

    内核开始准备数据。

    应用程序立刻返回 ，继续处理其他事情，完全不被阻塞。

    内核会在 数据准备好并且已经从内核空间拷贝到用户空间的缓冲区后 ，才发送一个通知（如回调函数）告诉应用程序操作已完成。

    特点 ：这是 真正的异步I/O 。应用程序只需要发起请求和接收结果，中间过程无需任何干预。 理论上是最高效的模型 ，但Linux上的原生AIO支持并不完善，在网络编程中应用远不如Windows的IOCP广泛。Java中的AIO API ( AsynchronousServerSocketChannel ) 使用较少。

    场景：设计一个Socket服务端

    设计一个高性能、可扩展的Socket服务端，通常采用 Reactor模式 （或基于NIO的多路复用模型）。

    核心设计要点：

    使用NIO (Non-blocking IO) ：使用 ServerSocketChannel 和 Selector ，实现一个线程处理大量连接，避免为每个连接创建一个线程的巨大开销。

    线程模型 ：

    单Reactor单线程 ：所有操作（accept, read, decode, compute, encode, send）由一个线程完成。模型简单，但无法利用多核，性能有限。

    单Reactor多线程 （ 推荐 ）：

    Reactor 线程（一个）：负责监听所有事件（ OP_ACCEPT , OP_READ ）。处理 OP_ACCEPT 和 OP_READ 事件（读到数据）。

    工作者线程池 (Worker Thread Pool) ： Reactor 线程将读取到的完整请求包解码后， 封装成任务提交给线程池处理 。计算完成后，将响应结果返回给 Reactor 线程。

    Reactor 线程负责将响应写回给客户端。

    主从Reactor多线程 ：进一步将 OP_ACCEPT 和 OP_READ 事件分离。主Reactor负责接收新连接，然后将建立好的连接注册到从Reactor上。从Reactor负责这些连接的IO读写。Netty采用类似此模型。

    协议设计 ：定义应用层协议，如定长报文、分隔符、或最常见的 Length-Based协议 （在消息头中定义长度字段，解决粘包/拆包问题）。

    资源管理 ：对连接数、请求速率进行限流和熔断，防止服务被压垮。

    扩展机制

    当 ArrayList 的元素数量超过其容量时， ArrayList 会自动扩容，扩容的默认规则是将原数组的容量增加 50%（即原数组的 1.5 倍）。

    扩容是通过创建一个新的数组，将原数组中的元素拷贝到新的数组上来实现的。这个过程会使得 ArrayList 的性能有一定的影响，尤其是当元素数量非常大时，频繁的扩容会导致性能下降。

    为什么开辟一个新数组？

    数组不可扩展 ：Java 中的数组在初始化时，数组的长度是固定的，一旦创建后就无法改变大小。数组在内存中是连续的一块内存区域，一旦创建其大小就被固定。Java 中的垃圾回收机制会处理一整块内存区域，而不是单独的一个数组元素。

    内存模型 ：如果数组是可扩展的，扩展操作将涉及到内存的重新分配、拷贝和调整，如果数组长度可变内存的分配和回收将会变得非常复杂，可能会导致内存碎片问题。

    性能考虑 ：当数组达到一定容量时，开辟一个新的数组并将数据拷贝过去是一个O(n)操作，但这是扩容时必须要做的，使用新数组可以避免内存碎片问题。

    HashMap📌

    HashMap 是基于哈希表的Map接口的非同步实现。

    它存储的是键值对（Key-Value）映射，允许 null 键和 null 值。

    HashMap不保证元素的顺序，特别是它不保证顺序恒久不变。提供了（ O(1) ）时间复杂度的查找、插入和删除操作（在没有哈希冲突的情况下）。

    底层数据结构

    JDK 1.7及以前 ： 数组 + 链表

    JDK 1.8及以后 ： 数组 + 链表 + 红黑树

    数组（桶） ：存储链表的头节点或红黑树的根节点。

    链表 ：解决哈希冲突，当哈希值冲突时，元素以链表形式存储。

    红黑树 ：

    当链表长度 ≥ 8 且数组长度 ≥ 64 时，链表转换为红黑树，以提高查询效率（O(n) → O(log n)）；

    当红黑树节点数 ≤ 6 时，退化为链表

    为啥不用平衡二叉树

    这正是因为HashMap的优化方向是综合性能。在发生哈希冲突导致链表变长时，我们转为红黑树。

    这个位置可能会发生频繁的插入和删除（因为HashMap本身的put和remove操作很频繁），选择旋转次数更少的红黑树，整体性能收益更大。虽然单次查询比AVL慢一点，但这个损耗在O(log n)级别是可以接受的。”

    旋转次数

    AVL树在插入后可能需要沿着路径回溯进行多次旋转（最坏情况O(log n)次）

    红黑树的插入最多需要2次旋转，删除最多需要3次旋转。这是红黑树增删效率更高的直接原因。”

    红黑树vs平衡二叉树

    红黑树和AVL树都是高效的自平衡二叉搜索树，但它们最核心的区别在于 平衡策略的严格程度 不同，这直接导致了它们在 查询和更新操作性能上的权衡 。

    简单来说，AVL树查询更快，但维护平衡的代价更高；而红黑树通过牺牲部分查询性能，换来了更高效的插入和删除操作。”

    AVL树 追求的是 严格平衡 。它要求每个节点的左右子树高度差（平衡因子）的绝对值不能超过1。这保证了树的高度始终被维持在最小的理论值，所以 查询性能（Read）是极致优化的 。

    红黑树 则采用一种 近似平衡 的策略。它通过‘节点颜色’和‘黑高一致’等规则来确保最长的路径不会超过最短路径的两倍。它不像AVL树那么严格，所以树可能会稍微高一点， 平均查询速度会稍慢于AVL树 ，但仍然是O(log n)级别。

    如果直接使用 hashCode() ，当数组长度较小时（比如默认的 16），哈希值的高位无法参与索引计算（见下一步），导致哈希冲突概率增大

    通过哈希值映射到数组索引:位运算代替取模
    数组长度 n 是 2 的幂，因此 (n - 1) & hash 等价于 hash % n ，但位运算效率更高。

    哈希冲突

    解决方法

    如果两个不同的 Key 计算出相同的索引，就会发生 哈希冲突 。

    除了最常用的 链地址法 （拉链法），还有：

    开放定址法 ：

    线性探测 ：发生冲突后，顺序查找下一个空槽位。

    二次探测 ：使用二次方程计算下一个探测位置。

    再哈希法 ：使用第二个哈希函数计算新的地址。

    缺点 ：容易产生聚集现象；删除操作麻烦（需标记删除）；表长度固定。

    再哈希法 ：提供多个哈希函数，第一个冲突就用第二个，以此类推。

    建立公共溢出区 ：将所有冲突的元素都放入一个单独的溢出表中。

    HashMap 选择链地址法的原因 ：简单有效；易于实现；适合存储动态集合；删除操作简单。

    链地址法

    元素以链表形式存储在同一个桶中。

    当链表长度 ≥ 8 且数组长度 ≥ 64 时，链表转换为红黑树（提高查询效率）

    链地址法：把存在冲突的key组成单向链表，挂在数组之下（JDK 1.8 以后转换为红黑树）

    开放地址法：再hash**，用一个hash进行计算，直接从冲突位置向下找一个空着的数组下标，或者**建立公共溢出区，将存在冲突的key进行一个统一存放。

    双哈希法：使用两个不同的哈希函数，减少冲突几率。

    HashMap扩容机制

    触发条件

    当元素数量 > 当前容量 × 负载因子（默认负载因子 0.75，容量默认 16）。

    链表长度 ≥ 8，但数组长度 \< 64 时，优先扩容而非树化。

    为什么扩容是 2 倍？

    保持容量为 2 的幂：

    保证 (n - 1) & hash 能均匀分布元素，减少哈希冲突。

    若容量不是 2 的幂，位运算无法等价于取模，导致哈希分布不均匀。

    高效数据迁移：

    扩容后只需判断高位（旧容量的最高位），无需重新计算所有哈希值。

    例如：旧容量为 16（二进制 10000 ），新容量为 32（二进制 100000 ），只需检查哈希值第 5 位是否为 1。

    扩容流程

    新容量计算 ：旧容量 × 2（保证始终为 2 的幂）。

    **数据迁移：**遍历旧数组，重新计算每个节点的索引位置，分配到新数组。

    JDK1.8的优化 ：由于数组长度是2的幂，扩容后元素的新位置 要么在原下标位置（oldIndex），要么在原下标+旧容量的位置（oldIndex + oldCap） 。这个优化避免了重新计算hash，只需看原hash值新增的那个bit是1还是0，极大地提高了扩容效率。

    判断：若为 0，节点留在原位置；若为 1，节点移动到 原位置 + 旧容量 。

    红黑树拆分 ：当红黑树节点数 ≤ 6 时，退化为链表；否则重新生成红黑树。

    线程安全性

    HashMap是非线程安全的。 在多线程环境下主要存在以下问题：

    死循环 （JDK1.7特有）：在扩容时，采用头插法会导致链表反转，多线程同时操作可能形成循环链表，导致后续的 get() 操作出现CPU 100%的问题。

    数据覆盖 （JDK1.7和1.8都有）：多个线程同时执行 put() 操作，可能导致其中一个线程的put数据被覆盖，造成数据丢失。

    解决方案 ：

    使用 Collections.synchronizedMap(new HashMap()) 包装。

    使用 ConcurrentHashMap （ 推荐 ）

    ConcurrentHashMap 底层📌

    ConcurrentHashMap架构跟HashMap是一致的，由数组，链表和红黑树组成。HashMap扩容机制，就是在HashMap在基础上通过加锁实现了 并发安全

    线程安全原理

    JDK1.7之前 ：分段锁（Segment数组），每段独立加锁，提高并发度。 JDK1.8之后 ：CAS + synchronized （锁单个桶的头节点），降低锁粒度。

    put 操作：桶为空则CAS插入；非空则锁头节点，处理链表/红黑树

    (1) JDK 1.7：采用分段锁机制，多个线程可以并行访问不同的桶。

    Segment 数组 ：类似小型 HashMap ，每个 Segment 维护一部分数据。

    ReentrantLock ：每个 Segment 维护一个 可重入锁 ，只对局部加锁，提高并发性。

    (2) JDK 1.8：JDK 1.8 采用 CAS + synchronized 机制，避免锁竞争

    相当于通过对 链表头结点加锁 来保证线程安全的，锁的粒度相比较 Segment小 ，发生冲突和加锁的频率降低了，并发操作的性能就提高了

    加锁机制 ：根据锁竞争程度来选用的

    JDK8+的 ConcurrentHashMap 混合使用 CAS 和 synchronized锁 实现高效并发：

    线程安全实现 ：

    CAS + synchronized ：插入数据时，首先通过 CAS 尝试写入，失败（检测到哈希冲突）则使用 synchronized 锁住 数组桶的首节点 （锁粒度更细，性能更好）。

    volatile ： Node 的 val 和 next 属性用 volatile 修饰，保证线程间的可见性。

    不可变对象 ： Node 本身是不可变的，提高了安全性。

    CAS原理

    一种无锁并发机制，通过原子性比较和更新实现线程安全

    内存位置（V） ：要修改的共享变量（如 ConcurrentHashMap 中的某个键的值）。

    预期原值（A） ：线程认为该变量当前应该是什么值。

    新值（B） ：线程希望将变量更新为的值。

    执行流程 ：

    检查内存位置 V 的当前值是否等于预期原值 A 。

    如果相等，将 V 的值更新为 B 。

    如果不相等，说明其他线程已修改过 V ，本次操作失败（通常重试或放弃）。

    Synchronized具体原理

    synchronized 是一种 同步 机制，主要用于保证对共享资源的互斥访问，避免多个线程同时访问共享资源时发生数据竞争。

    使用方法 ：

    同步方法 ：修饰方法，锁定当前实例对象（或类对象）。

    同步代码块 ：指定一个对象作为锁，锁定某一段代码。

    原理 ：

    synchronized 在对象上加了一个 监视器锁 （monitor），当一个线程持有锁时，其他线程无法进入同步方法或代码块。

    线程进入同步代码块时，首先获取锁，执行完毕后释放锁。

    如果多个线程争抢同一个对象的锁，则需要等待，直到锁被释

    ConcurrentHashMap 更新key

    如果多个线程同时对 同一个 key 执行操作，例如 get + 1 和 update （假设是 put ），可能会发生 线程安全问题 ，这主要是因为：

    get 和 put 不是原子操作。即，在一个线程获取到值并更新之前，另一个线程也可能读取并修改同一个值，造成竞争条件和数据不一致。

    举个例子：

    线程A先读取到 key 的值为1，然后线程B也读取到同样的值1。

    线程A对值加1后更新为2，而线程B也对值加1后更新为2，结果 key 的值变成了2，而不是期望的3。

    解决办法：

    使用 compute 或 computeIfAbsent 方法，这些方法保证了操作的原子性。

    ConcurrentHashMap 提供的 compute 方法，它会在修改某个 key 时保证操作的原子性。

    使用 AtomicInteger 和 CAS 操作 来确保更新操作是原子性的。

    AtomicInteger 是 Java 提供的一个 原子变量类 ，它内部使用了 CAS机制 实现无锁线程安全。

    Hashtable底层📌

    Hashtable的底层 数据结构 主要是 数组加上链表 ，数组是主体，链表是解决hash冲突存在的。 HashTable是 线程安全 的，实现方式是 Hashtable的所有公共方法均采用synchronized关键字 ，当一个线程访问同步方法，另一个线程也访问的时候，就会陷入阻塞或者轮询的状态。

    Hashtable 本身是线程安全的，所有方法都加了 synchronized 。

    但由于所有访问都是全局锁，性能也不如 ConcurrentHashMap 。
